# Лабораторная 3. Доменные типы: заказ из пяти сущностей

**К лекции:** [Л3. C#: философия языка и система типов](../L03-csharp-philosophy.md)
**Условие:** проекты создаются, собираются и запускаются **из терминала**, как и раньше. Код
пишется в любом редакторе.
**Сдаётся вживую:** отчёта нет. Вы садитесь за терминал со своим проектом, показываете
результат и отвечаете на вопросы по любому шагу.

## Что нужно поставить заранее

Ничего нового: хватит .NET 10 SDK из первой лабораторной.

## Что должно быть готово

- Библиотека классов `Shop.Domain` — домен будущего сервиса заказов. Она собрана из пяти
  сущностей лекции — `record struct`, `record`, `enum`, `class`, `interface` — и у каждой своё
  место, выбранное по правилу «данные или поведение».
- Консольное приложение `HelloWorld` из прошлых лабораторных, подключённое к библиотеке ссылкой
  на проект. На нём показываются все проверки, и в нём лежит реализация интерфейса из домена.
- Главная сущность, `Order`, с равенством, которое вы написали руками. Для всех остальных
  типов равенство делает компилятор.
- Оба проекта под git, и ни `bin`, ни `obj` ни в одном из двух репозиториев.

## Что строим

| Тип | Что это |
|---|---|
| `Email`, `OrderId`, `Money` | маленькие значения с проверкой при создании: почта, идентификатор заказа, сумма |
| `Customer` | покупатель: почта и имя |
| `OrderItem` | позиция заказа: `Product`, `Quantity`, `Price` |
| `OrderStatus` | статус: `Created`, `Paid`, `Shipped`, `Delivered`, `Cancelled` |
| `Order` | заказ: идентификатор, покупатель, позиции, статус |
| `IOrderNotifier`, `OrderProcessor` | «отправитель» и тот, кто им пользуется |

Названия полей `OrderItem` важны: на них рассчитано дополнительное задание.

Какая сущность для какого типа — решаете вы, у каждого выбора спросят «почему».

## Шаги

### 2. Значения: почта, идентификатор, деньги

Почта, идентификатор заказа и сумма — не строка, не `Guid` и не число, а свои типы. Образец —
почта:

```csharp
namespace Shop.Domain;

public readonly record struct Email
{
    public string Value { get; }

    public Email(string value)
    {
        if (string.IsNullOrWhiteSpace(value) || !value.Contains('@'))
        {
            throw new ArgumentException($"Not an email: '{value}'", nameof(value));
        }

        Value = value;
    }
}
```

По тому же образцу напишите сами:

- **`OrderId`** — идентификатор заказа поверх `Guid`. Пустой `Guid` не принимается.
- **`Money`** — сумма типа `decimal`. Отрицательная сумма не создаётся.

**Вопрос:** почему здесь `readonly record struct`, а не класс и не обычная `struct`? Где
в проекте проверяется формат почты — сколько таких мест?

**Вопрос:** почему в `Money` именно `decimal`, а не `double`?

**Вопрос (усложнённый):** создайте массив `new Email[2]` и посмотрите на `Value` его первого
элемента. Проверка в конструкторе есть, `Nullable` включён — откуда там `null` и почему
компилятор не предупредил?

### 3. Данные и статус

- **`Customer`** — покупатель: почта и имя.
- **`OrderItem`** — позиция: название товара `Product`, количество `Quantity`, цена за единицу
  `Price`.
- **`OrderStatus`** — перечисление: `Created`, `Paid`, `Shipped`, `Delivered`, `Cancelled`.

**Вопрос:** что вы выбрали для `Customer` и `OrderItem` и почему? Спросите у каждого то, что
спрашивали в лекции: это данные или поведение? Что у них получилось «бесплатно», без единой
строки кода?

### 4. Заказ

**`Order`** — заказ: идентификатор, покупатель, позиции, статус. Новый заказ — `Created`.
Статус снаружи **только читается**; меняет его **один** метод, который бросает исключение при
недопустимом переходе. Допустимы: `Created → Paid`, `Created → Cancelled`, `Paid → Shipped`,
`Paid → Cancelled`, `Shipped → Delivered`. Всё остальное — нет. Таблицу допустимых переходов
вынесите во вспомогательный тип: он пригодится на шаге 7.

**Вопрос:** почему `Order` не `record`, хотя это тоже данные: идентификатор, покупатель,
позиции? Что бы получилось, если бы статус был среди параметров `record`?

### 5. Контракт и поведение

Заказ надо оплатить и сообщить об этом покупателю. Но как сообщить — почтой, в консоль или в
тестовую заглушку — домен знать не должен.

- **`IOrderNotifier`** — контракт отправителя: один метод `Send`, который принимает адрес
  получателя и текст.
- **`OrderProcessor`** — тот, кто делает дело: получает отправитель в конструкторе, а его метод
  `Pay` переводит заказ в `Paid` и отправляет покупателю сообщение.
- В **`HelloWorld`**, а не в домене, напишите `ConsoleNotifier`: он реализует `IOrderNotifier` и
  печатает сообщение в консоль.

Соберите в `Program.cs` покупателя, заказ с одной-двумя позициями, оплатите его через
`OrderProcessor` и напечатайте статус.

**Вопрос:** почему интерфейс лежит в `Shop.Domain`, а его реализация — в `HelloWorld`? Кто из
двух проектов знает о другом? Что пришлось бы менять в `OrderProcessor`, чтобы вместо консоли
отправлять настоящую почту?

**Вопрос (усложнённый):** напишите вторую реализацию — «заглушку», которая складывает
сообщения в список, — и передайте её в `OrderProcessor`. Сколько строк пришлось поменять в
`Shop.Domain`?

### 6. Равенство: как сравниваются ваши типы

Здесь главный опыт лабораторной. Все проверки печатаются в `Program.cs`.

**Сначала то, что сделал компилятор.** Для двух покупателей с одинаковыми почтой и именем:

- напечатайте результат `==`;
- напечатайте самого покупателя через `Console.WriteLine`;
- создайте копию через `with`, изменив имя, и напечатайте обе: оригинал не изменился;
- положите в `Dictionary<Email, string>` значение под одной почтой и найдите его по другому
  экземпляру `Email`, созданному из той же строки.

**Вопрос:** почему покупатель печатается как `Customer { Email = ..., Name = ... }`, хотя
`ToString` вы для него не писали? Почему `Email` работает ключом словаря без единой строки кода
про равенство?

**Теперь заказ.** Создайте два заказа с **одним и тем же** `OrderId`, но с разными покупателями
и позициями — один и тот же заказ в двух экземплярах. Напечатайте:

```csharp
Console.WriteLine(first == second);
Console.WriteLine(first.Equals(second));
Console.WriteLine(new List<Order> { first }.Contains(second));
Console.WriteLine(new HashSet<Order> { first }.Add(second));
Console.WriteLine(new Dictionary<Order, string> { [first] = "x" }.ContainsKey(second));
Console.WriteLine(new[] { first, second }.Distinct().Count());
```

Запишите шесть результатов. Теперь **напишите равенство заказа руками**: переопределите
`Equals` и `GetHashCode` так, чтобы два заказа были равны, когда у них одинаковый `OrderId`, и
больше ни от чего это не зависело. Запустите те же шесть строк снова.

**Вопрос:** что поменялось между двумя запусками, а что — нет? Почему `==` по-прежнему `False`,
хотя `Equals` вернул `True`? Какие из шести операций работают через `Equals`, а какие ещё и
через `GetHashCode`?

**Вопрос:** почему равенство заказа — по идентификатору, а равенство покупателя — по всем полям?
Что бы случилось, если бы у `Order` равенство считалось по статусу тоже?

**Вопрос (усложнённый):** закомментируйте `GetHashCode` и соберите. Что сказал компилятор?
Запустите шесть строк: какие результаты изменились и почему именно эти? Верните метод на место.

**Вопрос (усложнённый):** замените в `Email` `readonly record struct` на `readonly struct` и
сравните две одинаковые почты через `==`. Что сказал компилятор? Как теперь печатается покупатель?
Верните как было.

**Исключения.** Напоследок поймайте и напечатайте сообщения трёх исключений: почта без `@`,
отрицательная сумма, недопустимый переход статуса.

## Дополнительное задание (по желанию)

Вот фрагмент, написанный «как в C»: названия товаров, которых в одной позиции заказали больше
пяти штук, без повторов и по алфавиту. Здесь `items` — `List<OrderItem>`.

```csharp
List<string> result = new List<string>();
for (int i = 0; i < items.Count; i++) {
    if (items[i].Quantity > 5) {
        bool seen = false;
        for (int j = 0; j < result.Count; j++) {
            if (result[j] == items[i].Product) {
                seen = true;
                break;
            }
        }
        if (!seen) {
            result.Add(items[i].Product);
        }
    }
}
result.Sort(StringComparer.Ordinal);
```

Перепишите его декларативно, как на слайдах лекции, и покажите в `HelloWorld`, что на одних и
тех же позициях оба варианта дают одинаковый список.

**Вопрос:** какой метод заменил внутренний цикл с флагом `seen`? Как вы проверили, что
результаты совпадают, — сравнили глазами или кодом?

задаёт вопросы по тому, что видит на экране, и может попросить изменить одну строку — например,
убрать `GetHashCode`, сменить `record` на `class` или сделать тип `internal` — и объяснить, что
сломалось.
