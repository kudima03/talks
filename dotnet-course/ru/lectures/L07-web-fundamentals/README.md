## Сквозные тезисы

- До вашего кода отрабатывают четыре слоя и несколько чужих машин; каждый стоит времени и может изменить запрос.
- Соединение дорогое: четыре обмена до первого байта. Переиспользуй соединения.
- HTTP — текст из трёх частей и договор о смысле методов, статусов и заголовков. Договор читает инфраструктура.
- Ошибка выражается кодом, а не телом. Никогда `200` для ошибки.
- Семантика HTTP одна для всех версий; транспорт под ней меняется, ваш код — нет.
- Любой экземпляр отвечает на любой запрос. Состояние сервиса — только данные в базе.
- Стиль взаимодействия — договор о смысле поверх HTTP; выбирают по задаче, протокол под ним не отменяется.

## 1. Как данные доходят (20 мин · слайды 2–19)

- **[2]** Раздел: что происходит между Enter и первым байтом в вашем коде.
- **[3]** Вопрос: что первым делом сделает браузер? Не «отправит запрос», а «спросит DNS» — у него имя, а
  сети нужен адрес.
- **[4]** Четыре слоя: DNS — имя → адрес, TCP — соединение и порядок, TLS — шифрование и подлинность,
  HTTP — запрос и ответ. Каждый — ещё один обмен туда-обратно.
- **[5]** DNS: браузер → резолвер ОС → DNS-сервер → серверы зоны. UDP, порт 53: один вопрос, один ответ.
  Ответ кэшируется на TTL — после переезда часть клиентов ещё ходит по старому адресу, это не ошибка.
  Несколько адресов в записи — простейший балансировщик.
- **[—]** DNS может не ответить или ответить медленно; ваш сервис зависит от него так же, как клиенты. Л10:
  HTTP-клиент, который держат вечно, запоминает адрес, а адрес меняется. Запись может ссылаться на другое имя.
- **[6]** TCP: рукопожатие SYN, SYN-ACK, ACK — один обмен до первого байта. Подтверждение, повтор
  потерянного, порядок. Цена: потеря задерживает всё, что за ней (это объяснит QUIC).
- **[7]** На сервере: «слушаю порт» → очередь ОС → accept → сокет (unmanaged-ресурс из Л6, закрыть).
  Соединение — четвёрка адресов и портов. 80 — HTTP, 443 — HTTPS, ниже 1024 — только привилегированный
  процесс, поэтому локально и в контейнере 8080. Принимают медленно — очередь переполнена, отказ до HTTP.
  «Address already in use» — найдите процесс, часто это ваш же прошлый экземпляр.
- **[8]** TLS: ClientHello → ServerHello + сертификат → Finished; один обмен в 1.3, два в старых.
  Шифрование и, важнее, подлинность: имя сервера в сертификате. HTTPS = HTTP внутри TLS.
- **[—]** В проде TLS терминирует прокси, а не сервис. Л8: сертификат для разработки из SDK.
- **[9]** Четыре проверки сертификата: имя, цепочка до корня, срок, отзыв. Dev-сертификат подписан сам собой —
  добавить в доверенные один раз. Истёкший сертификат (сломался скрипт продления) — частая причина «сервис лежит».
- **[10]** HTTP: запрос и ответ поверх готового канала; надёжность, шифрование, адреса — не его забота.
  **Сервер не может начать разговор первым** — всё «от сервера» в разделе 4 это обходные пути.
- **[11]** Цена: DNS + TCP + TLS + запрос = четыре обмена; при 100 мс в одну сторону ≈ 800 мс. **Переиспользуй
  соединения!** Новый HTTP-клиент на вызов — три обмена впустую (Л10). Пул соединений, HTTP/2 — одно на всё.
- **[12]** UDP: без соединения, подтверждений, повторов, порядка. Там, где свежесть важнее полноты: DNS,
  видеозвонки, игры.
- **[13]** Вопрос: почему HTTP захотел уйти с TCP? «Ради скорости» — да, но точнее…
- **[14]** Блокировка головы очереди: десять картинок в одном соединении, пакет первой потерян — девять
  пришли и лежат в буфере, браузер их не получит. TCP отдаёт байты строго по порядку.
- **[15]** QUIC — транспорт поверх UDP: независимые потоки (порядок внутри потока); TLS внутри — одно
  рукопожатие; привязка к идентификатору — переживает смену Wi-Fi на мобильную; HTTP/3 = HTTP поверх QUIC.
- **[—]** Для автора сервиса третья версия бесплатна: код не меняется. Вопрос «зачем HTTP ушёл на UDP» задают
  на собеседовании.
- **[16]** Вкладка сети в браузере: DNS, соединение, TLS, ожидание сервера, загрузка тела. «Медленно» лечится
  в пяти разных местах — сначала смотрите разбивку.
- **[17]** Между клиентом и вами: CDN (кэш ближе к клиенту, принимает атаки), балансировщик (раздаёт
  экземплярам, проверяет «жив?»), реверс-прокси (терминирует TLS, сжимает, режет частоту и большие тела).
  Каждый может изменить запрос.
- **[—]** Ещё и чужие узлы: корпоративный прокси клиента, антивирус, вскрывающий TLS, оператор, сжимающий
  картинки.
- **[18]** Сервис за прокси видит `http` вместо `https` и адрес балансировщика вместо клиента. Правду прокси
  дописывает в `X-Forwarded-Proto` / `X-Forwarded-For`, но дописать их может кто угодно — Л8.
- **[—]** У каждого узла свой таймаут: прокси не дождался — клиент получил `504`, а в ваших логах успех,
  отправленный в никуда. Задержки узлов складываются: «у нас 5 мс» = «у клиента 200» (Л12).
- **[19]** Мысль раздела: четыре слоя и чужие машины до вашего кода; каждый стоит времени и меняет запрос.

## 2. HTTP как протокол (25 мин · слайды 20–39)

- **[20]** Раздел: структура HTTP.
- **[21]** Сырой запрос: стартовая строка (метод, путь с параметрами, версия), заголовки «имя: значение»,
  пустая строка, тело (у `GET` нет). Это текст — его можно напечатать в сокет руками.
- **[22]** Адрес по частям: путь и параметры — в стартовую строку, хост — в `Host`, схема и порт — только чтобы
  соединиться, фрагмент `#…` не отправляется. Не из набора символов — `%20` и т. п.
- **[23]** Сырой ответ: строка статуса, заголовки, пустая строка, тело. `Content-Length: 25` — ровно 25 байт
  тела; напишите 26 — клиент висит до таймаута (так и будет в лабораторной).
- **[24]** Три части: стартовая строка — «что и с чем», заголовки — «как» (формат, длина, кэш, авторизация,
  идентификатор трассировки), тело — данные предметной области. Тело по `Content-Type`: JSON, HTML-форма,
  multipart (файл с полями), байты. Без `Content-Type` — ошибка 4xx.
- **[25]** Методы: таблица «безопасный / идемпотентный / тело» и что делает каждый — `GET`, `HEAD`, `POST`,
  `PUT`, `PATCH`, `DELETE`, `OPTIONS`, `QUERY`. Метод — семантика, не обязанность: остальное — `405`.
- **[—]** `PUT` — замена целиком, `PATCH` — часть (удобнее клиенту, сложнее серверу). Действие вне CRUD —
  `POST` на адрес с именем действия.
- **[26]** Повтор: `GET`/`HEAD`/`PUT`/`DELETE` повторять можно, `POST` — два заказа. Повторяемый `POST` —
  ключ идемпотентности (платёжные системы, Л10). `GET`, который удаляет, — робот удалит базу.
- **[27]** Вопрос: может ли у `GET` быть тело? Правы обе стороны: на бумаге да, смысла нет.
- **[28]** На деле тело `GET` выбрасывают прокси и игнорируют кэши. `QUERY` — безопасный, идемпотентный,
  кэшируемый по телу; проходит стандартизацию — проверьте клиент и прокси. Пока нельзя — `POST /…/search`
  и пометка в документации.
- **[29]** Пять групп, группа важнее номера: 1xx продолжаем (`100`, `101`), 2xx получилось (`200`, `201` +
  `Location`, `204`), 3xx иди туда (`301`/`302`, `304`), 4xx ты ошибся, 5xx я ошибся (`500` — исключение,
  `502`/`504` — проблема между узлами, а не в коде, `503` — временно).
- **[30]** 4xx: `400` не разобрать, `401` не знаем кто, `403` знаем и нельзя (путают — основа Л11), `404`,
  `405`, `409` конфликт, `422` невалидно (валидация Л9), `429` слишком часто.
- **[31]** Вопрос: заказа нет — какой статус? «200 с “не найден” в теле» или «404»?
- **[32]** `404`. «200 с ошибкой внутри» — самая частая ошибка: клиент, прокси, кэш, мониторинг смотрят на
  код — мониторинг покажет 100 % успеха. Код — контракт с инфраструктурой, тело уточняет.
- **[33]** Правила: успех 2xx (разный для создания, изменения, чтения); 4xx разный по смыслу; `500` только из
  обработчика на границе (Л8), никогда руками; никогда `200` для ошибки. Формат тела ошибки — один на сервис,
  свой, формируется в одном месте.
- **[—]** `202` — принято, результат позже, в теле адрес. Перенаправления в API почти не используются.
- **[34]** Заголовки — три темы: согласование (`Content-Type`, `Accept`; Л9), кэширование (`Cache-Control`,
  `ETag`, `If-None-Match`; Л12), состояние (`Cookie`, `Set-Cookie`, `Authorization`; Л11). `Content-Type` в
  ответе обязателен всегда.
- **[—]** Кодировка — часть `Content-Type` (`charset=utf-8`). Язык — отдельный заголовок, в API редко.
- **[35]** Условный запрос: `200` + `ETag: "v7"` → следующий `GET` с `If-None-Match: "v7"` → `304` без тела.
  Механика встроена в браузеры и прокси; нужно только выставить заголовки.
- **[—]** Cookie: сервер просит запомнить пару, клиент шлёт её с каждым запросом. `Authorization: Bearer …` —
  токен; оба — состояние, которое носит клиент (к разделу 3).
- **[36]** Флаги cookie: `HttpOnly`, `Secure`, `SameSite`. «В curl работает, в браузере нет» — почти всегда
  CORS: запрос к API на другом домене браузер сначала согласует через `OPTIONS`.
- **[37]** `Host` (обязателен с 1.1), `Content-Length` или `Transfer-Encoding: chunked`, `Location`,
  `Accept-Encoding` — сжатие бесплатно, JSON сжимается в разы; обычно делает прокси, сервер тоже умеет (Л8).
- **[38]** 1.1 — текст, один запрос за раз на соединение, шесть соединений — костыль; 2 — двоичный, потоки в
  одном соединении, сжатые заголовки, но всё ещё одна TCP-очередь; 3 — то же поверх QUIC. Семантика одна —
  код не меняется. По умолчанию сервер говорит на 1.1 и 2, третью включают явно.
- **[—]** Конец тела без закрытия соединения в 1.1 — `Content-Length` или chunked с нулевым куском; во 2-й
  вопрос исчезает (кадры со своей длиной). Учите семантику — транспорт поменялся дважды за десять лет.
- **[39]** Мысль раздела: HTTP — текст из трёх частей и договор о смысле; договор читает инфраструктура.

## 3. Почему сервис обязан быть stateless (10 мин · слайды 40–48)

- **[40]** Раздел: любой экземпляр отвечает на любой запрос.
- **[41]** Вопрос: вошёл на первом экземпляре, следующий запрос попал на второй — что увидит? Попросят войти
  снова: у второго своя память.
- **[42]** Stateless: между запросами сервис не хранит в памяти ничего о клиенте; запрос несёт всё нужное.
  Исторически — сессия в памяти + cookie, работает до второго экземпляра. В ASP.NET Core сессия хранится во
  внешнем кэше; в курсе не используем — токен (Л11) решает без хранения.
- **[43]** Картинка: stateless — одинаковые экземпляры и общее хранилище; сессии в памяти — балансировщик
  должен помнить, кого куда, — липкие сессии, неравномерная нагрузка.
- **[44]** Четыре причины: масштабирование (новые экземпляры сразу работают), перезапуск по одному (никого не
  разлогинило), отказ (остальные приняли долю), тестируемость (запрос зависит только от себя). The
  Twelve-Factor App, пункт VI.
- **[—]** Вертикальное масштабирование упирается в потолок и требует остановки; горизонтальное — только в
  деньги, но лишь для сервиса, которому всё равно, на какой машине он.
- **[45]** Четыре места: клиент (интерфейс), токен (кто и что можно), общий кэш (то, что можно пересчитать),
  база (всё, что должно пережить всё). Ни одно — не память экземпляра.
- **[46]** **Состояние сервиса — только данные в базе.** Клиент и токен — то, что запрос приносит с собой;
  кэш — ускоритель: потеряли — ничего не сломалось, только медленнее. Потеря кэша что-то ломает — значит,
  в кэше то, чему место в базе. Stateless не значит «без состояния».
- **[47]** В памяти можно: состояние процесса — конфигурация, пул соединений, справочники, замороженный
  словарь (Л5), локальный кэш поверх общего. Нельзя: состояние клиента. Проверка: исчезнет экземпляр —
  потеряет ли что-то клиент? Фоновая задача у двух экземпляров запустится дважды.
- **[—]** Следствия для кода: идентичность читается из запроса; идентификатор трассировки в запросе (Л12);
  кэш в памяти — ускоритель, который может отстать, а не источник правды.
- **[48]** Мысль раздела: экземпляр не должен быть особенным — особенное вы потеряете при первом перезапуске.

## 4. Технологии взаимодействия (25 мин · слайды 49–67)

- **[49]** Раздел: договор о смысле поверх HTTP.
- **[50]** Вопрос: кто вызывал чужой API? Адрес, метод, JSON — это REST или то, что им называют.
- **[51]** REST: ресурс — адрес, действие — метод. `GET`/`PUT`/`DELETE` `/orders/42`, `POST /orders`,
  `POST /orders/42/cancel`. Статусы — что вышло. Не изобретать протокол поверх HTTP.
- **[52]** Прижился не по техническим причинам: нужен только HTTP, инфраструктура понимает без настройки,
  читается глазами. Нет: строгого контракта (OpenAPI — Л9), стриминга, типов. Для публичного API — выбор по
  умолчанию; сервис курса — REST.
- **[53]** Хороший REST-API: существительные во множественном, вложенность — принадлежность, фильтры и
  страницы — параметрами, версия в адресе или заголовке. JSON: нет дат и точных десятичных — деньги (Л3)
  строкой или с договорённой точностью.
- **[—]** Шкала зрелости REST: большинство останавливается на «ресурсы, методы, статусы» — достаточно.
- **[54]** SOAP: XML-конверт Envelope → Header → Body → операция. Всегда `POST`, один адрес, почти всегда `200`,
  смысл внутри конверта. WSDL — контракт.
- **[—]** XML: пространства имён (главная боль), XSD, многословно. По WSDL инструмент SDK генерирует клиент
  за минуту.
- **[55]** Даёт: строгий контракт, кодогенерацию, подписи/шифрование/транзакции. Ушли: многословно, не
  кэшируется, не читается. Банки и госорганы — встретите. Логируйте сырой XML с первого дня.
- **[56]** Вопрос: мобильному — номер и статус, вебу — заказ целиком; адрес один. «Всё» — мегабайт ради двух
  полей; «два адреса» — через год тридцать. Избыточная и недостаточная выборка.
- **[57]** GraphQL: клиент описывает форму ответа, сервер отдаёт ровно её. Один адрес, обычно `POST`; схема
  проверяет запрос до выполнения. Того же семейства — PureQL.
- **[58]** Цена на сервере: произвольная глубина, наивно — запрос в базу на каждое поле (квадрат из Л5),
  HTTP-кэш не работает, авторизация по полю. Операции: запрос, мутация, подписка (через WebSocket).
  Оправдан, когда клиентов много и они разные.
- **[59]** gRPC: контракт сначала — `.proto`, из него клиент и заготовка сервера на любом языке; типы
  проверяет компилятор.
- **[—]** REST думает ресурсами, RPC — операциями: выбор стиля — отчасти выбор того, как думает потребитель.
- **[60]** Двоичный формат, HTTP/2 → четыре вида вызовов: обычный, серверный, клиентский, двунаправленный
  стриминг. Цена: не читается глазами, браузеру нужна прослойка. Окупается между своими сервисами; в .NET —
  встроенная поддержка и шаблон.
- **[61]** Версионирование: номер поля — контракт навсегда. Добавить поле с новым номером — можно, удалить —
  можно, переиспользовать номер — нельзя. Неизвестные поля пропускаются.
- **[62]** SSE: обычный ответ `text/event-stream` без длины, соединение не закрывается, событие — `data:` и
  пустая строка. Одно направление; браузер переподключается сам. Так стримят ответы языковые модели.
- **[—]** Л9: обработчик вернёт `IAsyncEnumerable` (Л6) — сервер сам пишет тело кусками. Ограничения SSE:
  только текст, прокси буферизуют, в HTTP/1.1 — соединение на поток.
- **[63]** WebSocket: `GET` с `Upgrade` → `101` → HTTP закончился, дальше кадры в обе стороны. Прокси и
  балансировщики должны уметь его пропускать.
- **[64]** SSE — одно направление, обычный HTTP; WebSocket — обе стороны, другой протокол, соединение —
  состояние (клиент на первом экземпляре, событие на втором → шина между экземплярами). Достаточно одного
  направления — SSE. Heartbeat, переподключение, нумерация сообщений — проектирование, не протокол.
- **[65]** Таблица сравнения: контракт, формат, стриминг, браузер, кэш, цена входа.
- **[66]** Выбор по задаче: публичный API — REST; между своими сервисами — gRPC; много разных клиентов —
  GraphQL; старая система — SOAP; поток от сервера — SSE; обе стороны — WebSocket. Стили сочетаются в одной
  системе.
- **[—]** Длинный опрос — история: каждое уведомление — новый запрос со всеми четырьмя слоями.
- **[—]** Дальше: Л8 — сервер и конвейер; Л9 — REST-контракт и стриминг; Л11 — токен из `Authorization`.
  Лабораторная 7 — HTTP-сервер на сокетах.
- **[67]** Мысль раздела: стиль — договор о смысле поверх HTTP; выбирают по задаче, протокол под ним не
  отменяется.
