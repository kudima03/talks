# Лабораторная 7. Магазин по HTTP: сервер на сокетах

**К лекции:** [Л7. Веб-фундамент: HTTP и стили взаимодействия](../L07-web-fundamentals.md)
**Условие:** проекты создаются, собираются и запускаются **из терминала**, как и раньше. Код
пишется в любом редакторе. Никаких веб-фреймворков: только `TcpListener`, поток байтов и ваши
руки.
**Сдаётся вживую:** отчёта нет. Вы садитесь за терминал со своим проектом, показываете
результат и отвечаете на вопросы по любому шагу.

## Что нужно поставить заранее

- .NET 10 SDK, как и раньше.
- `curl`. В Linux и macOS он обычно уже есть, в Windows 10 и новее — тоже.
- `nc` (netcat) — чтобы отправить серверу байты, которые `curl` отправлять не станет. В Linux и
  macOS он обычно уже есть; в Windows работайте в WSL. Команды ниже написаны для `nc` из Linux;
  если ваш `nc` не знает ключа `-q`, уберите его и закройте `nc` по Ctrl+C, когда придёт ответ.
- Любой браузер.
- `Shop.Domain` из прошлых лабораторных: `Order`, `Customer`, `OrderStatus`, `Money` и `Total()`
  из пятой.

## Что должно быть готово

- Новый консольный проект **`Shop.RawServer`** рядом с `Shop.Domain` и `HelloWorld`, со ссылкой
  на `Shop.Domain`.
- Сервер на `TcpListener`: принимает соединения асинхронно и останавливается по Ctrl+C.
- Запрос **разобран руками**: стартовая строка на метод, путь и версию, заголовки — в словарь без
  учёта регистра имён, тело — ровно по `Content-Length`.
- Ответ **собран руками**: строка статуса, `Content-Type`, `Content-Length` **в байтах**, пустая
  строка, тело.
- Три адреса магазина; `404` на неизвестный адрес и на несуществующий заказ; `405` с заголовком
  `Allow` на чужой метод.
- `OrderStore` — заказы в памяти, без единой строчки про HTTP.
- Вы своими руками сломали ответ четырьмя способами и знаете, что в каждом случае видит клиент.
- Сборка без единого предупреждения. Проект под git.

## Что строим

| Тип или файл | Где | Что это |
|---|---|---|
| `OrderStore` | `Shop.RawServer` | заказы в памяти, номера с единицы, как в оболочке; про HTTP не знает |
| `HttpRequest` | `Shop.RawServer` | разобранный запрос: метод, путь, версия, заголовки, тело |
| `RequestReader` | `Shop.RawServer` | байты из сокета → `HttpRequest` |
| `HttpResponse`, `ResponseWriter` | `Shop.RawServer` | ответ и его запись в сокет |
| `Router` | `Shop.RawServer` | `HttpRequest` → `HttpResponse` |
| `Program.cs` | `Shop.RawServer` | приём соединений и остановка по Ctrl+C |

Адреса сервера. Все ответы — `text/plain; charset=utf-8`:

| Запрос | Ответ |
|---|---|
| `GET /` | `200`, приветствие по-русски: `Магазин работает` |
| `GET /orders` | `200`, по строке на заказ — как `list` в оболочке четвёртой лабораторной |
| `GET /orders/<номер>` | `200` и один заказ; нет такого номера — `404` |
| другой метод на одном из этих адресов | `405` и заголовок `Allow: GET` |
| любой другой адрес | `404` |

Сессия может выглядеть так (ключ `-i` показывает строку статуса и заголовки ответа):

```text
$ curl -i http://localhost:8088/orders
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Content-Length: 57
Connection: close

1  Ann Smith  Paid  300.00
2  Bob Brown  Created  120.00
$ curl -i http://localhost:8088/orders/7
HTTP/1.1 404 Not Found
Content-Type: text/plain; charset=utf-8
Content-Length: 11
Connection: close

no order 7
$ curl -i -X DELETE http://localhost:8088/orders/1
HTTP/1.1 405 Method Not Allowed
Content-Type: text/plain; charset=utf-8
Content-Length: 19
Allow: GET
Connection: close

method not allowed
```

Текст тел — на ваше усмотрение. Статусы, заголовки и их значения — нет: их читает не человек, а
клиент.

### 1. Проект и заказы в памяти

1. Рядом с папками `Shop.Domain` и `HelloWorld` — не внутри них — создайте проект и подключите
   домен:

   ```sh
   dotnet new console --name Shop.RawServer
   cd Shop.RawServer
   dotnet add reference ../Shop.Domain
   ```

2. Напишите класс `OrderStore`. При создании он заводит два заказа **через методы вашего
   домена**, а не в обход них:
   - `ann@example.com`, Ann Smith: 2 × Green tea по 150.00, заказ оплачен;
   - `bob@example.com`, Bob Brown: 1 × Coffee за 120.00, заказ только создан.
3. Снаружи у `OrderStore` два члена: `IReadOnlyList<Order> All { get; }` и
   `Order? Find(int number)`. Номер — место заказа в списке с единицы, как в оболочке. Нет такого
   номера — `null`.
4. В файле `OrderStore` не должно быть ничего про HTTP: ни `using System.Net`, ни статусов, ни
   строк ответа.

**Вопрос:** почему `OrderStore` не знает про HTTP? Что пришлось бы менять в нём, если бы завтра
те же заказы понадобилось отдавать не через сокет, а через готовый веб-сервер?

**Вопрос:** заказы живут в памяти процесса. Нарушает ли ваш сервер правило третьего раздела
лекции? Что увидят клиенты, если сервер перезапустить, и что — если запустить два экземпляра за
балансировщиком?

### 2. Слушать порт

1. В `Program.cs` заведите источник отмены и свяжите его с Ctrl+C:

   ```csharp
   using CancellationTokenSource stop = new CancellationTokenSource();
   Console.CancelKeyPress += (sender, e) =>
   {
       e.Cancel = true;
       stop.Cancel();
   };
   ```

2. Создайте `TcpListener` на `IPAddress.Loopback` и порту `8088` (или любом свободном выше
   1024), объявите его через `using` и вызовите `Start()`. Напечатайте, на каком адресе сервер
   слушает.
3. Напишите цикл приёма: `await listener.AcceptTcpClientAsync(stop.Token)`, соединение — через
   `using`. Токен передаётся в каждый асинхронный вызов, который его принимает.
4. Остановка по Ctrl+C выражается исключением отмены. Поймайте его **один раз**, вокруг всего
   цикла, с фильтром `when` на то, что отмену действительно запросили, и напечатайте `stopped`.
5. Пока сервер ничего не отвечает: принял соединение и закрыл. Запустите его и в другом
   терминале выполните `curl -v http://localhost:8088/`. Запишите последнюю строку вывода `curl`.
6. Не останавливая первый экземпляр, запустите второй в третьем терминале.

**Вопрос:** что напечатал `curl` в пункте 5 и почему? Что напечатал второй экземпляр в пункте 6,
с каким кодом завершился и как найти процесс, который держит порт?

**Вопрос:** в выводе `curl -v` есть строка `Trying [::1]:8088...` и отказ в соединении. Почему
`curl` сначала пошёл туда и почему получил отказ? Что поменять в сервере, чтобы этой строки не
было?

**Вопрос (усложнённый):** уберите `e.Cancel = true` и остановите сервер по Ctrl+C. Напечаталось
ли `stopped`? Какой код завершения у процесса (`echo $?`) — до правки и после?

### 3. Читать запрос

Запрос — это байты. Заголовки — текст в ASCII, тело — сколько угодно байтов, и где кончаются
одни и начинается другое, говорит только пустая строка.

1. Читайте поток по одному байту и складывайте в список, пока последние четыре байта не станут
   `\r\n\r\n`. Это конец заголовков; всё, что до него, переведите в строку через
   `Encoding.ASCII`.
2. Если клиент закрыл соединение раньше, чем пришла пустая строка (`ReadAsync` вернул 0), ничего
   не отвечайте: отвечать некому.
3. Разбейте текст по `"\r\n"`. Первая строка — стартовая: ровно три части через пробел — метод,
   цель запроса, версия. Не три — запрос не разобран.
4. Остальные строки — заголовки. Имя — до **первого** двоеточия, значение — после него, без
   пробелов по краям. Сложите их в `Dictionary<string, string>` с
   `StringComparer.OrdinalIgnoreCase`. Строка без двоеточия — запрос не разобран.
5. Если есть `Content-Length`, прочитайте **ровно столько байтов** тела — `ReadExactlyAsync` с
   токеном. Значение не число или отрицательное — запрос не разобран.
6. Путь — цель запроса до `?`, если он есть.
7. Сложите всё в record `HttpRequest`. Неразобранный запрос — ответ `400`.

**Вопрос:** почему не `StreamReader` и `ReadLineAsync`, как в прошлой лабораторной? Что он
прочитает из сокета сверх строки и в чём он считает длину?

**Вопрос:** зачем словарю `OrdinalIgnoreCase`? Отправьте серверу заголовки с маленькой буквы и
проверьте, что он их понял:

```sh
printf 'GET /orders/2 HTTP/1.1\r\nhost: localhost\r\n\r\n' | nc -q 2 localhost 8088
```

**Вопрос:** зачем читать тело запроса, на который вы всё равно ответите `405`?

**Вопрос (усложнённый):** клиент прислал `Content-Length: 2000000000` и три байта тела. Что
сделает ваш сервер — по строкам кода? Что будет, если таких клиентов придёт десять? Кто в
цепочке узлов из первого раздела лекции защищает от этого сервис, который сам не защищается?

### 4. Собрать ответ

1. Опишите ответ record `HttpResponse`: код, поясняющий текст, `Content-Type`, тело как
   `byte[]`, необязательное значение для `Allow`.
2. Тело из строки получайте через `Encoding.UTF8.GetBytes`.
3. `ResponseWriter` пишет в поток по порядку:
   - строку статуса: `HTTP/1.1 404 Not Found`;
   - `Content-Type`;
   - `Content-Length` — **длину массива байтов тела**;
   - `Allow`, если он задан;
   - `Connection: close` — после ответа вы закрываете соединение;
   - пустую строку;
   - тело.
4. Каждая строка заголовков кончается на `\r\n`. Заголовки переводите в байты через
   `Encoding.ASCII`, тело уже в байтах.

**Вопрос:** сколько символов в строке `Магазин работает` с переводом строки и сколько байтов
в её теле? Откуда разница?

**Вопрос:** что обещает клиенту заголовок `Connection: close` и где в вашем коде это обещание
выполняется?

### 5. Маршруты

1. Разбейте путь на части: `request.Path.Split('/', StringSplitOptions.RemoveEmptyEntries)`.
2. Тело `Router.Route` — **одно switch-выражение** над методом и частями пути, паттернами списка,
   как разбор команд в четвёртой лабораторной:

   ```csharp
   (request.Method, segments) switch
   {
       ("GET", []) => ...,
       ("GET", ["orders"]) => ...,
       ...
   }
   ```

3. Номер заказа разбирайте в `when` через `int.TryParse`. `/orders/abc` — такого ресурса нет,
   это `404`.
4. Строка заказа — как в `list` оболочки: номер, имя покупателя, статус, сумма, например
   `1  Ann Smith  Paid  300.00`. Сумма — через ваш `Total()`.
5. Нет заказа с таким номером — `404` с коротким телом. Не `200` с текстом «не найден».
6. Другой метод на `/`, `/orders` или `/orders/<номер>` — `405` и `Allow: GET`.
7. После каждого ответа печатайте в консоль сервера одну строку: метод, путь, код.

**Вопрос:** почему на `GET /orders/7` — `404`, а не `200` с текстом `no order 7`? Кто, кроме
человека, читает код ответа?

**Вопрос:** почему `DELETE /orders/1` — это `405`, а не `404`? Что говорит клиенту `Allow`?

**Вопрос (усложнённый):** `HEAD` — тот же `GET`, только без тела. Что должен вернуть ваш сервер
на `HEAD /orders` и какое значение `Content-Length` в нём правильное — `0` или `57`?

### 7. Сломайте нарочно

Здесь главный опыт лабораторной. Каждую правку делайте по одной, запускайте `curl -v` и
записывайте, что он напечатал. После каждой правки возвращайте как было.

1. **Длина в символах.** Посчитайте `Content-Length` по строке тела, а не по байтам. Запросите
   `/`.
2. **Длина на единицу больше.** Верните байты и прибавьте к длине единицу. Запросите `/`.
3. **Длина больше, соединение не закрыто.** Оставьте лишнюю единицу и уберите `using` у
   принятого соединения. Запросите `/` с ограничением времени: `curl -v --max-time 5 ...`.
   Потом верните правильную длину, но `using` пока не возвращайте, и запросите ещё раз. Теперь
   верните и `using`.
4. **Нет пустой строки.** Не пишите пустую строку между заголовками и телом. Запросите `/`.
5. **`\n` вместо `\r\n`.** Пишите заголовки ответа с `\n`. Запросите `/orders`. Верните `\r\n`
   и отправьте серверу запрос с `\n`:

   ```sh
   printf 'GET / HTTP/1.1\nHost: localhost\n\n' | timeout 3 nc localhost 8088
   ```

6. **Недописанный запрос.** Отправьте серверу заголовки без пустой строки и держите соединение:

   ```sh
   (printf 'GET / HTTP/1.1\r\nHost: localhost\r\n'; sleep 30) | nc localhost 8088
   ```

   Пока оно открыто, в другом терминале: `curl -v --max-time 3 http://localhost:8088/`. Потом
   прервите `nc` по Ctrl+C и посмотрите в консоль сервера.

**Вопрос:** в каком из пунктов 1–5 `curl` **не сообщил об ошибке**, а ответ при этом
неправильный? Почему это хуже, чем зависание?

**Вопрос:** почему в пункте 2 `curl` сразу пишет об ошибке, а в пункте 3 висит? Что из этого
видно про неправильную длину и про незакрытое соединение — по отдельности?

**Вопрос:** `curl` спокойно принял ответ с `\n`, а ваш сервер на запрос с `\n` не ответил.
Кто из них прав и почему это разные решения?

**Вопрос:** в пункте 6 `curl` напечатал `Connected`, хотя ваш сервер его соединение ещё не
принял. Кто тогда завершил рукопожатие? Почему один недописанный запрос остановил обслуживание
всех?

**Вопрос (усложнённый):** как сделать, чтобы один медленный клиент не держал остальных? Нужны
две вещи из прошлой лекции: что сделать с задачей обработки соединения в цикле приёма и как
ограничить время на чтение заголовков. Где здесь легко потерять исключение?

## Как проходит приёмка

Вы за своим терминалом, сервер собран и запущен. Принимающий отправляет ему запросы через `curl`
и `nc` — правильные и нет, — задаёт вопросы по тому, что видит на экране, и может попросить
сломать одну строку из шага 7 и до запуска сказать, что увидит клиент.

На следующей лабораторной вы соберёте этот же сервис на ASP.NET Core и сравните его ответы с
этими.
