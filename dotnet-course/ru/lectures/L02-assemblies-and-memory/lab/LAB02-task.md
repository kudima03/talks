# Лабораторная 2. Сборка изнутри: декомпиляция, NuGet и модели поставки

**К лекции:** [Л2. Сборки, модели поставки и память](../L02-assemblies-and-memory.md)
**Условие:** всё делается **только из терминала**, как и в прошлый раз — включая декомпиляцию:
используется её консольная версия, `ilspycmd`. Текстовый редактор для файлов — любой.
**Сдаётся вживую:** отчёта нет. Вы садитесь за терминал со своим проектом, показываете
результат и отвечаете на вопросы по любому шагу.

## Что нужно поставить заранее

**`ilspycmd`** — консольный декомпилятор, ставится так же, как всё остальное в этом курсе,
глобальным инструментом:

```sh
dotnet tool install -g ilspycmd
```

**Нативный набор инструментов** — понадобится на последнем режиме публикации, NativeAOT.
Требования свои на каждой ОС и меняются от версии к версии, поэтому единственный надёжный
источник — страница NativeAOT в документации .NET:

<https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/>

Найдите там раздел про свою платформу и поставьте всё нужное **заранее**. На Linux это обычно
компилятор `clang` и заголовки `zlib`:

```sh
sudo apt install clang zlib1g-dev
```

На Windows нужна рабочая нагрузка «Разработка классических приложений на C++» из установщика
Visual Studio. На macOS одних Xcode Command Line Tools может не хватить: линковщику нужны
нативные библиотеки, которых в системе уже нет, и их ставят отдельно — разберитесь по ссылке
выше до занятия, а не на приёмке.

## Что должно быть готово

- Проект `HelloWorld` из первой лабораторной (или его копия) с уже подключённым пакетом.
- Второй пакет, `Pure.Primitives`, подключённый специально для этой лабораторной — ради его
  транзитивных зависимостей.
- Пять публикаций одного и того же проекта — по одной на каждый режим из лекции — рядом, в
  разных папках, и хотя бы одна из них запущена.
- `.gitignore`, в котором ни одна из пяти папок публикации не коммитится.

## Шаги

Под каждым шагом — **«Вопрос»**: то, что вы должны уметь объяснить на приёмке. Вопросы
с пометкой **«усложнённый»** — со звёздочкой: их задают тем, у кого основной ответ уже есть.

### 1. Прочитать сборку изнутри рефлексией

Добавьте в `Program.cs` код из лекции и запустите:

```csharp
using System.Reflection;

Assembly assembly = typeof(Console).Assembly;
Console.WriteLine(assembly.FullName);

foreach (Type type in assembly.GetExportedTypes().Take(5))
{
    Console.WriteLine(type.FullName);
}
```

Замените `typeof(Console).Assembly` на `typeof(Program).Assembly` и посмотрите, как изменится
вывод.

**Вопрос:** назовите все четыре части полного имени сборки из вывода и что означает каждая.
Почему у вашей собственной сборки токен ключа, скорее всего, пустой?

**Вопрос (усложнённый):** компилятор, когда вы ссылаетесь на библиотеку, читает из неё
метаданные, а не IL. Что именно из увиденного в выводе он не смог бы узнать, если бы в сборке
остался только IL без метаданных?

### 2. Декомпилировать свою сборку

```sh
dotnet build -c Release
ilspycmd bin/Release/net10.0/HelloWorld.dll
```

**Вопрос:** найдите в выводе класс и метод `Main`, которых нет в вашем `Program.cs`. Откуда они
взялись?

### 3. Подключить второй пакет и декомпилировать чужую сборку

Подключите **`Pure.Primitives`** — версия указана точная, чтобы у всех на приёмке совпадали и
пути, и номера:

```sh
dotnet add package Pure.Primitives --version 3.6.5
```

Допишите в `Program.cs` вызов — пакет должен реально использоваться, а не просто числиться в
`csproj`. На шаге 7 это окажется важно:

```csharp
using Pure.Primitives.Abstractions.Number;
using Pure.Primitives.Number;

INumber<int> answer = new Int(42);
Console.WriteLine(answer.NumberValue);
```

Пакет скачался в кэш. Найдите там его dll и декомпилируйте тем же способом, что и свою. Имя
папки в кэше — всегда в нижнем регистре:

```sh
ilspycmd ~/.nuget/packages/pure.primitives/3.6.5/lib/net10.0/Pure.Primitives.dll | less
```

Не считайте, что имя dll всегда совпадает с именем пакета: здесь совпадает, но, например, у
`Humanizer.Core` внутри лежит `Humanizer.dll`. Если сомневаетесь — сначала `ls` по папке пакета,
потом путь.

Найдите приватное поле и `internal`-тип — то, чего не видно ни в публичной документации пакета,
ни в автодополнении IDE.

**Вопрос:** какая связь между тем, что вы сейчас видите, и модификаторами доступа вроде
`private`?

**Вопрос (усложнённый):** что из увиденного восстановлено дословно, а что — со сгенерированными
именами, и почему именно так.

### 4. Посмотреть на граф зависимостей

`Pure.Primitives` вы уже подключили на шаге 3 — теперь посмотрите, что приехало вместе с ним:

```sh
dotnet list package --include-transitive
```

**Вопрос:** сколько строк в выводе — прямые зависимости, а сколько — транзитивные?

Обратите внимание: `dotnet list package` печатает транзитивные пакеты **плоским списком**, без
всякого указания на то, кто их притащил. Чтобы восстановить связь, есть отдельная команда —
спросите её про любой транзитивный пакет из вашего списка:

```sh
dotnet nuget why . ByteAether.Ulid
```

**Вопрос:** назовите для каждого транзитивного пакета, через какой прямой пакет он приехал, и
покажите, чем вы это выяснили.

### 5. Прочитать и изменить версию пакета

Откройте `HelloWorld.csproj`, найдите строку `PackageReference` для `Pure.Primitives` и
заключите версию в квадратные скобки:

```xml
<PackageReference Include="Pure.Primitives" Version="[3.6.5]" />
```

Выполните `dotnet restore` и убедитесь, что ничего не сломалось.

**Вопрос:** что означает голая версия без скобок в `PackageReference`, в отличие от версии в
квадратных скобках?

**Вопрос (усложнённый):** в `dotnet list package` две колонки — `Requested` и `Resolved`.
Почему их две и когда они расходятся?

Верните версию к рабочей.

### 6. Опубликовать во всех пяти режимах

Определите свой RID:

```sh
dotnet --info
```

и выполните все пять публикаций по очереди, каждую в свою папку:

```sh
dotnet publish -c Release -o framework-dependent-folder
dotnet publish -c Release -r <ваш RID> --self-contained -o self-contained-folder
dotnet publish -c Release -r <ваш RID> -p:PublishReadyToRun=true -o ready-to-run-folder
dotnet publish -c Release -r <ваш RID> --self-contained -p:PublishTrimmed=true -o trimmed-folder
dotnet publish -c Release -r <ваш RID> -p:PublishAot=true -o aot-folder
```

Посмотрите на содержимое каждой папки и на суммарный размер:

```sh
ls framework-dependent-folder self-contained-folder ready-to-run-folder \
   trimmed-folder aot-folder
du -sh framework-dependent-folder self-contained-folder ready-to-run-folder \
      trimmed-folder aot-folder
```

Запустите результат из каждой папки.

**Вопрос:** для каждой из пяти папок — что в ней лежит и почему. Где нужен установленный на
машине .NET, а где нет. Почему у `framework-dependent-folder` и `self-contained-folder` один и
тот же набор ролей файлов, но разный размер. Почему у `aot-folder` нет dll.

**Вопрос (усложнённый):** `ready-to-run-folder` крупнее, чем `framework-dependent-folder`, хотя
обе публикации зависят от установленного рантайма. Что именно занимает разницу и что это даёт
при старте?

### 7. Сломать рефлексией то, что работало

Добавьте в `Program.cs` поиск типа по строке. Тип берётся из `ByteAether.Ulid` — одной из
транзитивных зависимостей `Pure.Primitives`, которую вы видели на шаге 4. Нигде в вашем коде
этот тип не упоминается, и имя его **собирается в рантайме**, а не лежит готовой константой:

```csharp
string ns = "ByteAether.Ulid";
string typeName = $"{ns}.Ulid, {ns}";

Type? found = Type.GetType(typeName);
Console.WriteLine(found is null ? "тип не найден" : $"нашёл: {found.FullName}");
```

Соберите обычной сборкой (`dotnet build`) и запустите — тип находится, и никаких
предупреждений нет. Теперь опубликуйте заново в режим `trimmed-folder`: в выводе появится
предупреждение `IL2057` на вашу новую строку. Запустите результат из `trimmed-folder` и сравните
сами папки:

```sh
ls framework-dependent-folder | grep -iE 'Ulid|Pure'
ls trimmed-folder             | grep -iE 'Ulid|Pure'
```

Две детали, без которых не получится. Первая: тип обязательно **чужой**. Свой `Program`
так сломать нельзя — сборка, с которой приложение стартует, попадает в корни обрезки целиком, и
её типы остаются на месте. Вторая: имя типа обязательно **собрано в рантайме**. Если написать
его одной строковой константой, обрезка эту константу прочитает и специально сохранит именно
этот тип — приложение продолжит работать, и ломать будет нечего.

**Вопрос:** что вывела программа в обычной сборке и что — в обрезанной? Что показало сравнение
двух папок и как оно объясняет вывод? Почему анализатор обрезки не мог заранее понять, какой
тип вы имели в виду?

**Вопрос (усложнённый):** проверьте вторую деталь руками — добавьте рядом второй поиск, где имя
типа записано готовой константой, и опубликуйте `trimmed-folder` заново. Почему этот тип обрезку
пережил, а собранный в рантайме — нет? Что это говорит о границе возможностей статического
анализа?

**Вопрос (усложнённый):** предупреждений на самом деле два и они разные — `IL2026` появилось
ещё на шаге 6, `IL2057` только сейчас. Прочитайте текст каждого, найдите строку, на которую оно
показывает, и объясните, чем эти две претензии отличаются. Что из увиденного на шагах 6 и 7
сломалось бы точно так же в NativeAOT, и почему там это ещё жёстче?

## Дополнительное задание (по желанию)

Соберите из своего кода не приложение, а пакет, и подключите его к самому себе как к обычной
зависимости:

`<ProjectReference>`?

## Как проходит приёмка

Вы за своим терминалом, все пять публикаций уже собраны. Принимающий просит показать несколько
шагов и задаёт вопросы по тому, что видит на экране. NativeAOT собирается за секунды, поэтому
любую из пяти публикаций, включая её, на приёмке могут попросить пересобрать при вас.
