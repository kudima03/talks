# Лабораторная 2. Сборка изнутри: декомпиляция, NuGet и модели поставки

**К лекции:** [Л2. Сборки, модели поставки и память](../L02-assemblies-and-memory.md)
**Условие:** всё делается **только из терминала**, как и в прошлый раз — включая декомпиляцию:
используется её консольная версия, `ilspycmd`, а не приложение с окнами. Текстовый редактор для
файлов — любой.
**Сдаётся вживую:** отчёта нет. Вы садитесь за терминал со своим проектом, показываете
результат и отвечаете на вопросы по любому шагу.

## Что нужно поставить заранее

**`ilspycmd`** — консольный декомпилятор, ставится так же, как всё остальное в этом курсе,
глобальным инструментом:

```sh
dotnet tool install -g ilspycmd
```

**Нативный набор инструментов** — понадобится на последнем режиме публикации, NativeAOT. На
Linux это компилятор `clang` и заголовки `zlib`:

```sh
sudo apt install clang zlib1g-dev
```

На Windows и macOS ставится вместе с компонентами Visual Studio или Xcode Command Line Tools —
если вы не на Linux, найдите свой вариант на странице требований NativeAOT в документации .NET
заранее, не в день приёмки.

## Что должно быть готово

- Проект `HelloWorld` из первой лабораторной (или его копия) с уже подключённым пакетом.
- Второй пакет, подключённый специально для этой лабораторной так, чтобы у проекта появились
  транзитивные зависимости.
- Собственная сборка и одна из зависимостей, декомпилированные `ilspycmd`.
- Пять публикаций одного и того же проекта — по одной на каждый режим из лекции — рядом, в
  разных папках, и хотя бы одна из них запущена.
- `.gitignore`, в котором ни одна из пяти папок публикации не коммитится.

## Шаги

Под каждым шагом — **«Вопрос»**: то, что вы должны уметь объяснить на приёмке. Вопросы
с пометкой **«усложнённый»** — со звёздочкой: их задают тем, у кого основной ответ уже есть.

### 1. Прочитать сборку изнутри рефлексией

Добавьте в `Program.cs` код из лекции и запустите:

```csharp
var assembly = typeof(Console).Assembly;
Console.WriteLine(assembly.FullName);

foreach (var type in assembly.GetExportedTypes().Take(5))
{
    Console.WriteLine(type.FullName);
}
```

Замените `typeof(Console).Assembly` на `typeof(Program).Assembly` и посмотрите, как изменится
вывод.

**Вопрос:** назовите все четыре части полного имени сборки из вывода и что означает каждая.
Почему у вашей собственной сборки токен ключа, скорее всего, пустой?

**Вопрос (усложнённый):** компилятор, когда вы ссылаетесь на библиотеку, читает из неё
метаданные, а не IL. Что именно из увиденного в выводе он не смог бы узнать, если бы в сборке
остался только IL без метаданных?

### 2. Декомпилировать свою сборку

```sh
dotnet build -c Release
ilspycmd bin/Release/net10.0/HelloWorld.dll
```

**Вопрос:** найдите в выводе класс и метод `Main`, которых нет в вашем `Program.cs`. Откуда они
взялись?

### 3. Декомпилировать чужую сборку

Найдите в кэше пакетов (`~/.nuget/packages`) dll подключённого вами пакета и декомпилируйте её
тем же способом:

```sh
ilspycmd ~/.nuget/packages/<пакет>/<версия>/lib/net10.0/<Пакет>.dll | less
```

Найдите приватный метод или приватное поле — то, чего не видно в публичной документации пакета.

**Вопрос:** какая связь между тем, что вы сейчас видите, и модификаторами доступа вроде
`private`? Почему декомпилятор их не уважает?

**Вопрос (усложнённый):** что из увиденного восстановлено дословно, а что — со сгенерированными
именами, и почему именно так.

### 4. Подключить второй пакет и посмотреть на граф зависимостей

Подключите ещё один пакет — любой, лишь бы он тянул за собой собственные зависимости (почти
любой не самый маленький пакет годится):

```sh
dotnet add package <пакет>
dotnet list package --include-transitive
```

**Вопрос:** сколько строк в выводе — прямые зависимости, а сколько — транзитивные? Для каждой
транзитивной назовите, через какой прямой пакет она пришла.

### 5. Прочитать и изменить версию пакета

Откройте `HelloWorld.csproj`, найдите строку `PackageReference` одного из пакетов и замените
версию на точную, в квадратных скобках:

```xml
<PackageReference Include="..." Version="[X.Y.Z]" />
```

Выполните `dotnet restore` и убедитесь, что ничего не сломалось. Теперь укажите версию заведомо
ниже той, которую требует граф зависимостей (например, на одну минорную меньше), и снова
сделайте restore.

**Вопрос:** что означает голая версия без скобок в `PackageReference`, в отличие от версии в
квадратных скобках? Что вывел restore, когда вы попросили версию ниже нужной, и почему это
предупреждение, а не ошибка?

Верните версию к рабочей.

### 6. Опубликовать во всех пяти режимах

Определите свой RID:

```sh
dotnet --info
```

и выполните все пять публикаций по очереди, каждую в свою папку:

```sh
dotnet publish -c Release -o out-fd
dotnet publish -c Release -r <ваш RID> --self-contained -o out-sc
dotnet publish -c Release -r <ваш RID> -p:PublishReadyToRun=true -o out-r2r
dotnet publish -c Release -r <ваш RID> --self-contained -p:PublishTrimmed=true -o out-trim
dotnet publish -c Release -r <ваш RID> -p:PublishAot=true -o out-aot
```

Посмотрите на содержимое каждой папки и на суммарный размер:

```sh
ls out-fd out-sc out-r2r out-trim out-aot
du -sh out-fd out-sc out-r2r out-trim out-aot
```

Запустите результат из каждой папки.

**Вопрос:** для каждой из пяти папок — что в ней лежит и почему. Где нужен установленный на
машине .NET, а где нет. Почему у `out-fd` и `out-sc` один и тот же набор ролей файлов, но разный
размер. Почему у `out-aot` нет dll.

**Вопрос (усложнённый):** `out-r2r` крупнее, чем `out-fd`, хотя оба framework-dependent. Что
именно занимает разницу и что это даёт при старте?

### 7. Сломать рефлексией то, что работало

Добавьте в `Program.cs` код, который ищет тип по строке:

```csharp
var typeName = "HelloWorld.Program";
var type = Type.GetType(typeName);
Console.WriteLine(type is null ? "тип не найден" : $"нашёл: {type.FullName}");
```

Соберите обычной сборкой (`dotnet build`) — предупредит ли компилятор о чём-то? Опубликуйте
заново в режим `out-trim` и запустите результат оттуда.

**Вопрос:** сработал ли поиск типа в обрезанной публикации? Почему анализатор обрезки не мог
заранее понять, какой тип вы имели в виду? Что из увиденного на шагах 6 и 7 сломалось бы точно
так же в NativeAOT, и почему там это ещё жёстче?

### 8. Убрать производное из репозитория

```sh
git status
```

**Вопрос:** какие из пяти новых папок публикации git уже видит как чужие, а какие пришлось
дописывать в `.gitignore` руками, и почему разница здесь та же, что была с `out` в прошлый раз.

### 9. Собрать картинку

Главный вопрос приёмки: **чем один и тот же исходный код обернулся в каждой из пяти публикаций,
и какую цену вы платите за каждый вариант.** Пройдите по всем пяти по порядку, своими словами,
глядя на свои же папки.

## Дополнительное задание (по желанию)

Соберите из своего кода не приложение, а пакет, и подключите его к самому себе как к обычной
зависимости:

```sh
dotnet pack -c Release
dotnet nuget add source ./bin/Release --name local
dotnet add package <ваш PackageId> --source local
```

**Вопрос:** что оказалось внутри `.nupkg`, если открыть его архиватором? Чем то, что вы сейчас
подключили командой `add package`, отличается от подключения на тот же код через
`<ProjectReference>`?

## Как проходит приёмка

Вы за своим терминалом, все пять публикаций уже собраны. Принимающий просит показать несколько
шагов и задаёт вопросы по тому, что видит на экране. Прогоните шаги у себя хотя бы раз заранее —
NativeAOT собирается не быстро, и на приёмке не будет времени ждать первую сборку.
