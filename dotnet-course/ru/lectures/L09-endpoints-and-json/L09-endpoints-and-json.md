## 1. Два способа описать эндпоинт (18)

В прошлый раз мы разобрали конвейер и остановились на его конце: на компоненте, который вызывает обработчик. Сегодня про обработчик. Как его описать, как запрос превращается в его параметры, как его результат превращается в JSON, и как рассказать о нём тем, кто будет его вызывать. Это лекция про контракт: про ту поверхность сервиса, которую видят снаружи, и которую нельзя менять как попало.

[ВОПРОС В ЗАЛ]

Начнём с вопроса. В прошлой лекции обработчик был лямбдой: путь и функция, одна строка. А кто из вас видел код с классами, у которых атрибуты над методами, слово Controller в имени и наследование от базового класса? Много. Это второй способ, и он старше. Сегодня оба, и я скажу, какой берём мы и почему.

[СЛАЙД: листинг минимального API целиком; выделить группу, ограничение в маршруте, зависимость в параметрах и типизированный результат]

```csharp
var orders = app.MapGroup("/orders");

orders.MapGet("/{id:int}", async Task<Results<Ok<OrderDto>, NotFound>> (
    int id, IOrderService service, CancellationToken ct) =>
{
    var order = await service.FindAsync(id, ct);
    return order is null ? TypedResults.NotFound() : TypedResults.Ok(order);
});

orders.MapPost("/", async Task<Created<OrderDto>> (
    CreateOrderDto dto, IOrderService service, CancellationToken ct) =>
{
    var created = await service.CreateAsync(dto, ct);
    return TypedResults.Created($"/orders/{created.Id}", created);
});
```

Способ первый: минимальный API. Эндпоинт это делегат. Путь, метод HTTP, функция. Всё, что нужно знать об обработчике, видно в одном месте: откуда берётся идентификатор, какие зависимости нужны, что возвращается, с каким статусом. Никакого класса, никаких атрибутов, никакого наследования.

Минимальные API появились в платформе несколько версий назад, под влиянием микрофреймворков из других языков, где сервис на десять маршрутов умещался в один файл. Поначалу это был упрощённый вариант с ограничениями, и часть людей до сих пор так о нём думает. Сегодня это полноценный способ: группы, фильтры, авторизация, привязка форм, документация, всё есть, и новые возможности фреймворка появляются здесь первыми.

Разберём, что здесь происходит, потому что в этих строках половина сегодняшней лекции.

Группа. Все маршруты заказов начинаются с одного префикса, и он написан один раз. К группе можно прицепить общие вещи: авторизацию, фильтры, о которых будет в третьем разделе, и они применятся ко всем маршрутам внутри.

Группы вкладываются: общая группа с префиксом для всего API и номером версии, о котором пятый раздел, и внутри неё группы по ресурсам. Всё, что прицеплено к внешней, наследуется внутренними. Так одна строка с требованием авторизации на внешней группе закрывает весь API, а исключения делаются на конкретных маршрутах.

Шаблон маршрута с ограничением. Фигурные скобки, имя параметра, двоеточие, тип. Запрос с нечисловым идентификатором до обработчика не дойдёт: маршрут просто не совпадёт. Об этом второй раздел.

Параметры функции. Целое число с тем же именем, что в маршруте, и фреймворк подставит его из пути. Интерфейс сервиса, и фреймворк подставит его из контейнера зависимостей, о котором следующая лекция. Токен отмены, и фреймворк подставит тот самый RequestAborted из прошлой лекции. Три параметра, три разных источника, и ни одного атрибута: фреймворк понял по типу и имени. Во втором обработчике первый параметр это объект, и объект берётся из тела запроса, разобранного как JSON. Четвёртый источник, и тоже без атрибута.

Возвращаемый тип. Не просто объект, а объединение возможных результатов: либо двести с заказом, либо четыреста четыре. Это записано в сигнатуре, и это читает не только человек, но и генератор документации из пятого раздела: он узнает, что этот эндпоинт может вернуть два разных статуса, из типа, а не из комментария. TypedResults это готовые ответы с правильным статусом, и их имена совпадают со статусами из седьмой лекции: Ok, NotFound, Created с адресом созданного ресурса в заголовке Location.

Если обработчик возвращает не результат, а просто объект, фреймворк сделает из него двести с JSON. Строку отдаст как текст. Ничего, то есть Task без значения, превратит в двести с пустым телом. Это удобно для простых случаев, но по сигнатуре опять не видно статусов, поэтому для настоящего контракта возвращайте результаты явно.

Есть два семейства этих готовых ответов, и разница в них важна. Одно возвращает общий интерфейс результата: работает, но по сигнатуре обработчика нельзя понять, что именно он возвращает. Другое, с приставкой Typed, возвращает конкретные типы, и именно они складываются в объединение из сигнатуры. Берите второе всегда: разница в одном слове, а выигрыш в том, что документ и компилятор знают о ваших статусах.

[ПАУЗА]

[СЛАЙД: листинг контроллера целиком; подписи: «атрибут маршрута на классе», «атрибут метода», «базовый класс», «зависимость через конструктор»]

```csharp
[ApiController]
[Route("orders")]
public sealed class OrdersController(IOrderService service) : ControllerBase
{
    [HttpGet("{id:int}")]
    public async Task<ActionResult<OrderDto>> Get(int id, CancellationToken ct)
    {
        var order = await service.FindAsync(id, ct);
        return order is null ? NotFound() : Ok(order);
    }

    [HttpPost]
    public async Task<ActionResult<OrderDto>> Create(CreateOrderDto dto, CancellationToken ct)
    {
        var created = await service.CreateAsync(dto, ct);
        return CreatedAtAction(nameof(Get), new { id = created.Id }, created);
    }
}
```

Способ второй: контроллеры. То же самое поведение, другая форма. Класс, наследующий базовый, с атрибутом маршрута сверху. Методы с атрибутами, которые говорят, какой метод HTTP и какой хвост пути. Зависимость через конструктор, одна на весь класс. Результаты через методы базового класса: NotFound, Ok, Created. И атрибут над классом, который включает набор соглашений: автоматический ответ четыреста при невалидной модели, вывод источника параметров по типу, и ещё несколько.

Слово «соглашения» здесь ключевое. Контроллеры построены на них: класс с именем, оканчивающимся на Controller, считается контроллером. Публичный метод в нём считается обработчиком. Сложный тип в параметре считается телом. Всё это правила, которые надо знать, и которые не видны в коде: они где-то в документации. Атрибуты уточняют соглашения там, где они не подходят.

Ещё два соглашения, которые вы увидите в чужих контроллерах. Возвращаемый тип ActionResult с параметром умеет неявно принимать и объект, и результат вроде NotFound, поэтому в методе можно вернуть просто заказ, и он станет двухсотым. Удобно, но по сигнатуре нельзя понять, какие статусы возможны: любые. И экземпляр контроллера создаётся на каждый запрос, поэтому поле в нём это состояние одного запроса, а не что-то общее, о чём иногда забывают и удивляются, что счётчик в поле всегда ноль.

[ВОПРОС В ЗАЛ]

А теперь вопрос, ради которого этот раздел. Мы написали класс. Мы нигде не вызвали его конструктор, нигде не зарегистрировали его маршруты, нигде не сказали фреймворку «вот контроллер». Строка регистрации контроллеров в файле запуска одна, и в ней нет имён. Откуда фреймворк узнал, что этот класс существует и что у него есть метод на GET с таким путём? Кто скажет «по имени»? Ближе. Кто скажет «рефлексия»? Да.

[СЛАЙД: схема: сборка → метаданные (Л2) → сканирование типов → фильтр «наследует ControllerBase или имя на Controller» → чтение атрибутов → таблица маршрутов; внизу: «при старте, один раз, через рефлексию»]

Вспомните вторую лекцию: сборка описывает себя сама, метаданные знают о каждом типе и каждом методе. При старте фреймворк берёт сборку приложения и проходит по всем типам. Для каждого проверяет: наследует ли базовый класс, или имя кончается на Controller. Для каждого подходящего проходит по публичным методам и читает атрибуты: маршрут, метод HTTP, источники параметров. Из этого строится таблица маршрутов. Красиво: вы написали класс, и он работает, ничего не регистрируя.

И это же цена. Всё это рефлексия, та самая динамика, которую мы во второй лекции назвали тем, что ломается под обрезкой и AOT. Анализатор не видит, что этот класс кто-то использует: на него никто не ссылается, его находят по имени во время выполнения. Обрезка его выкинет. AOT не сможет сгенерировать для него код, потому что не знает, что он понадобится. Дальше активация: на каждый запрос контроллер создаётся заново через контейнер, и способ его создания тоже опирается на метаданные. За удобство «просто напиши класс» мы платим рефлексией при старте и на каждом запросе, и вот где приходит счёт: контроллеры несовместимы с AOT из второй лекции, и фреймворк об этом говорит прямо.

Про цену на каждом запросе добавлю честности. Фреймворк не вызывает метод контроллера рефлексией каждый раз, он строит делегаты один раз и кэширует. Но вокруг вызова есть свой конвейер фильтров, создание экземпляра через контейнер, привязка модели через общий механизм с проверкой всех источников. Это накладные расходы, измеримые в бенчмарках, о которых пятнадцатая лекция, и минимальный API в тех же бенчмарках заметно легче. Для обычного сервиса разница не решает, база дороже. Но она есть, и она в ту же сторону, что и вопрос про AOT.

Минимальный API дружелюбнее. Обработчик это делегат, на который есть прямая ссылка из кода: компилятор её видит, анализатор её видит. Для параметров и результатов есть генератор кода, который на этапе компиляции пишет то, что иначе делала бы рефлексия: разбор параметров, вызов, сериализацию. Помните из второй и седьмой лекций: перенести динамику из рантайма в компилятор. Вот это оно, и включается оно вместе с AOT в файле проекта.

У генератора есть условие, которое стоит знать: обработчик должен быть виден статически. Лямбда прямо в вызове Map, или ссылка на метод по имени, это видно. Делегат, положенный в переменную и передаваемый в цикле, уже нет: генератор не понимает, что за ним, и такой маршрут откатится на рефлексию, а под AOT не заработает. Правило простое: маршрут регистрируется явно, с обработчиком на месте, и это же делает код читаемым.

[ПАУЗА]

Что берём мы. Минимальный API, и три причины.

Первая: всё в одном месте. Путь, параметры, зависимости, результат, всё в одной сигнатуре, и читается сверху вниз без знания соглашений. Новый человек в проекте понимает обработчик, не читая документацию о том, что считается телом.

И он видит, что обработчик асинхронный: Task в сигнатуре, await внутри, токен в параметрах. Всё из шестой лекции здесь обязательно: обработчик выполняется на потоке из пула, и синхронное ожидание в нём это то самое голодание под нагрузкой. Обработчик, который что-то запускает и не ждёт, теряет исключения, как мы разбирали. Сигнатура с Task это не украшение, это договор с сервером.

Вторая: честность типов. Возвращаемый тип говорит, какие статусы возможны, и это проверяет компилятор и читает генератор документации. У контроллера ActionResult говорит «что угодно», и документация узнаёт о статусах из атрибутов, которые легко забыть.

Третья: AOT и обрезка, о которых мы говорили. Даже если вы не собираетесь их использовать, код, который дружит со статическим анализом, это код, в котором меньше магии.

Когда контроллеры. Если у вас уже есть проект на них, переписывать не нужно, они не устарели и поддерживаются. Если вам нужны их специфические механизмы: сложные фильтры на уровне класса, привязка форм со сложной вложенностью, вещи из старых библиотек, которые ждут контроллер. И если команда их знает, а минимальный API нет, это тоже аргумент. Но для нового сервиса, который мы строим, выбор сделан.

И одно наблюдение из опыта, которое тоже аргумент. Контроллер имеет свойство расти: раз это класс, в него удобно добавить ещё метод, потом ещё, потом приватный вспомогательный, потом поле. Я видел контроллеры на две тысячи строк, в которых бизнес-логика жила прямо в методах-обработчиках, потому что «так ближе». Минимальный API этому сопротивляется: обработчик это функция, и когда она выросла до тридцати строк, это видно, и логика уезжает в сервис, где ей место. Форма подсказывает архитектуру.

Практически обработчики оформляют статическими методами в классе по ресурсу, а в регистрации маршрута стоит ссылка на метод по имени, та самая группа методов из четвёртой лекции. Тогда обработчик это обычный метод, который можно вызвать из теста напрямую, с подставленными параметрами, без сервера. Лямбды прямо в регистрации остаются для однострочных вещей. И генератор для AOT, о котором я говорил, ссылку на метод видит так же хорошо, как лямбду.

И одно замечание про размер. В минимальном API все обработчики можно написать в файле запуска, и на второй лабораторной так и будет. На двадцатом обработчике файл станет нечитаемым. Тогда обработчики группируют по ресурсу в отдельные файлы, каждый файл это статический класс с методом расширения из пятой лекции, который регистрирует маршруты своей группы, и файл запуска снова читается как список: «зарегистрировать заказы, зарегистрировать пользователей». Та же дисциплина, что для регистрации сервисов в прошлой лекции.

К маршрутам и группам можно добавлять метаданные цепочкой методов: имя маршрута, чтобы ссылаться на него из кода при формировании адресов; теги, чтобы документ группировал их; описания возможных ответов, если тип не выражает их сам; и требование авторизации, о котором одиннадцатая лекция, одним вызовом на всю группу. Всё это читается сверху вниз рядом с маршрутом, и всё это попадает в документ из пятого раздела.

Мысль раздела на ребро. Обработчик это делегат, и минимальный API показывает его целиком в одной сигнатуре. Контроллеры дают то же самое через соглашения и рефлексию, и за рефлексию приходит счёт при обрезке и AOT.

## 2. От запроса к типам .NET (18)

[СЛАЙД: заголовок раздела и схема: сырой запрос из Л7 → маршрутизация → привязка → параметры обработчика с типами]

Теперь путь от сырого запроса из седьмой лекции до параметров вашего метода. Три шага: найти обработчик, достать данные из запроса, превратить строки в типы. И на каждом шаге есть место, где это ломается.

Шаг первый: маршрутизация. Компонент из прошлой лекции, который смотрит на метод и путь и выбирает обработчик. Он работает с шаблонами.

[СЛАЙД: шаблоны маршрутов в таблице: /orders — литерал; /orders/{id} — параметр; /orders/{id:int} — с ограничением; /orders/{id:int:min(1)} — два ограничения; /files/{*path} — остаток пути; /orders/{page=1} — со значением по умолчанию]

Шаблон это путь, в котором части в фигурных скобках это параметры. Литеральная часть должна совпасть буквально. Параметр совпадает с любым сегментом и запоминает его значение под именем. Ограничение после двоеточия сужает: только целое, только буквы, не меньше единицы, длина не больше десяти. Есть параметр для остатка пути со звёздочкой, он забирает всё до конца, включая косые черты, для файловых путей. Есть значение по умолчанию, если сегмент отсутствует.

Ограничения это не валидация. Это выбор маршрута. Запрос на заказы с идентификатором «abc» не попадёт в обработчик с ограничением int, он получит четыреста четыре, потому что маршрута для него нет. Это правильно: нечисловой идентификатор заказа это не «плохие данные для этого обработчика», это «такого адреса не существует». Валидация, о которой третий раздел, начинается там, где маршрут совпал.

Ограничения можно писать и свои, для повторяющихся форматов вроде артикула или кода региона: класс, который проверяет сегмент, и регистрация под именем. Но не увлекайтесь: ограничение отвечает на вопрос «существует ли такой адрес», а не «правильные ли данные», и для второго есть валидация. И договоритесь в команде: нечисловой идентификатор это четыреста четыре, как у нас, или четыреста, как предпочитают некоторые. Оба варианта встречаются, важно, чтобы был один.

Приоритеты. Два шаблона могут подходить одному пути: «orders, latest» и «orders, идентификатор». Фреймворк выбирает более конкретный: литерал важнее параметра, параметр с ограничением важнее параметра без. Поэтому «latest» уйдёт в первый, а число во второй, независимо от порядка регистрации. Если два шаблона равны по конкретности и оба подходят, это ошибка, и фреймворк бросит исключение о неоднозначности при запросе. Не при старте, при запросе, и это одна из вещей, которые ловит тест из пятнадцатой лекции, а не компилятор.

Две мелочи про совпадение. Маршруты не чувствительны к регистру: путь с большими буквами совпадёт с шаблоном в маленьких. И косая черта в конце пути не имеет значения: с ней и без неё это один маршрут. Клиенты присылают и так, и так, и вам не нужно об этом думать. А вот параметры строки запроса чувствительны к регистру имён по умолчанию, и «Page» это не «page».

Ещё две вещи, которые маршрутизация делает сама. Если путь совпал, а метод HTTP нет, например POST на маршрут, где есть только GET, клиент получит четыреста пять, метод не разрешён, с заголовком, перечисляющим разрешённые. Вам это писать не нужно. И на запрос HEAD она ответит тем же обработчиком, что на GET, но без тела, как требует протокол из седьмой лекции.

[ПАУЗА]

Шаг второй: привязка. Откуда берётся каждый параметр обработчика.

[СЛАЙД: листинг целиком; подписи у параметров: «из пути», «из строки запроса», «из заголовка», «из тела», «из контейнера», «из контекста»]

```csharp
app.MapGet("/orders/{id:int}/items", (
    int id,                                        // из пути
    IOrderService service,                         // из контейнера зависимостей
    CancellationToken ct,                          // из контекста запроса
    int page = 1,                                  // из строки запроса, необязательный
    [FromQuery(Name = "size")] int pageSize = 20,  // из строки запроса под другим именем
    [FromHeader(Name = "X-Request-Id")] string? requestId = null)
    => service.GetItemsAsync(id, page, pageSize, ct));

app.MapPost("/orders", (CreateOrderDto dto, IOrderService service, CancellationToken ct)
    => service.CreateAsync(dto, ct));         // dto — из тела как JSON
```

Пять источников. Путь: параметр с именем, совпадающим с именем в шаблоне. Строка запроса: простые типы, не найденные в пути, ищутся там по имени, и значение по умолчанию делает их необязательными. Заголовок: только с атрибутом, потому что по имени заголовок не угадать. Тело: сложный тип без атрибута считается JSON-телом, и это единственный сложный тип, который так можно взять, второй такой параметр это ошибка. Форма: с атрибутом, для данных из HTML-формы и для файлов. И два служебных: сервисы из контейнера по типу и служебные объекты из контекста, токен, сам контекст, пользователь.

Тело читается как JSON только если клиент прислал заголовок с типом содержимого из седьмой лекции. Без него или с другим типом обработчик не вызывается, клиент получает четыреста пятнадцать, неподдерживаемый тип содержимого. Это правильно и это первый вопрос, когда «тело приходит пустым»: посмотрите на Content-Type запроса. Утилиты командной строки его ставят не всегда.

Заметьте, что источник определяется в основном по типу и имени, а атрибут нужен только там, где угадать нельзя или где имя в запросе отличается от имени параметра. Это удобно и это же место, где ошибаются: сложный тип нечаянно стал телом, а вы хотели его из строки запроса. Для этого случая есть атрибут, который говорит «собери этот объект из параметров запроса по свойствам», и он же помогает, когда параметров становится десять: вместо десяти параметров функции один объект.

Два случая, которые встретятся сразу. Несколько значений одного параметра: «идентификаторы равно один, идентификаторы равно два» в строке запроса привязываются к массиву или списку по имени. И свои типы в параметрах. Помните record struct для почты из третьей лекции? Если у типа есть статический метод разбора из строки с известной сигнатурой, фреймворк использует его, и параметр обработчика может быть сразу типа Email, а не string. Проверка формата происходит в момент привязки, и в обработчик попадает уже правильный тип. Это тот самый принцип «проверка на границе, один раз», доведённый до параметров маршрута.

Обратите внимание на порядок параметров: сначала обязательные, потом необязательные со значениями по умолчанию, как у любого метода в C#. И на то, что сервис и токен стоят среди обязательных без всяких атрибутов: фреймворк узнаёт их по типу, потому что интерфейс зарегистрирован в контейнере, а токен это служебный тип.

[ПАУЗА]

Шаг третий: превращение строки в тип. Всё, что пришло из пути, строки запроса и заголовков, это строки. Тело это байты. Параметр обработчика это число, дата, перечисление, объект. Кто-то должен превратить одно в другое, и это называется привязкой модели, и вот где это ломается.

[ВОПРОС В ЗАЛ]

Параметр типа decimal, из строки запроса пришло «12,5» с запятой. Что получит обработчик? Кто скажет «двенадцать с половиной»? Кто скажет «ошибка»? Кто скажет «зависит»? Правы последние, и «зависит» здесь худший ответ из возможных, потому что зависит от настроек культуры на машине, где запущен сервис. На вашем ноутбуке с русской локалью запятая это разделитель дробной части. В контейнере с английской это ошибка разбора. Часть источников фреймворк разбирает по фиксированным правилам, независимо от машины, часть по правилам текущей культуры, и это первая ловушка: код, который работал у вас и не работает в проде, потому что у прода другая локаль.

Правило: в контракте API числа с точкой, всегда, и это надо зафиксировать в документации. Всё, что чувствительно к культуре, разбирается явно с указанием инвариантной культуры, а не «как получится».

Для сервиса есть и радикальный способ: одна строка в файле проекта включает режим, в котором приложение вообще не знает о культурах и всё считает инвариантным. Меньше размер, быстрее старт, и никаких сюрпризов с запятыми. Для API, который говорит на языке контракта, а не на языке пользователя, это правильный выбор, и в лабораторной я советую его включить. А чтобы ловить такие ошибки до прода, тесты из пятнадцатой лекции можно запускать с явно выставленной культурой, отличной от вашей.

Вторая ловушка: даты. Строка «03/04/2026» это третье апреля или четвёртое марта? Зависит от того же. Плюс часовой пояс: дата без пояса это дата где? В контракте дата это строка в стандартном формате, год-месяц-день, время через букву T, и пояс явно или всё во всемирном времени. Для дат с поясом есть отдельный тип, и он предпочтительнее обычного, потому что обычный не помнит, откуда он. Для даты без времени и времени без даты тоже есть свои типы, и они поддерживаются сериализатором. Не разбирайте даты из произвольных строк: примите стандартный формат или откажите.

Мелочи того же рода. Идентификаторы в формате GUID разбираются в нескольких вариантах записи, со скобками и без, и это обычно не проблема. Пробелы по краям значений не обрезаются сами, и «имя равно пробел» это не пустое имя. Логические значения принимаются как true и false, а «единица» и «да» нет. Каждая такая мелочь однажды станет вопросом от клиента, и ответ на все один: формат зафиксирован в документе из пятого раздела, и всё, что вне формата, отклоняется.

Третья ловушка: перечисления. Из третьей лекции: перечисление это число под капотом. Из строки запроса придёт либо число, либо имя. Число не проверяется на принадлежность к набору: «статус равно девяносто девять» превратится в значение перечисления, которого нет, и упадёт где-то глубже. Имя чувствительно к регистру или нет в зависимости от настроек. В четвёртом разделе мы это настроим для JSON, а для строки запроса правило одно: проверяйте, что значение определено в перечислении.

Четвёртая ловушка: пустые значения. Параметр есть, но пустой: «page равно» без значения. Параметра нет вовсе. В теле поле равно null. В теле поля нет. Четыре разные ситуации, которые в обработчике часто выглядят одинаково: значение по умолчанию. Если разница важна, а для частичного обновления из седьмой лекции она важна, нужно её различать явно, и в четвёртом разделе я скажу, что сериализатор с этим не помогает.

Для параметров строки запроса разница между «нет» и «пусто» решается типом. Целое со значением по умолчанию: отсутствие даёт умолчание, а пустое значение это ошибка разбора. Целое с вопросом из четвёртой лекции: отсутствие даёт null, и обработчик видит, что параметра не было. Второе честнее, когда отсутствие что-то значит, например «без фильтра по статусу», а не «статус равен нулю».

Общее у четырёх ловушек одно: превращение строки в тип это место, где контракт встречается с реальностью, и здесь либо жёсткие правила формата, либо сюрпризы на другой машине.

[ПАУЗА]

И последнее в разделе, самое важное с точки зрения архитектуры. DTO не равно доменная модель.

[СЛАЙД: две колонки: слева «сущность: то, как данные лежат в базе, с внутренними полями и связями», справа «DTO: то, что видит клиент, ровно нужные поля»; между ними стрелка «преобразование на границе»]

В листингах у нас были OrderDto и CreateOrderDto. Не Order. Это не случайность и не многословие.

Сущность это то, как заказ живёт внутри: со всеми полями, со связями, с тем, что нужно базе данных из четырнадцатой лекции, с внутренними флагами. DTO, объект передачи данных, это то, что видит клиент: ровно те поля, которые ему нужны, в той форме, которая ему удобна. Это два разных типа, и между ними преобразование на границе.

[ВОПРОС В ЗАЛ]

Зачем два типа, если поля почти совпадают? Кто скажет «чтобы не отдавать лишнее»? Да, это первая причина: у сущности есть поля, которые наружу нельзя, себестоимость, внутренние заметки, хэш пароля у пользователя. Отдали сущность целиком, и всё это в JSON у клиента. Но главная причина другая, и она в заметках сформулирована точно: иначе изменение схемы базы становится ломающим изменением API.

Представьте: вы переименовали колонку в базе, и сущность переименовала свойство. Если наружу отдаётся сущность, у клиента поле в JSON переименовалось, и его код сломался. Изменение, которое было внутренним, стало публичным. С DTO вы переименовываете свойство сущности, правите одну строку преобразования, и клиент ничего не замечает. DTO это то, что вы обещали снаружи, сущность это то, как вы это храните внутри, и они меняются с разной скоростью и по разным причинам.

На входе то же самое. CreateOrderDto содержит то, что клиент может задать. Не идентификатор, его назначаете вы. Не статус, его определяет логика. Не дату создания. Если принимать сущность целиком, клиент сможет прислать любое поле, и вы получите заказ со статусом «оплачен», который никто не оплачивал. Это называется избыточной привязкой, и это реальная уязвимость. Входной DTO это белый список того, что снаружи можно.

Отсюда и несколько DTO на один ресурс, и это нормально. Для создания одно, для обновления другое, для списка короткое, для карточки полное. Соблазн сделать один тип на всё, где все поля допускают null, велик, и результат известен: никто не понимает, какое поле когда обязательно, а валидатор из следующего раздела превращается в лестницу условий. Отдельные типы это больше объявлений и меньше неопределённости, и в третьей лекции мы уже решили, что для данных объявление стоит одну строку.

Преобразование между ними это код на границе: в обработчике или в сервисе сразу за ним. Для простых случаев это метод расширения из пятой лекции: сущность, стрелка, DTO. Для сложных есть библиотеки, которые делают это по соглашениям, но помните вторую лекцию про рефлексию: часть из них на ней и построена. Ручное преобразование в десять строк почти всегда честнее.

Форма DTO. Это данные, значит, record из третьей лекции: позиционный, неизменяемый, с равенством по значению, которое пригодится в тестах. Имена по соглашению, которое принято в команде: суффикс Dto, или Request и Response, любое, лишь бы одно. И DTO живут в проекте контракта, отдельно от домена, чтобы граница из третьей лекции была границей сборки: домен не ссылается на DTO, и компилятор это гарантирует. Версия DTO это версия контракта, и об этом пятый раздел.

Мысль раздела на ребро. От запроса до параметров три шага, и каждый может сломаться: маршрут не совпал, источник угадан не тот, строка разобрана по чужой культуре. А наружу уходит контракт, DTO, и никогда сущность.

## 3. Валидация (14)

[СЛАЙД: заголовок раздела и лестница: атрибуты → свои правила → FluentValidation; внизу: «невалидный запрос — исключение, ответ формирует middleware»]

Маршрут совпал, параметры привязаны, типы сошлись. Теперь: а данные-то правильные? Сумма положительная? Почта похожа на почту? Дата доставки не в прошлом? Это валидация, и у неё три ступени по сложности, и одно правило про то, где она живёт.

Зачем вообще проверять на входе, если логика и база всё равно упадут на плохих данных. Потому что цена ошибки растёт с глубиной. Отрицательное количество на границе это одно понятное сообщение клиенту. То же количество, дошедшее до базы, это исключение из драйвера с текстом про ограничение, которое клиенту не сказать, и запись в логе, по которой не понятно, кто виноват. А если ограничения в базе нет, это заказ с отрицательной суммой в отчёте через месяц. Проверка на границе это самый дешёвый момент из всех.

Ступень первая: атрибуты. Над свойством DTO пишется атрибут: обязательно, диапазон, максимальная длина, регулярное выражение. Набор из стандартной библиотеки, называется аннотациями данных, и вы видели такие атрибуты в любом учебнике. Контроллеры с тем атрибутом над классом проверяют их сами и отвечают четырёхсотым, не вызывая метод. Минимальные API долго этого не умели, и в десятой версии платформы получили встроенную поддержку тех же атрибутов, которая включается одной регистрацией.

Что они дают: простые правила прямо рядом с полем, читаются с листа, работают без кода. Чего не дают: правил, которые смотрят на два поля сразу, правил с зависимостями, например «такой email уже есть», и правил, которые меняются по контексту. И у них есть неприятное свойство: DTO обрастает атрибутами, и через год над каждым свойством по три строки, которые никто не читает.

Где атрибуты по-настоящему на месте, я покажу в следующей лекции: настройки приложения. Там объект маленький, правила простые, обязательно и диапазон, и проверка выполняется один раз на старте. Для контракта API атрибутов быстро становится мало, для конфигурации их обычно достаточно.

Ступень вторая: свои правила. Метод на DTO или отдельный класс, который проверяет то, что атрибутами не выразить: дата окончания позже даты начала, сумма позиций равна сумме заказа, для юридического лица обязателен номер, для физического нет. Здесь уже нужен код, и вопрос только в том, куда его положить.

Ступень третья: FluentValidation. Библиотека, в которой правила пишутся отдельным классом, по одному на DTO, цепочкой методов. Не атрибуты, а код, и не в DTO, а рядом.

[СЛАЙД: листинг валидатора целиком; выделить: класс на один DTO, цепочки RuleFor, условное правило и сообщение]

```csharp
public sealed class CreateOrderDtoValidator : AbstractValidator<CreateOrderDto>
{
    public CreateOrderDtoValidator()
    {
        RuleFor(x => x.CustomerEmail).NotEmpty().EmailAddress();
        RuleFor(x => x.Items).NotEmpty().WithMessage("Заказ без позиций невозможен");
        RuleForEach(x => x.Items).ChildRules(item =>
        {
            item.RuleFor(i => i.Quantity).GreaterThan(0);
            item.RuleFor(i => i.Price).GreaterThanOrEqualTo(0);
        });
        RuleFor(x => x.DeliveryDate)
            .Must(d => d is null || d > DateOnly.FromDateTime(DateTime.UtcNow))
            .WithMessage("Дата доставки должна быть в будущем");
    }
}
```

Один класс на один DTO. Каждое правило это строка, которая читается как предложение: почта не пустая и похожа на почту; позиций не ноль; у каждой позиции количество больше нуля; дата доставки в будущем, если она указана, и это правило записано своим предикатом через Must, потому что готового «больше, если не пусто» нет. Условия, вложенные правила, свои предикаты, свои сообщения, всё выражениями из четвёртой и пятой лекций. Валидатор это обычный класс, его регистрируют в контейнере, его можно тестировать отдельно: подать DTO, проверить список ошибок, и в пятнадцатой лекции это будет одним из самых простых тестов.

Сообщения об ошибках это часть контракта, и над ними стоит подумать один раз. Клиенту-программе нужен код ошибки, стабильный и документированный, чтобы реагировать. Клиенту-человеку нужен текст, и он может быть на разных языках. Библиотека позволяет задать и то и другое, и хранить тексты отдельно от правил. Минимум для лабораторной: понятный текст на одном языке. Но не привязывайте клиента к тексту: тексты меняются, коды нет.

Почему третья ступень чаще всего правильная для сервиса. DTO остаётся чистым описанием данных. Правила живут в одном месте и читаются целиком. Сложные правила выражаются без акробатики. И результат проверки это список ошибок с именами полей, готовый для ответа клиенту. Атрибуты хороши для двух-трёх полей, дальше это.

Регистрация валидаторов в контейнере из следующей лекции делается одной строкой на всю сборку: библиотека находит все классы-валидаторы и регистрирует их по типу DTO. Дальше валидатор нужного типа запрашивается из контейнера, как в листинге через минуту. И одно правило для самих валидаторов: они проверяют DTO сам по себе и не ходят в базу и во внешние сервисы. Правило «такой email уже есть» это не валидатор, и почему, я скажу в конце раздела.

[ПАУЗА]

Теперь правило, ради которого этот раздел, и оно возвращает нас к четвёртой и восьмой лекциям.

[ВОПРОС В ЗАЛ]

Валидатор нашёл ошибки. Что делает обработчик? Кто скажет «проверяет результат и возвращает четыреста»? Так пишут почти все, и так написано в половине примеров. Кто скажет «бросает исключение»? Вот. И сейчас объясню, почему второе.

Вспомните четвёртую лекцию: два вида плохого входа. Ошибка сценария, которая часть логики и возвращается значением. И ошибка контракта, когда клиент прислал то, чего по договору быть не может. Невалидный запрос это ошибка контракта. Отрицательное количество это не «сценарий, в котором заказ не создаётся», это нарушение договора о том, как вообще можно вызывать сервис. Сервис не должен доходить до логики с таким входом. Это исключительная ситуация с точки зрения кода, и это исключение домена.

Как это выглядит. Проверка выполняется до обработчика или в его первой строке. Если ошибки есть, бросается исключение валидации с этим списком. Дальше исключение летит вверх, до того единственного middleware из прошлой лекции. Там появляется третья ветка в switch: исключение валидации превращается в четыреста двадцать два с телом, где перечислены поля и сообщения. Тот же формат ошибки, что для всех остальных, в том же одном месте.

[СЛАЙД: листинг фильтра целиком; подписи: «фильтр на группе», «валидатор из контейнера», «бросок, не возврат», «ветка в middleware из Л8»]

```csharp
orders.AddEndpointFilter(async (context, next) =>
{
    var dto = context.Arguments.OfType<CreateOrderDto>().FirstOrDefault();
    if (dto is not null)
    {
        var validator = context.HttpContext.RequestServices.GetRequiredService<IValidator<CreateOrderDto>>();
        var result = await validator.ValidateAsync(dto, context.HttpContext.RequestAborted);
        if (!result.IsValid)
            throw new ValidationException(result.Errors);
    }
    return await next(context);
});

// в ErrorHandlingMiddleware из Л8 добавляется ветка:
// ValidationException v => (StatusCodes.Status422UnprocessableEntity, v.Errors),
```

Это фильтр конечной точки, о котором я упоминал в прошлой лекции: он срабатывает после маршрутизации, для конкретной группы, и видит аргументы обработчика. Он находит DTO среди аргументов, берёт валидатор из контейнера, проверяет, и если ошибки есть, бросает. Обработчик не вызывается вовсе. А если ошибок нет, обработчик получает уже проверенный DTO и работает с ним, не проверяя ничего. В настоящем проекте такой фильтр пишут один раз обобщённым по типу DTO и вешают на все группы, и это будет частью лабораторной.

Есть и более короткий путь: получить валидатор в параметры обработчика, вызвать в первой строке и бросить. Правило то же, бросок вместо возврата, просто проверка стоит в обработчике, а не снаружи. Фильтр лучше тем, что обработчик о валидации не знает вовсе, и забыть её нельзя. А встроенная поддержка атрибутов из десятой версии платформы отвечает четырёхсотым сама, в своём формате, и это её плюс и минус: меньше кода, но формат ответа не ваш и не в вашем middleware. В курсе формат один, и он наш.

Что мы получили. Обработчик короткий: он делает своё дело и не знает ни о валидации, ни об ошибках. Правила в валидаторе, проверка в фильтре, ответ в middleware. Три места, каждое делает одно. Изменили формат ответа об ошибках валидации, правите одно место. Добавили правило, правите валидатор. Обработчики не тронуты.

Как выглядит ответ с четыреста двадцать два. Тот же объект, что для остальных ошибок: код, сообщение, идентификатор трассировки, и дополнительно словарь из имени поля в список сообщений. Имена полей в том виде, в каком они в JSON, с маленькой буквы, чтобы клиент мог подсветить нужное поле формы. Один формат, одно место, и клиент пишет обработку ошибок один раз для всего API.

И не забывайте про размеры. Список позиций в заказе может прийти с миллионом элементов, и валидатор честно проверит каждый, потратив на это секунды процессора по просьбе одного клиента. Ограничение на количество элементов и на длину строк это тоже правила валидации, и они стоят первыми в цепочке, до проверки содержимого. Вместе с лимитом на размер тела от сервера из прошлой лекции это защита от самого простого способа положить сервис.

И почему не «проверить и вернуть четыреста» в обработчике. Потому что тогда в каждом обработчике первые пять строк одинаковые, формат ответа размазан по всем, и в одном из ста обработчиков кто-то забудет проверить. Ровно аргументы прошлой лекции про try/catch в каждом обработчике, и решение то же: одно место снаружи.

[ПАУЗА]

Одна оговорка про границу. Валидация формы это про то, что данные вообще имеют смысл: число положительное, строка не пустая, дата в будущем. Это проверяется здесь, до логики, без обращения к базе. А «такой email уже зарегистрирован» или «на складе нет столько» это уже логика: требует данных, зависит от состояния, и может быть ошибкой сценария, а не контракта. Такие проверки живут в сервисе, и их результат это либо возвращаемое значение, либо исключение домена другого типа, которое middleware превратит в четыреста девять, конфликт, из седьмой лекции. Граница: валидатор проверяет запрос сам по себе, логика проверяет запрос относительно мира.

Ещё два замечания к границам. Валидация это не авторизация: то, что запрос корректен по форме, не значит, что этому клиенту можно его выполнять, и это отдельный вопрос одиннадцатой лекции с отдельным статусом. И параметры пути и строки запроса тоже данные: размер страницы в сто тысяч это невалидный запрос, и его надо отклонять до похода в базу, иначе один клиент выгружает вам таблицу целиком. Валидатор для параметров запроса пишется так же, только над объектом, собранным из параметров.

И антипаттерн, который я вижу регулярно: проверить в фильтре, а потом ещё раз проверить то же в сервисе, «на всякий случай». Двойная проверка это два места, которые разойдутся. Сервис доверяет тому, что дошло до него через границу, и проверяет только то, чего граница проверить не могла: состояние мира.

Мысль раздела на ребро. Невалидный запрос это нарушение контракта, и он обрывается исключением до обработчика. Правила в валидаторе, проверка в фильтре, ответ в middleware: обработчик про ошибки не знает.

## 4. JSON и сериализация (детали) (22)

[СЛАЙД: заголовок раздела и фраза: «JSON — это строки и числа; всё остальное — договорённость»]

Двадцать две минуты про то, что происходит с объектом между обработчиком и проводом. Вы вернули DTO, клиент получил JSON. Вы приняли JSON, обработчик получил DTO. Между ними сериализатор, и я честно скажу, что о нём думаю, но сначала механика.

[ВОПРОС В ЗАЛ]

Вопрос на разогрев. В C# свойство называется CustomerEmail, с большой буквы. Как оно будет называться в JSON, если ничего не настраивать? Кто скажет «так же»? Кто скажет «с маленькой»? В ASP.NET Core с маленькой: customerEmail. Умолчания веб-фреймворка отличаются от умолчаний самого сериализатора, и это первое, что нужно знать: у сериализатора есть настройки, у веба они свои, и они выставлены за вас.

Совет на всю лекцию: смотрите на сырой JSON. Утилита командной строки с подробным выводом покажет ровно те байты, которые ушли клиенту, и половина вопросов «почему поле не такое» решается этим взглядом. А когда сериализатор не смог прочитать тело запроса, клиент получает четырёхсотый с сообщением, в котором обычно есть путь до проблемного поля и позиция в тексте. Читайте его целиком, прежде чем гадать.

Пойдём по сопоставлению, потому что JSON и типы .NET это два разных мира, и на каждой границе есть решение, которое кто-то принял за вас.

[СЛАЙД: таблица сопоставления: имена → camelCase; регистр при чтении → нечувствителен; null → пишется как null; enum → число по умолчанию, строка по настройке; даты → ISO 8601; decimal → число; отсутствие поля → значение по умолчанию]

Имена. При записи свойства превращаются в имена с маленькой буквы, при чтении сопоставление нечувствительно к регистру. Если имя в JSON другое, например с подчёркиваниями, потому что так решил клиент, есть атрибут над свойством с точным именем и есть настройка на всё приложение с политикой именования. Одно из двух, и лучше второе: одна политика на весь контракт.

Что попадает в JSON, а что нет. Публичные свойства с геттером пишутся, с сеттером или init читаются. Поля по умолчанию не участвуют. Свойство можно исключить атрибутом, и это способ не отдать наружу то, что случайно оказалось в DTO, хотя правильнее, чтобы его там не было. Для record с позиционными параметрами сериализатор вызывает конструктор, сопоставляя имена параметров с именами полей JSON, и поэтому имена параметров в record должны совпадать со свойствами, что позиционная запись из третьей лекции делает сама.

Null. Свойство со значением null записывается как null. Можно настроить, чтобы такие свойства не писались вовсе, и это экономит трафик, но меняет контракт: клиент, который ждёт поле, его не увидит. При чтении null в JSON становится null в свойстве, и если свойство не допускает null по аннотации из четвёртой лекции, сериализатор по умолчанию об этом не знает: аннотация для компилятора, а не для рантайма. В новых версиях его можно попросить уважать аннотации, и тогда null в обязательном поле станет ошибкой чтения, а не исключением где-то глубже. Попросите.

Перечисления. По умолчанию число. Статус «оплачен» уедет клиенту как единица, и клиент должен знать, что единица это «оплачен». Это плохой контракт: число ничего не говорит, и при добавлении значения в середину все числа сдвигаются. Есть конвертер, который пишет и читает перечисления строками, и он включается одной настройкой. Включайте всегда. И вспомните из третьей лекции: неизвестная строка при чтении это ошибка, а неизвестное число молча становится несуществующим значением.

Даты. Стандартный формат из второго раздела: год-месяц-день, буква T, время, и смещение, если оно есть. Сериализатор пишет и читает его без настройки. Тип с поясом пишется со смещением, обычный тип пишется так, как помнит, а помнит он плохо. Дата без времени и время без даты, отдельные типы, тоже поддерживаются. Не изобретайте свой формат дат в JSON, и не принимайте чужой без явного конвертера.

Ещё два типа с форматами, о которых спросят: интервал времени пишется в стандартном текстовом виде, часы, минуты, секунды через двоеточие, и GUID пишется строкой с дефисами. Оба читаются обратно без настройки, и оба лучше не менять.

Числа. Целые и дробные, и decimal из третьей лекции пишется как число с нужной точностью. Одна ловушка: JSON не различает целое и дробное, а клиент на другом языке может прочитать большое целое как число с плавающей точкой и потерять младшие разряды. Идентификаторы больше двух в пятьдесят третьей степени лучше передавать строкой, и есть настройка, которая разрешает читать числа из строк.

С деньгами то же соображение, что в третьей лекции. Decimal уедет в JSON как число с нужными знаками, но клиент на языке, где все числа с плавающей точкой, прочитает его в double и потеряет копейку на большой сумме. Часть платёжных API поэтому передаёт суммы строками или целым числом в минимальных единицах, в копейках. Это решение контракта, и его нужно принять до первого клиента, потому что потом это ломающее изменение из пятого раздела.

Отсутствие. Поле в JSON отсутствует: свойство получает значение по умолчанию, и сериализатор не жалуется. Это та четвёртая ловушка из второго раздела: отсутствие и null неразличимы. Есть слово required из третьей лекции, и сериализатор его уважает: отсутствие обязательного поля станет ошибкой чтения. Для остального различить «не прислали» и «прислали null» стандартными средствами нельзя, и для частичного обновления это придётся решать отдельным типом-обёрткой или другим форматом запроса.

На запись есть настройки, что пропускать: только null, или ещё и значения по умолчанию, вроде нуля и false. Вторая экономит ещё больше, но делает контракт хуже: клиент не отличит «ноль» от «не указано». Для API я советую писать всё, и пусть тело будет на десять байт длиннее. Ясность дороже.

[ПАУЗА]

Полиморфизм. Вот тема, которая болит всегда, на любом сериализаторе, на любом языке, и я объясню, почему.

[ВОПРОС В ЗАЛ]

У вас свойство типа «способ оплаты», а способов три: карта, счёт, наличные, и у каждого свои поля. В C# это базовый тип и три наследника, или три record с общим интерфейсом. Как это записать в JSON? Кто скажет «просто записать поля»? Хорошо, записали поля карты. Клиент прислал обратно те же поля. Сериализатор смотрит на них и должен создать объект. Какого типа? У него в руках базовый тип и набор полей, и он не знает, что это карта. JSON не несёт типов.

Значит, в JSON нужно добавить поле, которое говорит, какой это тип. Это называется дискриминатором, и с этого момента начинаются вопросы. Как поле называется? Какие значения? Должно ли оно быть первым в объекте, чтобы сериализатор узнал тип до того, как начал читать остальное? Что делать с неизвестным значением? Как это описать в документации из пятого раздела?

[СЛАЙД: листинг полиморфизма целиком; выделить атрибут с именем дискриминатора, атрибуты наследников с их значениями, и JSON справа с полем "$type"]

```csharp
[JsonPolymorphic(TypeDiscriminatorPropertyName = "kind")]
[JsonDerivedType(typeof(CardPayment), "card")]
[JsonDerivedType(typeof(InvoicePayment), "invoice")]
public abstract record Payment(decimal Amount);

public sealed record CardPayment(decimal Amount, string Last4) : Payment(Amount);
public sealed record InvoicePayment(decimal Amount, string InvoiceNumber) : Payment(Amount);

// {"kind":"card","amount":100,"last4":"4242"}
```

Сериализатор умеет это с атрибутами: имя поля-дискриминатора на базовом типе, и по атрибуту на каждого наследника с его значением. Пишет правильно, читает правильно, и тип создаётся тот, который указан. Это работает, и это то, что нужно для трёх способов оплаты.

Почему всё равно болит. Первое: долгое время сериализатор требовал, чтобы дискриминатор стоял в JSON первым, иначе не мог прочитать, а клиенты не гарантируют порядок полей; в новых версиях это можно ослабить настройкой, но по умолчанию требование осталось. Второе: неизвестное значение дискриминатора это ошибка, и клиент старой версии, получивший новый тип, падает целиком, а не пропускает одно поле. Третье: дискриминатор это часть контракта, его нельзя переименовать, и его значения нельзя менять, никогда. Четвёртое: документация должна описать все варианты, и генератор из пятого раздела делает это неидеально. Полиморфизм в контракте это обязательство на годы, и прежде чем его вводить, спросите: а нельзя ли три плоских поля с одним обязательным? Часто можно, и это скучнее, но не болит.

Две скучные альтернативы, которые я предпочитаю. Первая: отдельные маршруты на каждый тип, «оплатить картой» и «оплатить по счёту», и у каждого свой плоский DTO. Второй тип никогда не приходит туда, где ждут первый. Вторая: один DTO с полем-перечислением «вид» и набором полей, часть которых обязательна только для своего вида, что проверяет валидатор из третьего раздела условными правилами. Обе не требуют от клиента ничего, кроме обычного JSON, и обе описываются документом без оговорок.

[ПАУЗА]

Теперь сам сериализатор. Он называется System.Text.Json, живёт в стандартной библиотеке, и вот три вещи, которые вы будете с ним делать.

Настройки на приложение. Одно место, где задаётся политика имён, конвертер перечислений, поведение с null, чувствительность к регистру. Для минимальных API это одна регистрация в файле запуска, для контроллеров другая, но суть одна: настройки задаются один раз и действуют на все обработчики. Никогда не настраивайте сериализацию в отдельном обработчике: контракт должен быть однородным, и клиент не должен угадывать, где даты в одном формате, а где в другом.

Единственная настройка, которую стоит менять по окружению, это отступы. В разработке отформатированный JSON читается глазами, в проде он только занимает трафик. Одна условная строка в файле запуска, и это как раз тот редкий случай из прошлой лекции, где развилка по окружению уместна.

Те же настройки используются в обе стороны: для чтения тел запросов и для записи ответов. И в следующей лекции, когда сервис сам будет вызывать другие сервисы, ему понадобится сериализатор для их контрактов, и настройки там свои, потому что чужой контракт может отличаться от вашего. Держите два набора настроек как два именованных объекта, а не один на всё.

Свои конвертеры. Когда сопоставление по умолчанию не подходит: свой формат даты для старого клиента, тип из третьей лекции с одним полем, который должен писаться как строка, а не как объект с полем. Конвертер это класс с двумя методами, прочитать и записать, и он регистрируется в тех же настройках. Тот самый record struct для почты из третьей лекции без конвертера превратится в объект с полем Value, а с конвертером в строку, как и должен. Это одно из первых, что вы напишете в лабораторной.

Как он выглядит, чтобы не пугаться. Класс, наследующий обобщённый базовый с параметром вашего типа. Метод чтения получает читатель, берёт из него строку и создаёт ваш тип. Метод записи получает писатель и ваше значение и пишет строку. Десять строк, и тип с одним полем ведёт себя в JSON как примитив. Сериализатор находит конвертер по типу свойства, и вам не нужно помечать каждое место, где тип используется.

Генераторы кода. Помните вторую лекцию: сериализатор по умолчанию работает через рефлексию. Он смотрит на тип во время выполнения, находит свойства, строит код доступа к ним. Это и есть то, что ломается под обрезкой и AOT, и вот как это чинится.

[СЛАЙД: листинг контекста целиком; подписи: «partial-класс, вторую половину пишет генератор», «по атрибуту на тип контракта», «подключение к настройкам»]

```csharp
[JsonSerializable(typeof(OrderDto))]
[JsonSerializable(typeof(CreateOrderDto))]
[JsonSerializable(typeof(Payment))]
internal sealed partial class AppJsonContext : JsonSerializerContext;

// в файле запуска:
builder.Services.ConfigureHttpJsonOptions(options =>
    options.SerializerOptions.TypeInfoResolverChain.Insert(0, AppJsonContext.Default));
```

Класс со словом partial из третьей лекции, и по атрибуту на каждый тип контракта. Генератор на этапе компиляции дописывает вторую половину класса: код, который читает и пишет эти типы без рефлексии. Свойства, конвертеры, полиморфизм, всё это становится обычным кодом, который видит компилятор и анализатор обрезки. Одна строка в настройках подключает контекст, и сериализатор берёт сгенерированное вместо рефлексии. Для AOT это обязательно, без контекста приложение не соберётся или упадёт при первом запросе. Без AOT это тоже полезно: старт быстрее, потому что нечего анализировать в рантайме, и все типы контракта перечислены в одном месте, что само по себе документация.

Контекст и рефлексия могут сосуществовать: цепочка резолверов в настройках сначала спрашивает контекст, и если тип там не описан, идёт к рефлексии. Без AOT это удобно для перехода. Под AOT рефлексии нет, и тип, забытый в контексте, это исключение при первом запросе с ним, поэтому тест, который проходит по всем маршрутам, из пятнадцатой лекции, здесь обязателен. И перечисляйте в контексте типы контракта, DTO, а не сущности: это ещё одна причина, почему они разные.

[ПАУЗА]

И теперь честно, как обещано в программе.

[СЛАЙД: одна фраза: «сериализация — слабое место платформы; кто напишет нормальный сериализатор — я первым на него перейду»]

Сериализация это слабое место платформы. Я это говорю как человек, который пользуется ей каждый день, и вот претензии по существу. Требование к порядку дискриминатора, которое я описал: клиенты не обязаны его соблюдать, и это правильно с точки зрения JSON, а сериализатор годами не умел иначе. Неразличимость отсутствия и null, которую приходится решать обёртками. Сообщения об ошибках чтения, из которых не всегда понятно, какое поле и почему. Настройки, разбросанные между атрибутами на типах, настройками на приложении и контекстом генератора, где одно может перекрыть другое незаметно. Привязка через конструктор для record, у которой свои правила про имена параметров, которые нужно знать. Каждое из этого по отдельности мелочь и решаемо. Вместе это час на каждую нетривиальную схему, и я этот час теряю регулярно.

Предыдущий сериализатор, который жил в отдельном пакете и который вы найдёте в половине старых проектов, был гибче: он умел почти всё из этого списка. Но он был медленнее и строился на рефлексии целиком, и платформа сделала ставку на скорость и AOT. Это осознанный выбор, и я понимаю его причины. Но вопрос «кто напишет сериализатор, который одновременно быстрый, дружит с генераторами и при этом гибкий в схемах» остаётся открытым. Если кто-то из вас его напишет, пусть даже без выдающейся производительности, я первым перейду на него. Это не жалоба. Это приглашение.

Чтобы приглашение было конкретным, вот что я бы хотел от нормального сериализатора. Различать отсутствие поля и null без обёрток. Читать метаданные в любом порядке. Сообщать об ошибке с именем поля и ожидаемым типом в одной строке. Настраиваться в одном месте, без трёх слоёв, которые перекрывают друг друга. Дружить с генератором кода, чтобы работать под AOT. Всё это по отдельности сделано в разных библиотеках на разных языках. Вместе пока нет.

Практический вывод из этого честного абзаца: держите контракт простым. Плоские DTO, строки и числа, стандартные даты, перечисления строками, минимум полиморфизма. Чем проще схема, тем меньше вы встречаетесь со слабыми местами, и тем проще клиенту на любом языке.

[ПАУЗА]

И последнее в разделе, приятное: стриминг ответа. Помните IAsyncEnumerable из шестой лекции, который я обещал довезти до HTTP? Вот он.

[СЛАЙД: листинг целиком; подписи: «обработчик возвращает асинхронную последовательность», «сериализатор пишет массив по элементам», «первый элемент уходит до вычисления последнего»]

```csharp
app.MapGet("/orders/export", (IOrderService service, CancellationToken ct) =>
    service.ExportAsync(ct));   // IAsyncEnumerable<OrderDto>

// в сервисе:
public async IAsyncEnumerable<OrderDto> ExportAsync([EnumeratorCancellation] CancellationToken ct)
{
    await foreach (var order in repository.ReadAllAsync(ct))
        yield return order.ToDto();
}
```

Обработчик возвращает асинхронную последовательность. Сериализатор понимает этот тип особым образом: он открывает JSON-массив, и по мере того, как последовательность отдаёт элементы, пишет их в ответ, один за другим, и закрывает массив, когда элементы кончились. Ответ уходит клиенту по кускам, тем самым chunked из седьмой лекции. Первый заказ уходит клиенту до того, как из базы прочитан последний. В памяти в каждый момент один элемент, а не весь список. Миллион заказов на экспорт это ровный поток, а не гигабайт в куче и минута ожидания.

Всё, что мы разбирали в шестой лекции, здесь работает: токен отмены из контекста прерывает чтение, если клиент ушёл; атрибут на токене направляет его внутрь; каждое ожидание отдаёт поток. И ничего нового писать не нужно: тип возврата, и фреймворк делает остальное. Для событий, идущих во времени, а не для массива, в десятой версии платформы появился встроенный результат для Server-Sent Events из седьмой лекции, с тем же принципом: последовательность на входе, поток событий на выходе.

У стриминга есть цена, и её надо знать до того, как поставить его на главный маршрут. Статус и заголовки уходят с первым элементом, вспомните флаг «ответ начался» из прошлой лекции. Если ошибка случилась на тысячном элементе, изменить статус уже нельзя: клиент получит двести и оборванный массив. Обработчик ошибок из прошлой лекции здесь не поможет, он увидит начатый ответ и пропустит исключение дальше, и соединение оборвётся. Клиент должен быть готов к незакрытому массиву, а сервис должен делать всё, что может упасть, до первого элемента. Для экспорта это приемлемо, для операции, где важна целостность, нет.

И про безопасность чтения два слова. У сериализатора есть ограничение глубины вложенности по умолчанию, и оно защищает от документа из тысяч вложенных скобок, который иначе съел бы стек. Есть лимит размера тела от сервера из прошлой лекции. Оба лимита разумны, и поднимать их стоит только для конкретного маршрута с конкретной причиной.

Мысль раздела на ребро. Сериализация это набор решений, принятых за вас, и их надо знать и задавать один раз на всё приложение. Контракт держите плоским, потому что каждая сложность в схеме это встреча со слабым местом.

## 5. Описание контракта наружу (8)

[СЛАЙД: заголовок раздела и фраза: «документ генерируется из кода, а не пишется рядом с ним»]

Восемь минут о том, как рассказать о контракте тем, кто будет его вызывать, и как его потом менять, не сломав их.

OpenAPI. Стандарт описания HTTP-API: документ, обычно JSON, в котором перечислены все маршруты, их методы, параметры, тела запросов и ответов со схемами, возможные статусы. По этому документу генерируются клиенты на любом языке, рисуется интерактивная страница, где можно попробовать запрос, проверяется совместимость версий. Это то, чем для REST стал WSDL из седьмой лекции, только без обязательности и тяжести.

Главное свойство: документ генерируется из кода. Не пишется рядом, а выводится из того, что вы написали. Из шаблонов маршрутов берутся пути и параметры. Из типов параметров берутся схемы запросов. Из типизированных результатов первого раздела, того самого объединения «либо двести с заказом, либо четыреста четыре», берутся возможные ответы. Из DTO берутся схемы ответов, с учётом настроек сериализатора из прошлого раздела. Вот почему я настаивал на типизированных результатах: они не только для компилятора, они для документа. Генератор встроен в платформу, включается двумя строками, и документ доступен по адресу в самом сервисе. Интерактивная страница поверх него это отдельный пакет, и в шаблоне проекта её больше нет, потому что в проде она не нужна.

Кто читает этот документ. Люди, через интерактивную страницу локально. Инструменты, которые по документу генерируют клиент на любом языке, и это главный потребитель: клиентская команда получает типизированный клиент за минуту, вместо того чтобы писать его руками по описанию. И проверки в конвейере сборки: документ текущей версии сравнивается с документом предыдущей, и ломающее изменение из следующей части ловится до выкладки, а не после звонка от клиента. В пятнадцатой лекции мы к этой идее вернёмся.

Что генератор не может вывести сам. Описания словами: что значит поле, какие бизнес-правила. Примеры значений. Для этого есть атрибуты и методы на маршрутах, и есть возможность брать описания из комментариев к коду. Не увлекайтесь: документ, который никто не читает, потому что он не совпадает с кодом, хуже отсутствующего. Генерируемая часть совпадает всегда, рукописная только пока её обновляют.

Полиморфизм из прошлого раздела в документе описывается как выбор из нескольких схем с дискриминатором, и генераторы клиентов понимают это по-разному: часть делает иерархию типов, часть общий тип со всеми полями. Ещё один аргумент за плоские DTO: их схема одинаково понятна любому инструменту. А примеры значений, если вы их добавите, попадают в документ и в интерактивную страницу, и клиентская команда увидит не только тип поля, но и как выглядит настоящее значение.

[ПАУЗА]

Теперь версионирование, и это про обязательства.

[ВОПРОС В ЗАЛ]

Вы переименовали поле в DTO. Клиенты сломались? Кто скажет «да, если они его читали»? Все. А если вы добавили поле? Кто скажет «нет»? Правильно, почти всегда нет. Вот в этой разнице вся обратная совместимость.

[СЛАЙД: две колонки: «можно без новой версии: добавить необязательное поле в ответ, добавить необязательный параметр, добавить новый маршрут, добавить значение перечисления с оговоркой» и «нельзя: переименовать или удалить поле, изменить тип, сделать поле обязательным в запросе, изменить смысл статуса, изменить формат даты»]

Что можно менять, не ломая никого. Добавить поле в ответ: клиент, который его не знает, проигнорирует. Добавить необязательный параметр в запрос со значением по умолчанию: старый клиент не присылает, получает умолчание. Добавить новый маршрут. Добавить новое значение перечисления, с оговоркой из прошлого раздела: если клиент читает перечисление строго, новое значение его уронит, поэтому договоритесь заранее, что неизвестные значения клиент обязан переживать.

Что нельзя. Переименовать или удалить поле. Изменить тип поля: число стало строкой. Сделать необязательное поле запроса обязательным: старые клиенты его не шлют. Изменить смысл: тот же статус теперь означает другое. Изменить формат: даты стали в другом виде. Всё это ломающие изменения, и каждое из них означает, что клиенты должны переписать код одновременно с вашей выкладкой, чего в реальности не бывает никогда.

Если ломающее изменение всё-таки нужно, появляется версия. Обычно в адресе: сегмент с номером версии перед ресурсом. Реже в заголовке. Старая версия продолжает работать, новая живёт рядом, клиенты переезжают в своём темпе, и через объявленный срок старая отключается. Для этого есть библиотека, которая делает версии частью маршрутизации и документа, и в лабораторной достаточно префикса в группе из первого раздела.

Старая версия не исчезает молча. Есть заголовки, которыми сервер сообщает клиенту, что маршрут устарел и когда будет отключён, и есть пометки устаревания в документе. Клиенты редко читают письма, но инструменты читают заголовки и документ, и предупреждение появится у них в сборке. Отключение объявляется заранее, в датах, и соблюдается, иначе следующее объявление никто не воспримет всерьёз.

Два правила из опыта. Первое: версия это дорого. Две версии это два набора обработчиков, два набора DTO, два набора тестов, и всё это живёт годами. Прежде чем ломать, спросите, нельзя ли добавить. Почти всегда можно: новое поле рядом со старым, старое помечено устаревшим в документе, и через год, когда его никто не читает, его убирают уже без версии. Второе: контракт это то, что вы обещали, а не то, что написали. Клиент, который полагается на порядок полей в JSON или на то, что список всегда отсортирован, полагается на то, чего вы не обещали. Документ из этого раздела это и есть граница обещания, и всё, что за ней, можно менять.

Сегодня мы описали контракт: обработчик как делегат с типизированным результатом, путь от запроса к параметрам с его ловушками, DTO вместо сущностей, валидация исключением до логики, сериализация с её решениями и слабыми местами, и документ, который выводится из всего этого. В следующей лекции мы займёмся тем, что стояло в параметрах обработчиков и о чём я говорил «фреймворк подставит из контейнера»: внедрением зависимостей, исходящими вызовами и конфигурацией.

На девятой лабораторной вы опишете CRUD-контракт сервиса: эндпоинты, DTO, валидация, и свой формат ответа об ошибке ровно в одном middleware, так что эндпоинты про ошибки не знают.
