# Л10. DI, конфигурация и исходящие вызовы — тезисы

**Длительность:** 80 минут
**Цель:** показать, как приложение собирается из частей и настраивается снаружи.
**Полный текст лекции:** [L10-di-and-configuration.md](L10-di-and-configuration.md)
**Слайды:** [slides/L10-di-and-configuration-slides.tex](slides/L10-di-and-configuration-slides.tex) —
55 кадров, один на каждый `[СЛАЙД n — …]` в сценарии.

Лекция про то, что решается снаружи сервиса: из чего он состоит и где он работает. Раздел 1 — внедрение
зависимостей: идея, схема контейнера, времена жизни и их ошибки, код (регистрации, service locator,
модули). Раздел 2 — конфигурация: слои источников, окружения, один образ и переменные окружения.
Раздел 3 — options pattern: класс настроек, три интерфейса, проверка на старте. Раздел 4 — исходящие
HTTP-вызовы: почему нельзя создавать `HttpClient` на каждый запрос, фабрика и типизированный клиент,
устойчивость. Четвёртый раздел опирается на первые три: времена жизни и проверенные настройки.

## Как читать

Число в начале тезиса — кадр, на котором он живёт: **[6]**. Прочерк **[—]** значит, что кадра нет и
тезис идёт голосом. Вопросов в зал два — **[12]** и **[43]**: на слайде только вопрос, ответ звучит вслух.

## Сквозные тезисы

- Сервис не должен знать, из чего он состоит и где он работает: это решается снаружи.
- Конструктор — единственная честная точка входа зависимостей.
- Времена жизни — контракт с контейнером; его нарушение — пленённые зависимости и общее состояние.
- Разница между окружениями живёт в значениях конфигурации, а не в коде. Позднее перекрывает раннее.
- Образ один, сред много: верхний слой — переменные окружения.
- Настройки — тип, а не строка по ключу, и проверяются на старте.
- Внешний сервис — зависимость, как хранилище: типизированный клиент приходит в конструктор.
- Повторять можно только то, что безопасно повторить.

## 1. Внедрение зависимостей (30 мин · слайды 2–24)

- **[2]** Раздел: сервис не знает, из чего он состоит.
- **[—]** Две лекции звучало «фреймворк подставит из контейнера»; сегодня — что это значит.

Идея

- **[—]** Сервису нужно хранилище: самое простое — `new` прямо в сервисе. Так пишут первые несколько лет.
- **[3]** Класс создаёт зависимость сам: сервис привязан к SQL-хранилищу, смена базы — пересборка, тест
  требует базу, у десяти сервисов десять экземпляров.
- **[4]** Три слова: инверсия управления — принцип, внедрение зависимостей — способ, контейнер — инструмент.
  Пять классов собирают руками в `Main`.
- **[5]** Зависимость приходит снаружи: класс объявляет интерфейс, composition root создаёт и соединяет.
  Замена реализации — одна строка в корне; сколько экземпляров, решает корень.
- **[6]** Конструктор — единственная честная точка входа зависимостей.
- **[—]** Встроенный контейнер внедряет только через конструктор — это дисциплина. Конструктор с семью
  параметрами — подсказка о дизайне. Аналогия — сборка мебели по инструкции.
- **[—]** Зачем интерфейс, если реализация одна? Для тестов — и как граница (Л3). Для класса без внешних
  зависимостей интерфейс — шум.

Схема

- **[7]** Контейнер умеет две вещи. Регистрация — правило в списке `Services`: сервис, реализация, время
  жизни; ничего не создаёт. Разрешение — объект по правилу, после `Build`; его вызывает фреймворк. В
  Development `Build` проверяет список: «забыли зарегистрировать» ловится на старте.
- **[8]** Разрешение — дерево по конструкторам: строит сверху вниз, создаёт снизу вверх. План создания
  кэшируется: микросекунды.
- **[9]** Конструктор не делает работу: берёт зависимости и кладёт в поля. Соединения, файлы, сеть, потоки —
  в явном асинхронном методе или фоновом сервисе (Л8).

Времена жизни

- **[10]** Singleton — один на приложение; scoped — один на запрос; transient — новый на каждое разрешение.
  Создаются лениво.
- **[11]** Контейнер владеет тем, что создал: scoped и transient освобождаются с областью, singleton — при
  остановке; асинхронное освобождение — тоже. Пришло через конструктор — вы не владелец (Л6).
- **[12]** Вопрос: singleton принимает scoped — что произойдёт?
- **[13]** Captive dependency: singleton держит scoped дольше, чем тот живёт. Настоящее сообщение контейнера.
  Проверка — только в Development.
- **[14]** Пять ошибок: singleton держит scoped; изменяемый singleton (Л5); контекст базы не той длительности;
  transient из корня; `Dispose` чужого.
- **[15]** Как выбрать: нет изменяемого состояния — singleton; состояние запроса — scoped, ничьё — transient;
  держит ресурс — scoped. Хоть одна зависимость scoped — объект scoped.

Код

- **[16]** Было и стало: `new` конкретного класса со строкой подключения → интерфейс в конструкторе и две
  строки composition root до `Build`.
- **[17]** Формы регистрации: интерфейс и реализация, только реализация, готовый экземпляр, фабрика, открытые
  обобщения, `TryAdd`. Почти всегда хватает первых двух.
- **[18]** Несколько реализаций: `IEnumerable<T>` — все, в порядке регистрации; декоратор — обёртка снаружи,
  регистрируется фабрикой.
- **[19]** Service locator, пример: класс принимает `IServiceProvider` и достаёт две зависимости в теле метода;
  рядом тот же класс с двумя параметрами конструктора.
- **[20]** Регистрацию забыли: с локатором сервис стартовал и упал первый запрос; с конструктором сервис не
  стартовал. Настоящий вывод обоих запусков.
- **[21]** Цена локатора: прячет граф, переносит ошибку на первый вызов, ломает тесты и проверку времён жизни.
  Законен на границе.
- **[—]** Законная форма для дорогой зависимости — фабрика-делегат в конструкторе: один названный способ
  создать одну вещь.
- **[—]** Статический класс, который ходит в базу или читает время, — зависимость, которой нет ни в одном
  конструкторе.
- **[—]** Сто сервисов — сто строк с `Add` в файле запуска. Решение — методы расширения (Л5).
- **[22]** Модули: метод расширения `Add…` на модуль, возвращает коллекцию; файл запуска читается как
  оглавление. Модуль регистрирует только своё, порядок вызовов не важен.
- **[23]** Явные модули против сканирования сборки. Composition root проверяют тестом (Л15).
- **[—]** Куда копать: книга Симана и ван Дёрсена.
- **[24]** Мысль раздела: состав — в одном месте, зависимости — в конструкторе, времена жизни — контракт.

## 2. Конфигурация и окружение (25 мин · слайды 25–36)

- **[25]** Раздел: код один, окружений много; разница живёт снаружи.

Источники

- **[—]** В листинге «было и стало» осталась строка подключения. Composition root знает состав, но не
  должен знать, где работает.
- **[26]** Конфигурация — адреса, лимиты, уровни логов, переключатели. Бизнес-правила — код. Граница: значение
  может поменять администратор.
- **[27]** Слои: `appsettings.json` → файл окружения → секреты пользователя → переменные окружения →
  аргументы; вне разработки сверху хранилище секретов. Позднее перекрывает раннее.
- **[—]** Секция `ConnectionStrings` — соглашение, которое понимает всё вокруг. Провайдеры — плоские пары
  «ключ — значение»; ключи без учёта регистра; файлы отслеживаются.
- **[28]** Три записи одного ключа: вложенный JSON, `Rates__TimeoutSeconds`, `--Rates:TimeoutSeconds=2`.
- **[—]** Списки — индексами; десять переменных на список — сигнал, что списку место не в конфигурации.
- **[29]** Отладочное представление: ключ, значение и провайдер. Нет ключа — `null`, не исключение. По ключу
  читает файл запуска, бизнес-логика — нет. В этом выводе будут секреты: только в разработке.

Окружения

- **[30]** Окружение — строка в переменной: Development, Staging, Production. От неё зависят второй файл,
  поведение фреймворка, ваши развилки. Переменная не задана — Production: безопасное умолчание.
- **[—]** Локально имя задаёт файл настроек запуска с профилями; в опубликованное приложение он не попадает.
- **[31]** Разница — в значениях, а не в коде: адрес шлюза из конфигурации, в разработке там заглушка.
- **[—]** Стенд повторяет Production во всём, кроме адресов. Конфигурация в тестах — провайдер из словаря (Л15).
- **[32]** Переключатели: окружение, адреса Kestrel, уровень логов; `DOTNET_gcServer`,
  `DOTNET_GCHeapHardLimit`, `DOTNET_ThreadPool_MinThreads`, `DOTNET_TieredCompilation`,
  `DOTNET_ROLL_FORWARD`. `DOTNET_` читает рантайм до первой строки кода.
- **[—]** Не крутить ручки без измерения. Развёрнутый сервис ведёт себя иначе — сравните окружение, а не код.

Один образ

- **[—]** Один образ, стенд и Production с разными базами. Два образа — уже не то, что тестировали; файл
  при запуске — лишняя механика монтирования.
- **[33]** Образ один, среды разные, разница — в переменных. Секретов в образе нет.
- **[34]** Почему переменные: не требуют файловой системы, их задаёт всё, не попадают в образ. Файлы — для
  больших структур и секретов; переменные видно.
- **[—]** Локальную строку подключения хранят в секретах пользователя, а не в файле под игнором.
- **[35]** `dotnet user-secrets`: файл в домашней папке, только в разработке; значение приходит из
  `secrets.json`. В `appsettings.json` — структура и безобидные умолчания.
- **[—]** Проверка: репозиторий станет публичным — что утечёт? Переменные рабочего окружения — в репозитории
  развёртывания. В конфигурации нет логики и выбора классов.
- **[36]** Мысль раздела: разница — в конфигурации; образ один, сверху — переменные.

## 3. Options pattern (10 мин · слайды 37–41)

- **[37]** Раздел: настройки — это тип, а не строка по ключу.
- **[38]** Класс настроек: свойства, умолчания, атрибуты, имя секции константой, единица в имени. Цепочка:
  `BindConfiguration`, `ValidateDataAnnotations`, `ValidateOnStart`. Потребитель получает через конструктор.
- **[—]** Конструктор без параметров, публичная запись, никакой логики, два уровня вложенности — предел.
- **[39]** `IOptions` — один раз, singleton; `IOptionsSnapshot` — на запрос, scoped; `IOptionsMonitor` — всегда
  актуальное, singleton. Перечитываются файлы, а не переменные окружения.
- **[—]** `Value` против `CurrentValue`; именованные настройки — имена константами.
- **[—]** При выкладке забыли адрес сервиса курсов: без `ValidateOnStart` об этом узнают на первом запросе.
- **[40]** С `ValidateOnStart` — процесс не поднялся, трафик на старой версии. Без него — падает первый запрос
  за курсом. Настоящее сообщение об ошибке.
- **[—]** Проверка кодом — в той же цепочке; сообщение называет переменную, которую задать. В тесте — `IOptions`
  из готового объекта.
- **[41]** Мысль раздела: настройки — тип; проверяются на старте, пока ошибка ничего не стоит.

## 4. Исходящие HTTP-вызовы (15 мин · слайды 42–55)

- **[42]** Раздел: внешний сервис — это зависимость, как хранилище.

Проблема

- **[43]** Вопрос: HTTP-запрос из метода — что пишете? `new HttpClient` в `using`.
- **[44]** Клиент на каждый запрос: `HttpClient` держит обработчик, обработчик — пул соединений. Новый клиент —
  новый пустой пул; `Dispose` закрывает соединение. Пул, созданный на один запрос, ничего не переиспользует.
- **[45]** Что происходит с соединением: каждый запрос заново платит за DNS, TCP и TLS; закрытое соединение
  ещё минуту держит локальный порт (`TIME_WAIT`); портов около 28 тысяч — потолок примерно 470 новых
  соединений в секунду к одному адресу.
- **[46]** Проверим: 2000 запросов — 4,8 с и 1844 соединения в `TIME_WAIT` с клиентом на каждый запрос против
  2,0 с и одного соединения с общим клиентом. Настоящий вывод.
- **[—]** Когда порты кончаются, ошибка выглядит как сбой сети; `using` не помогает, а вредит.
- **[47]** Две ошибки: клиент на каждый запрос живёт слишком мало; один статический — слишком долго: DNS
  разрешён один раз, запросы идут на старый адрес. Клиент должен жить долго, но не вечно.
- **[—]** В утилите — время жизни соединения в пуле. Клиент рассчитан на одновременное использование.

Фабрика и клиент

- **[48]** Фабрика: лёгкие клиенты поверх пула обработчиков; обработчики заменяются раз в две минуты —
  соединения переоткрываются, DNS перечитывается. Именованные — строки, типизированные — класс.
- **[49]** Типизированный клиент: класс принимает `HttpClient` и умеет ходить в один внешний сервис;
  потребитель принимает его как обычную зависимость.
- **[50]** Регистрация: перегрузка `AddHttpClient` с контейнером берёт адрес и таймаут из проверенных
  `RatesOptions`; строковых ключей нет. Типизированный клиент — transient, в singleton его не держат.
- **[51]** Внутри клиента — адреса, заголовки, чужой DTO, превращение ошибок в свои исключения. Снаружи —
  логика; потребитель не знает про HTTP. Настройки JSON для чужого контракта — свои (Л9).

Устойчивость

- **[52]** Три инструмента: таймаут — не ждать вечно (по умолчанию сто секунд); повтор — только идемпотентное
  (Л7); выключатель — отказывать сразу, пока сосед лежит.
- **[—]** Таймаут — тот же `CancellationToken` (Л6). Через все слои идёт токен запроса.
- **[—]** Сколько раз повторять? «Пока не получится» — шторм повторов.
- **[53]** Стандартный набор: таймаутов два — на попытку и на операцию; попыток немного, пауза растёт,
  разброс случайный. По умолчанию повторяет и `POST`: для неидемпотентных вызовов повторы отключают явно.
  Начинайте с умолчаний.
- **[54]** Когда сосед лежит: курс — из кэша с пометкой (Л12), платёж — честная 503. Решение принимает сервис,
  заранее. Исходящие вызовы видны в логе: длительность и статус.
- **[—]** Заголовок трассировки добавится в Л12. Тест клиента — подменённый нижний обработчик (Л15).
- **[—]** Итог лекции и анонс лабораторной звучат голосом перед последним кадром.
- **[55]** Мысль раздела: `HttpClient` выдаёт фабрика; повторять можно только безопасное.

## Открытые вопросы

Авторское решение, не менять по умолчанию:

1. **Порядок разделов — DI → конфигурация → options → HTTP.** Четвёртый раздел собирает первые три:
   типизированный клиент регистрируется из `RatesOptions`, поэтому options идут до HTTP.
2. **Раздел DI идёт от идеи к коду: идея → схема → времена жизни → код.** До кадра 16 в разделе нет ни одного
   листинга. Keyed-сервисы не показываются ни на слайдах, ни голосом.
3. **Кадров с планом раздела нет.** Порядок раздела называется голосом в его начале; отдельные навигационные
   слайды убраны по итогам ревью.
4. **Вопросов в зал два** — captive dependency (12) и HTTP-запрос из метода (43). Остальные вопросы первой
   версии стали обычным рассказом; новые не добавлять.
5. **Колода — 55 кадров**, целевой размер 50–60.
6. **Последний кадр — мысль раздела 4**, после итога лекции и анонса лабораторной.
7. **Кадр 28: `dotnet HelloWorld.dll`**, в листинге сценария — `OrdersService.dll`. На слайде имя учебного
   проекта курса, потому что вывод кадра 29 снят с него.
