# Л10. DI, конфигурация и исходящие вызовы — тезисы

Лекция про то, что решается снаружи сервиса: из чего он состоит и где он работает. Раздел 1 — внедрение

устойчивость. Четвёртый раздел опирается на первые три: времена жизни и проверенные настройки.

## Сквозные тезисы

- Сервис не должен знать, из чего он состоит и где он работает: это решается снаружи.
- Конструктор — единственная честная точка входа зависимостей.
- Времена жизни — контракт с контейнером; его нарушение — пленённые зависимости и общее состояние.
- Разница между окружениями живёт в значениях конфигурации, а не в коде. Позднее перекрывает раннее.
- Образ один, сред много: верхний слой — переменные окружения.
- Настройки — тип, а не строка по ключу, и проверяются на старте.
- Внешний сервис — зависимость, как хранилище: типизированный клиент приходит в конструктор.
- Повторять можно только то, что безопасно повторить.

## 1. Внедрение зависимостей (30 мин · слайды 2–32)

- **[2]** Раздел: сервис не знает, из чего он состоит.
- **[—]** Две лекции звучало «фреймворк подставит из контейнера»; сегодня — что это значит.
- **[3]** План раздела: идея → схема → времена жизни → код.

Шаг 1. Идея

- **[4]** Вопрос: сервису нужно хранилище — что в конструкторе? «`new`» — так пишут первые несколько лет.
- **[5]** Класс создаёт зависимость сам: сервис привязан к SQL-хранилищу, смена базы — пересборка, тест
  требует базу, у десяти сервисов десять экземпляров.
- **[6]** Три слова: инверсия управления — принцип, внедрение зависимостей — способ, контейнер — инструмент.
  Пять классов собирают руками в `Main`.
- **[7]** Зависимость приходит снаружи: класс объявляет интерфейс, composition root создаёт и соединяет.
  Замена реализации — одна строка в корне; сколько экземпляров, решает корень.
- **[8]** Конструктор — единственная честная точка входа зависимостей.
- **[—]** Встроенный контейнер внедряет только через конструктор — это дисциплина. Конструктор с семью
  параметрами — подсказка о дизайне. Аналогия — сборка мебели по инструкции.
- **[9]** Вопрос: зачем интерфейс, если реализация одна? Для тестов — и как граница (Л3). Для класса без
  внешних зависимостей интерфейс — шум.

Шаг 2. Схема

- **[10]** План раздела: шаг «схема».
- **[11]** Контейнер умеет две вещи. Регистрация — правило в списке `Services`: сервис, реализация, время
  жизни; ничего не создаёт. Разрешение — объект по правилу, после `Build`; его вызывает фреймворк. В
  Development `Build` проверяет список: «забыли зарегистрировать» ловится на старте.
- **[12]** Разрешение — дерево по конструкторам: строит сверху вниз, создаёт снизу вверх. План создания
  кэшируется: микросекунды.
- **[13]** Конструктор не делает работу: берёт зависимости и кладёт в поля. Соединения, файлы, сеть, потоки —
  в явном асинхронном методе или фоновом сервисе (Л8).

Шаг 3. Времена жизни

- **[14]** План раздела: шаг «времена жизни».
- **[15]** Singleton — один на приложение; scoped — один на запрос; transient — новый на каждое разрешение.
  Создаются лениво.
- **[16]** Контейнер владеет тем, что создал: scoped и transient освобождаются с областью, singleton — при
  остановке; асинхронное освобождение — тоже. Пришло через конструктор — вы не владелец (Л6).
- **[17]** Вопрос: singleton принимает scoped — что произойдёт?
- **[18]** Captive dependency: singleton держит scoped дольше, чем тот живёт. Настоящее сообщение контейнера.
  Проверка — только в Development.
- **[19]** Пять ошибок: singleton держит scoped; изменяемый singleton (Л5); контекст базы не той длительности;
  transient из корня; `Dispose` чужого.
- **[20]** Как выбрать: нет изменяемого состояния — singleton; состояние запроса — scoped, ничьё — transient;
  держит ресурс — scoped. Хоть одна зависимость scoped — объект scoped.

Шаг 4. Код

- **[21]** План раздела: шаг «код».
- **[22]** Было и стало: `new` конкретного класса со строкой подключения → интерфейс в конструкторе и две
  строки composition root до `Build`.
- **[23]** Формы регистрации: интерфейс и реализация, только реализация, готовый экземпляр, фабрика, открытые
  обобщения, `TryAdd`. Почти всегда хватает первых двух.
- **[24]** Несколько реализаций: `IEnumerable<T>` — все, в порядке регистрации; декоратор — обёртка снаружи,
  регистрируется фабрикой.
- **[25]** Service locator, пример: класс принимает `IServiceProvider` и достаёт две зависимости в теле метода;
  рядом тот же класс с двумя параметрами конструктора.
- **[26]** Регистрацию забыли: с локатором сервис стартовал и упал первый запрос; с конструктором сервис не
  стартовал. Настоящий вывод обоих запусков.
- **[27]** Цена локатора: прячет граф, переносит ошибку на первый вызов, ломает тесты и проверку времён жизни.
  Законен на границе.
- **[—]** Законная форма для дорогой зависимости — фабрика-делегат в конструкторе: один названный способ
  создать одну вещь.
- **[28]** Вопрос: кто писал статический класс, который ходит в базу или читает время? Это зависимость,
  которой нет ни в одном конструкторе.
- **[29]** Вопрос: сто строк с `Add` — что делать? Методы расширения (Л5).
- **[30]** Модули: метод расширения `Add…` на модуль, возвращает коллекцию; файл запуска читается как
  оглавление. Модуль регистрирует только своё, порядок вызовов не важен.
- **[31]** Явные модули против сканирования сборки. Composition root проверяют тестом (Л15).
- **[—]** Куда копать: книга Симана и ван Дёрсена.
- **[32]** Мысль раздела: состав — в одном месте, зависимости — в конструкторе, времена жизни — контракт.

## 2. Конфигурация и окружение (25 мин · слайды 33–51)

- **[33]** Раздел: код один, окружений много; разница живёт снаружи.
- **[34]** План раздела: источники → окружения → один образ.

Шаг 1. Источники

- **[35]** Вопрос: что в листинге «было и стало» исправили не до конца? Строка подключения. Composition root
  знает состав, но не должен знать, где работает.
- **[36]** Конфигурация — адреса, лимиты, уровни логов, переключатели. Бизнес-правила — код. Граница: значение
  может поменять администратор.
- **[37]** Слои: `appsettings.json` → файл окружения → секреты пользователя → переменные окружения →
  аргументы; вне разработки сверху хранилище секретов. Позднее перекрывает раннее.
- **[—]** Секция `ConnectionStrings` — соглашение, которое понимает всё вокруг. Провайдеры — плоские пары
  «ключ — значение»; ключи без учёта регистра; файлы отслеживаются.
- **[38]** Три записи одного ключа: вложенный JSON, `Rates__TimeoutSeconds`, `--Rates:TimeoutSeconds=2`.
- **[—]** Списки — индексами; десять переменных на список — сигнал, что списку место не в конфигурации.
- **[39]** Отладочное представление: ключ, значение и провайдер. Нет ключа — `null`, не исключение. По ключу
  читает файл запуска, бизнес-логика — нет. В этом выводе будут секреты: только в разработке.

Шаг 2. Окружения

- **[40]** План раздела: шаг «окружения».
- **[41]** Окружение — строка в переменной: Development, Staging, Production. От неё зависят второй файл,
  поведение фреймворка, ваши развилки.
- **[—]** Локально имя задаёт файл настроек запуска с профилями; в опубликованное приложение он не попадает.
- **[42]** Разница — в значениях, а не в коде: адрес шлюза из конфигурации, в разработке там заглушка.
- **[43]** Вопрос: переменная не задана — кем приложение себя считает? Production: безопасное умолчание.
- **[—]** Стенд повторяет Production во всём, кроме адресов. Конфигурация в тестах — провайдер из словаря (Л15).
- **[44]** Переключатели: окружение, адреса Kestrel, уровень логов; `DOTNET_gcServer`,
  `DOTNET_GCHeapHardLimit`, `DOTNET_ThreadPool_MinThreads`, `DOTNET_TieredCompilation`,
  `DOTNET_ROLL_FORWARD`. `DOTNET_` читает рантайм до первой строки кода.
- **[—]** Не крутить ручки без измерения. Развёрнутый сервис ведёт себя иначе — сравните окружение, а не код.

Шаг 3. Один образ

- **[45]** План раздела: шаг «один образ».
- **[46]** Вопрос: один образ, стенд и Production с разными базами — что делать с файлом?
- **[47]** Образ один, среды разные, разница — в переменных. Секретов в образе нет.
- **[48]** Почему переменные: не требуют файловой системы, их задаёт всё, не попадают в образ. Файлы — для
  больших структур и секретов; переменные видно.
- **[49]** Вопрос: где хранить локальную строку подключения? Секреты пользователя.
- **[50]** `dotnet user-secrets`: файл в домашней папке, только в разработке; значение приходит из
  `secrets.json`. В `appsettings.json` — структура и безобидные умолчания.
- **[—]** Проверка: репозиторий станет публичным — что утечёт? Переменные рабочего окружения — в репозитории
  развёртывания. В конфигурации нет логики и выбора классов.
- **[51]** Мысль раздела: разница — в конфигурации; образ один, сверху — переменные.

## 3. Options pattern (10 мин · слайды 52–57)

- **[52]** Раздел: настройки — это тип, а не строка по ключу.
- **[53]** Класс настроек: свойства, умолчания, атрибуты, имя секции константой, единица в имени. Цепочка:
  `BindConfiguration`, `ValidateDataAnnotations`, `ValidateOnStart`. Потребитель получает через конструктор.
- **[—]** Конструктор без параметров, публичная запись, никакой логики, два уровня вложенности — предел.
- **[54]** `IOptions` — один раз, singleton; `IOptionsSnapshot` — на запрос, scoped; `IOptionsMonitor` — всегда
  актуальное, singleton. Перечитываются файлы, а не переменные окружения.
- **[—]** `Value` против `CurrentValue`; именованные настройки — имена константами.
- **[55]** Вопрос: при выкладке забыли адрес сервиса курсов — когда узнаете?
- **[56]** С `ValidateOnStart` — процесс не поднялся, трафик на старой версии. Без него — падает первый запрос
  за курсом. Настоящее сообщение об ошибке.
- **[—]** Проверка кодом — в той же цепочке; сообщение называет переменную, которую задать. В тесте — `IOptions`
  из готового объекта.
- **[57]** Мысль раздела: настройки — тип; проверяются на старте, пока ошибка ничего не стоит.

## 4. Исходящие HTTP-вызовы (15 мин · слайды 58–75)

- **[58]** Раздел: внешний сервис — это зависимость, как хранилище.
- **[59]** План раздела: проблема → фабрика и клиент → устойчивость.

Шаг 1. Проблема

- **[60]** Вопрос: HTTP-запрос из метода — что пишете? `new HttpClient` в `using`.
- **[61]** Клиент на каждый запрос: `HttpClient` держит обработчик, обработчик — пул соединений. Новый клиент —
  новый пустой пул; `Dispose` закрывает соединение. Пул, созданный на один запрос, ничего не переиспользует.
- **[62]** Что происходит с соединением: каждый запрос заново платит за DNS, TCP и TLS; закрытое соединение
  ещё минуту держит локальный порт (`TIME_WAIT`); портов около 28 тысяч — потолок примерно 470 новых
  соединений в секунду к одному адресу.
- **[63]** Проверим: 2000 запросов — 4,8 с и 1844 соединения в `TIME_WAIT` с клиентом на каждый запрос против
  2,0 с и одного соединения с общим клиентом. Настоящий вывод.
- **[—]** Когда порты кончаются, ошибка выглядит как сбой сети; `using` не помогает, а вредит.
- **[64]** Две ошибки: клиент на каждый запрос живёт слишком мало; один статический — слишком долго: DNS
  разрешён один раз, запросы идут на старый адрес. Клиент должен жить долго, но не вечно.
- **[—]** В утилите — время жизни соединения в пуле. Клиент рассчитан на одновременное использование.

Шаг 2. Фабрика и клиент

- **[65]** План раздела: шаг «фабрика и клиент».
- **[66]** Фабрика: лёгкие клиенты поверх пула обработчиков; обработчики заменяются раз в две минуты —
  соединения переоткрываются, DNS перечитывается. Именованные — строки, типизированные — класс.
- **[67]** Типизированный клиент: класс принимает `HttpClient` и умеет ходить в один внешний сервис;
  потребитель принимает его как обычную зависимость.
- **[68]** Регистрация: перегрузка `AddHttpClient` с контейнером берёт адрес и таймаут из проверенных
  `RatesOptions`; строковых ключей нет. Типизированный клиент — transient, в singleton его не держат.
- **[69]** Внутри клиента — адреса, заголовки, чужой DTO, превращение ошибок в свои исключения. Снаружи —
  логика; потребитель не знает про HTTP. Настройки JSON для чужого контракта — свои (Л9).

Шаг 3. Устойчивость

- **[70]** План раздела: шаг «устойчивость».
- **[71]** Три инструмента: таймаут — не ждать вечно (по умолчанию сто секунд); повтор — только идемпотентное
  (Л7); выключатель — отказывать сразу, пока сосед лежит.
- **[—]** Таймаут — тот же `CancellationToken` (Л6). Через все слои идёт токен запроса.
- **[72]** Вопрос: сколько раз повторять? «Пока не получится» — шторм повторов.
- **[73]** Стандартный набор: таймаутов два — на попытку и на операцию; попыток немного, пауза растёт,
  разброс случайный. По умолчанию повторяет и `POST`: для неидемпотентных вызовов повторы отключают явно.
  Начинайте с умолчаний.
- **[74]** Когда сосед лежит: курс — из кэша с пометкой (Л12), платёж — честная 503. Решение принимает сервис,
  заранее. Исходящие вызовы видны в логе: длительность и статус.
- **[—]** Заголовок трассировки добавится в Л12. Тест клиента — подменённый нижний обработчик (Л15).
- **[—]** Итог лекции и анонс лабораторной звучат голосом перед последним кадром.
- **[75]** Мысль раздела: `HttpClient` выдаёт фабрика; повторять можно только безопасное.

## Открытые вопросы

Авторское решение, не менять по умолчанию:

1. **Порядок разделов — DI → конфигурация → options → HTTP.** Четвёртый раздел собирает первые три:
   типизированный клиент регистрируется из `RatesOptions`, поэтому options идут до HTTP.
2. **Раздел DI идёт в четыре шага: идея → схема → времена жизни → код.** До кадра 22 в разделе нет ни одного
