# Л10. DI, исходящие вызовы и конфигурация — тезисы

**Длительность:** 80 минут
**Цель:** показать, как приложение собирается из частей и настраивается снаружи.
**Полный текст лекции:** [L10-di-and-configuration.md](L10-di-and-configuration.md)
**Слайды:** [slides/L10-di-and-configuration-slides.tex](slides/L10-di-and-configuration-slides.tex) —
59 кадров, один на каждый `[СЛАЙД n — …]` в сценарии.

Лекция про то, что решается снаружи сервиса: из чего он состоит и где он работает. Раздел 1 — внедрение
зависимостей: composition root, контейнер, времена жизни и их аварии, несколько реализаций, service locator,
модули регистрации. Раздел 2 — исходящие HTTP-вызовы: две ошибки с `HttpClient`, фабрика, типизированный клиент,
устойчивость. Раздел 3 — конфигурация: слои источников, окружения, переключатели рантайма, один образ и
переменные окружения, секреты пользователя. Раздел 4 — options pattern: класс настроек, три интерфейса,
проверка на старте.

тезис идёт голосом. Кадры с вопросом в зал — **[3]**, **[11]**, **[14]**, **[21]**, **[22]**, **[27]**, **[33]**,

## Сквозные тезисы

- Сервис не должен знать, из чего он состоит и где он работает: это решается снаружи.
- Конструктор — единственная честная точка входа зависимостей.
- Времена жизни — контракт с контейнером; его нарушение — пленённые зависимости и общее состояние.
- Внешний сервис — зависимость, как хранилище: типизированный клиент приходит в конструктор.
- Повторять можно только то, что безопасно повторить.
- Разница между окружениями живёт в значениях конфигурации, а не в коде. Позднее перекрывает раннее.
- Образ один, сред много: верхний слой — переменные окружения.
- Настройки — тип, а не строка по ключу, и проверяются на старте.

## 1. Внедрение зависимостей (30 мин · слайды 2–25)

- **[2]** Раздел: сервис не знает, из чего он состоит.
- **[—]** Две лекции звучало «фреймворк подставит из контейнера»; сегодня — что это значит.
- **[3]** Вопрос: сервису нужно хранилище — что в конструкторе? «`new`» — так пишут первые несколько лет.
- **[4]** Было: `new` конкретного класса со строкой подключения. Сервис прибит к SQL-хранилищу, смена базы —
  пересборка, тест требует базу, у десяти сервисов десять экземпляров.
- **[5]** Три слова: инверсия управления — принцип, внедрение зависимостей — способ, контейнер — инструмент.
  Пять классов собирают руками в `Main`.
- **[6]** Стало: класс объявляет интерфейс в конструкторе; composition root — единственное место, где виден
  состав, до `Build`.
- **[7]** Формы регистрации: интерфейс и реализация, только реализация, готовый экземпляр, фабрика, `TryAdd`.
  Почти всегда хватает первых двух.
- **[—]** Контейнер умеет две вещи: регистрировать (правило в списке `Services`) и разрешать.
- **[8]** Разрешение — дерево по конструкторам: строит сверху вниз, создаёт снизу вверх. План создания
  кэшируется: микросекунды. Разрешение вызывает фреймворк.
- **[9]** Конструктор не делает работу: берёт зависимости и кладёт в поля. Соединения, файлы, сеть, потоки —
  в явном асинхронном методе или фоновом сервисе (Л8).
- **[10]** Конструктор — единственная честная точка входа зависимостей.
- **[—]** Отсюда тестируемость и проверка графа при `Build` в разработке: «забыли зарегистрировать» ловится
  на старте. Аналогия — сборка мебели по инструкции.
- **[—]** Встроенный контейнер умеет только конструкторы — это дисциплина. Конструктор с семью параметрами —
  подсказка о дизайне: класс делает семь дел.
- **[11]** Вопрос: зачем интерфейс, если реализация одна? Для тестов — и как граница (Л3). Для класса без
  внешних зависимостей интерфейс — шум.
- **[12]** Времена жизни: singleton — один на приложение; scoped — один на запрос; transient — новый на каждое
  разрешение. Создаются лениво.
- **[13]** Контейнер владеет тем, что создал: scoped и transient освобождаются с областью, singleton — при
  остановке; асинхронное освобождение — тоже. Пришло через конструктор — вы не владелец (Л6).
- **[14]** Вопрос: singleton принимает scoped — что произойдёт?
- **[15]** Captive dependency: singleton держит scoped дольше, чем тот живёт. Настоящее сообщение контейнера.
  Проверка — только в Development.
- **[—]** Авария 2: изменяемый singleton — тысяча потоков пишут в один словарь (Л5).
- **[16]** Как выбрать: нет изменяемого состояния — singleton; состояние запроса — scoped, ничьё — transient;
  держит ресурс — scoped. Хоть одна зависимость scoped — объект scoped.
- **[17]** Пять аварий: singleton держит scoped; изменяемый singleton; контекст базы не той длительности;
  transient из корня; `Dispose` чужого.
- **[18]** Несколько реализаций: `IEnumerable<T>` — все, в порядке регистрации; декоратор — обёртка снаружи;
  открытые обобщения — одна регистрация на семейство.
- **[19]** Сервисы с ключом: ключ при регистрации, `[FromKeyedServices]` на параметре. Ключ-перечисление
  безопаснее строки.
- **[—]** Раньше — фабрика со `switch` по имени. Ключами различают и экземпляры одной реализации.
- **[20]** Service locator: `IServiceProvider` в конструкторе прячет граф, переносит ошибку на первый вызов,
  ломает тесты и проверку времён жизни. Законен на границе.
- **[—]** Промежуточная форма — фабрика-делегат в конструкторе: один поименованный способ создать одну вещь.
- **[21]** Вопрос: кто писал статический класс, который ходит в базу или читает время? Это зависимость,
  которой нет ни в одном конструкторе.
- **[22]** Вопрос: сто строк с `Add` — что делать? Методы расширения (Л5).
- **[23]** Модули: метод расширения `Add…` на модуль, возвращает коллекцию; файл запуска читается как
  оглавление. Так устроена и стандартная библиотека.
- **[24]** Явные модули против сканирования сборки: модуль регистрирует только своё, порядок вызовов не важен.
  Composition root проверяют тестом (Л15).
- **[—]** Куда копать: книга Симана и ван Дёрсена; сторонние контейнеры в старых проектах.
- **[25]** Мысль раздела: состав — в одном месте, зависимости — в конструкторе, времена жизни — контракт.

## 2. Исходящие HTTP-вызовы (15 мин · слайды 26–36)

- **[26]** Раздел: внешний сервис — это зависимость, как хранилище.
- **[27]** Вопрос: HTTP-запрос из метода — что пишете? `new HttpClient` в `using`.
- **[28]** Две ошибки: клиент на каждый вызов — закрытые соединения копятся, сокеты кончаются; один
  статический — DNS разрешён один раз, ходим на старый адрес.
- **[—]** Диагностика: сотни соединений в ожидании закрытия; рост дескрипторов в счётчиках (Л2). В утилите —
  время жизни соединения в пуле. Клиент рассчитан на одновременное использование.
- **[29]** Фабрика: лёгкие клиенты поверх пула обработчиков; обработчики заменяются раз в пару минут —
  соединения переоткрываются, DNS перечитывается. Именованные — строки, типизированные — класс.
- **[30]** Типизированный клиент: класс принимает `HttpClient`, регистрация задаёт адрес, таймаут и
  устойчивость, потребитель принимает класс как обычную зависимость.
- **[—]** Настройки JSON для чужого контракта — свои (Л9). Адрес пока по ключу; раздел 4 это исправит.
- **[31]** Внутри клиента — адреса, заголовки, чужой DTO, превращение ошибок в свои исключения. Снаружи —
  логика; потребитель не знает про HTTP.
- **[32]** Три инструмента: таймаут — не ждать вечно; повтор — только идемпотентное; выключатель — падать
  быстро, пока сосед лежит.
- **[—]** Таймаут — тот же `CancellationToken` (Л6). Через все слои идёт токен запроса.
- **[33]** Вопрос: сколько раз повторять? «Пока не получится» — шторм повторов.
- **[34]** Стандартный набор: таймаутов два — на попытку и на операцию; попыток немного, пауза растёт,
  разброс случайный. Начинайте с умолчаний.
- **[—]** `GET` повторяется безопасно, `POST` — только с ключом идемпотентности (Л7). Выключатель считает
  ошибки и пробует один запрос через время.
- **[35]** Когда сосед лежит: курс — из кэша с пометкой (Л12), платёж — честная 503. Решение принимает сервис,
  заранее. Исходящие вызовы видны в логе: длительность и статус.
- **[—]** Заголовок трассировки добавится в Л12. Тест клиента — подменённый нижний обработчик (Л15).
- **[36]** Мысль раздела: `HttpClient` выдаёт фабрика; повторять можно только безопасное.

## 3. Конфигурация и окружение (25 мин · слайды 37–52)

- **[37]** Раздел: код один, окружений много; разница живёт снаружи.
- **[38]** Вопрос: что в первом листинге исправили не до конца? Строка подключения. Composition root знает
  состав, но не должен знать, где работает.
- **[39]** Конфигурация — адреса, лимиты, уровни логов, переключатели. Бизнес-правила — код. Граница: значение
  может поменять администратор.
- **[40]** Слои: `appsettings.json` → файл окружения → секреты пользователя → переменные окружения →
  аргументы; в проде сверху хранилище секретов. Позднее перекрывает раннее.
- **[—]** Секция `ConnectionStrings` — соглашение, которое понимает всё вокруг. Провайдеры — плоские пары
  «ключ — значение»; ключи без учёта регистра; файлы отслеживаются.
- **[41]** Три записи одного ключа: вложенный JSON, `Rates__TimeoutSeconds`, `--Rates:TimeoutSeconds=2`.
- **[—]** Списки — индексами; десять переменных на список — сигнал, что списку место не в конфигурации.
- **[42]** Отладочное представление: ключ, значение и провайдер. Нет ключа — `null`, не исключение. По ключу
  читает файл запуска, бизнес-логика — нет. Секреты в этом выводе — в прод никогда.
- **[43]** Окружение — строка в переменной: второй файл, поведение фреймворка, ваши развилки.
- **[—]** Локально имя задаёт файл настроек запуска с профилями; в опубликованное приложение он не попадает.
- **[44]** Разница — в значениях, а не в коде: адрес шлюза из конфигурации, в разработке там заглушка.
- **[45]** Вопрос: переменная не задана — кем приложение себя считает? Продом: безопасное умолчание.
- **[—]** Стенд похож на прод во всём, кроме адресов. Конфигурация в тестах — провайдер из словаря (Л15).
- **[46]** Переключатели: окружение, адреса Kestrel, уровень логов; `DOTNET_gcServer`,
  `DOTNET_GCHeapHardLimit`, `DOTNET_ThreadPool_MinThreads`, `DOTNET_TieredCompilation`,
  `DOTNET_ROLL_FORWARD`. `DOTNET_` читает рантайм до первой строки кода.
- **[—]** Не крутить ручки без измерения. Сервис в проде ведёт себя иначе — сравните окружение, а не код.
- **[47]** Вопрос: один образ, стенд и прод с разными базами — что делать с файлом?
- **[48]** Образ один, среды разные, разница — в переменных. Секретов в образе нет.
- **[49]** Почему переменные: не требуют файловой системы, их задаёт всё, не попадают в образ. Файлы — для
  больших структур и секретов; переменные видно.
- **[50]** Вопрос: где хранить локальную строку подключения? Секреты пользователя.
- **[51]** `dotnet user-secrets`: файл в домашней папке, только в разработке; значение приходит из
  `secrets.json`. В `appsettings.json` — структура и безобидные умолчания.
- **[—]** Проверка: репозиторий станет публичным — что утечёт? Переменные прода — в репозитории развёртывания.
  В конфигурации нет логики и выбора классов.
- **[52]** Мысль раздела: разница — в конфигурации; образ один, сверху — переменные.

## 4. Options pattern (10 мин · слайды 53–59)

- **[53]** Раздел: настройки — это тип, а не строка по ключу.
- **[54]** Класс настроек: свойства, умолчания, атрибуты, имя секции константой, единица в имени. Цепочка:
  `BindConfiguration`, `ValidateDataAnnotations`, `ValidateOnStart`. Потребитель получает через конструктор.
- **[—]** Конструктор без параметров, публичная запись, никакой логики, два уровня вложенности — предел.
- **[55]** `IOptions` — один раз, singleton; `IOptionsSnapshot` — на запрос, scoped; `IOptionsMonitor` — всегда
  актуальное, singleton. Перечитываются файлы, а не переменные окружения.
- **[—]** `Value` против `CurrentValue`; именованные настройки — имена константами.
- **[56]** Клиент из настроек: перегрузка `AddHttpClient` с контейнером берёт адрес и таймаут из
  `RatesOptions`. Строковых ключей нет.
- **[57]** Вопрос: забыли адрес курсов в проде — когда узнаете?
- **[58]** С `ValidateOnStart` — процесс не поднялся, трафик на старой версии. Без него — падает первый запрос
  за курсом. Настоящее сообщение об ошибке.
- **[—]** Проверка кодом — в той же цепочке; сообщение называет переменную, которую задать. В тесте — `IOptions`
  из готового объекта.
- **[—]** Итог лекции и анонс лабораторной звучат голосом перед последним кадром.
- **[59]** Мысль раздела: настройки — тип; проверяются на старте, пока ошибка ничего не стоит.

## Открытые вопросы

Авторское решение, не менять по умолчанию:

1. **Двенадцать кадров-вопросов** — по одному на каждый `[ВОПРОС В ЗАЛ]` сценария. Если колоду сокращать,
   первые кандидаты — 21 и 38; маркер в сценарии тогда снимается вместе с кадром.
2. **Последний кадр — мысль раздела 4**, после итога лекции и анонса лабораторной: так абзацы стоят в сценарии,
   порядок не менялся.
3. **Кадр 41: `dotnet HelloWorld.dll`**, в листинге сценария — `OrdersService.dll`. На слайде имя учебного
   проекта курса, потому что вывод кадра 42 снят с него.
4. **Листинги кадров 7 и 18 собраны по словам сценария** — в сценарии формы регистрации, перечисление
   реализаций, декоратор и открытые обобщения описаны без кода.
5. **Порядок стратегий на кадре 34** (общий таймаут → повтор → выключатель → таймаут попытки) — по документации
   стандартного набора; запуском наблюдались только повторы.
