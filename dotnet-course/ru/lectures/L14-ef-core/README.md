## Сквозные тезисы

- EF Core — генератор кода, который вы обязаны проверять: ORM пишет SQL за вас, но не вместо вас.
- Сущность — обычный класс без атрибутов; всё про базу — в классе конфигурации, по одному на сущность.
- Всё, что важно, задаётся явно, даже если соглашение сделало бы то же самое.
- Контекст — наборы плюс подключение конфигураций; scoped, один на запрос.
- Миграция выводится из модели, не знает провайдера и применяется отдельным шагом до выкладки.
- Читаете, чтобы показать, — проецируйте в DTO в запросе; сущность загружают, чтобы её менять.
- Смотрите сгенерированный SQL после каждого нового запроса.
- ORM — генератор SQL и маппинга, а не архитектура.

## 1. Место EF Core в приложении (5 мин · слайды 2–6)

- **[2]** Раздел: генератор кода, который вы обязаны проверять.
- **[—]** В прошлый раз доступ к данным писали руками: механика маппинга, дублирование запросов, разрыв между
  схемой и типами. EF Core закрывает эти три боли.
- **[3]** Вопрос: что EF Core берёт на себя? Маппинг, SQL из LINQ, отслеживание изменений, миграции.
- **[4]** Чем не является: не кэш (объект живёт в контексте один запрос), не проектирование базы, не причина
  не знать SQL.
- **[5]** Берёт на себя четыре вещи; требует взамен понимать получившийся SQL и не считать базу деталью
  реализации. ORM пишет SQL за вас, но не вместо вас.
- **[—]** Пользуйтесь как компилятором из Л1: доверяйте, но читайте. Компилятор проверяли тысячи людей
  двадцать лет, ваш запрос — никто, кроме вас.
- **[6]** Доверять: создание, чтение по ключу, обновление одной сущности, удаление. Проверять каждый раз:
  связи, группировки, проекции с вычислениями, больше одного оператора после `Where`. Ядро общее, провайдер
  для PostgreSQL — поверх Npgsql.
- **[—]** Старый Entity Framework 6 — другая архитектура, встретится в наследии. Версия EF Core идёт вместе
  с версией платформы.
- **[—]** Лабораторная построена на сравнении SQL из Л13 со сгенерированным. Мысль раздела: EF Core закрывает
  три боли и требует смотреть на SQL.

## 2. Модель и её конфигурация (20 мин · слайды 7–21)

- **[7]** Раздел: сущность — обычный класс; всё про базу — в отдельном классе конфигурации.
- **[8]** Три слова: сущность (класс на таблицу, идентичность по ключу), DTO (уходит клиенту), доменная модель.
  Сущность ORM и доменная сущность в курсе — один класс; DTO — всегда отдельный тип.
- **[9]** Атрибуты или класс конфигурации: с атрибутами домен ссылается на пакет ORM, они мешают второму
  хранилищу и тесту домена, цена видна не сразу. Правило принимают заранее.
- **[10]** Сущность `Order`: закрытая запись, закрытый конструктор для ORM, публичный для домена, `MarkPaid`
  с правилом перехода. Ни слова про базу.
- **[11]** `OrderConfiguration`: таблица и ключ, точность суммы, статус строкой, конвертер `Email`, индекс,
  связь один ко многим с каскадом.
- **[—]** `Email` — record struct из Л3, `InvalidTransitionException` — из Л4. Закрытый конструктор ORM
  вызывать умеет.
- **[—]** Почему не один метод в контексте: конфигурация растёт — двадцать сущностей, пятьсот строк, которые
  никто не читает. Класс на сущность подхватывается из сборки одной строкой.
- **[12]** Соглашения: `Id` — ключ, `OrderId` — внешний ключ, тип без `?` — `NOT NULL`, `decimal` и `string`
  — умолчания базы. Важное задаём явно: соглашения невидимы.
- **[13]** Теневые свойства (дата изменения: есть в таблице, нет в классе, заполняет перехватчик сохранения)
  и глобальный фильтр запросов (мягкое удаление, арендатор); отключается на одном запросе явно.
- **[—]** Типы: сумма без точности теряет копейки, строка без длины не индексируется, дата — с поясом или
  без по провайдеру. Значения по умолчанию и вычисляемые колонки — тоже в конфигурации.
- **[14]** Владеемый тип: `Money` из суммы и валюты — две колонки той же таблицы с префиксом, одно свойство
  в коде.
- **[15]** Имена: по умолчанию — как в классе, в PostgreSQL это кавычки вокруг каждого имени; змеиный регистр
  — одной строкой на всю модель.
- **[—]** Исключения из имён — явно и только в конфигурации. Обязательность — из аннотаций `null` (Л4);
  уникальность, индексы и ограничения-проверки — явно.
- **[16]** Ключ: автоинкремент (известен после вставки), последовательность, на клиенте (известен до
  сохранения, не раскрывает количество, хуже для индекса). В курсе — автоинкремент.
- **[—]** Составные ключи усложняют всё: суррогатный ключ из одной колонки, естественная уникальность —
  отдельным уникальным индексом.
- **[17]** Три связи: 1:1 — ключ одной является внешним ключом на другую; 1:many — внешний ключ в таблице
  «многих»; many:many — промежуточная таблица.
- **[—]** Наследование сущностей — три способа и у всех оговорки; в курсе — композиция. Промежуточная таблица
  с данными становится сущностью.
- **[18]** Один ко многим: коллекция у заказа, обратной навигации нет, `int` без `?` — связь обязательна,
  каскад осознанный. Удалили покупателя — ушла история заказов. Навигация «на всякий случай» — цикл.
- **[19]** Вопрос: почта — тип, колонка — текст; что делать? Сказать ORM, как превращать одно в другое.
- **[20]** Конвертер: две лямбды; запрос с равенством по `Email` переводится в `WHERE o.customer_email =
  @email`. Операция внутри значения по доменному типу не переводится.
- **[—]** Так же — перечисления строками, идентификаторы-обёртки: «никаких строк вместо типов» доезжает до базы.
- **[21]** Мысль раздела: сущность без атрибутов, конфигурация по одной на сущность.

## 3. DbContext (10 мин · слайды 22–28)

- **[22]** Раздел: сессия работы с базой на один запрос, и ничего больше.
- **[23]** Контекст целиком: `DbSet` на таблицу, `ApplyConfigurationsFromAssembly`, параметры через
  конструктор; регистрация `AddDbContext` — scoped, `UseNpgsql`, змеиный регистр. Единица работы: одна
  транзакция одним вызовом.
- **[—]** Подробные ошибки и значения параметров в логе — только в разработке; развилка живёт в модуле
  регистрации.
- **[24]** Чего в контексте нет: бизнес-логики, запросов, конфигураций. Тонкое хранилище с методами по
  сценариям прячет ORM от домена; обобщённое «хранилище чего угодно» с лямбдой — ORM через заднюю дверь.
- **[25]** Вопрос: почему не singleton? Одно соединение на всех, отслеживаемые объекты копятся вечно, контекст
  не потокобезопасен.
- **[26]** Время жизни: singleton и transient — нет, scoped — один на запрос. Контекст не дорогой: дорогая
  модель, она строится один раз. Где запроса нет — область на итерацию или фабрика контекстов.
- **[—]** Контекст на вызов метода — единица работы распадается. `WhenAll` с двумя запросами через один
  контекст — исключение. Пул контекстов — для очень горячих сервисов. Один контекст на сервис; два — только
  для независимых областей.
- **[27]** Раскладка `OrdersService.Data`: контекст, `Configurations/`, `Migrations/`, `Repositories/`,
  `DataModule.cs`. Три проекта, ссылки в одну сторону.
- **[—]** Проект тестов (Л15) применяет все миграции к пустой базе в контейнере — рассинхронизация ловится
  до выкладки.
- **[28]** Мысль раздела: наборы плюс подключение конфигураций, scoped, один на запрос.

## 4. Миграции (15 мин · слайды 29–39)

- **[29]** Раздел: схема как код — изменение базы живёт рядом с изменением модели.
- **[30]** Устройство: модель сравнивается со снимком, разница — класс миграции с `Up` и `Down`, в базе
  таблица истории. Класс и снимок коммитятся вместе с сущностью; снимок руками не редактируют, конфликт при
  слиянии — пересоздать последнюю миграцию.
- **[—]** Что получаете: история схемы в репозитории с ревью, одинаковая схема на всех стендах, связь с моделью.
- **[31]** Рабочий цикл: `migrations add`, `migrations list` с пометкой `(Pending)`, сгенерированный
  `CreateIndex`. Изменили — добавили — прочитали — применили. Применённую миграцию не редактируют.
- **[—]** `Down` в проде используют редко: чаще новая миграция. Справочные данные — миграцией или шагом
  заполнения; тестовые данные в миграции не кладут. Сотни миграций сворачивают в одну осторожно.
- **[32]** Что здесь не так? Миграция `AddOrderArchive`: тип `jsonb` строкой и сырой SQL с диалектом.
- **[33]** Три ошибки: тип одной базы строкой; сырой SQL — диалект и мимо снимка; `CREATE INDEX CONCURRENTLY`
  нельзя в транзакции — миграция падает и на PostgreSQL (ошибка `25001` на слайде).
- **[—]** Почему правило: тесты на другой базе; миграция — описание модели; сырой SQL не участвует в снимке.
  Диалект неизбежен — ветвление по имени активного провайдера.
- **[34]** Как правильно: тип и индекс — в конфигурации, миграция выводится из модели. Сырой SQL — только
  для того, чего построитель не умеет, по стандарту. Тяжёлое заполнение — фоновая задача после выкладки.
- **[35]** Вопрос: приложение само применяет миграции на старте — что не так? Два экземпляра.
- **[36]** Шаг поставки: один раз, до выкладки, из конвейера, скриптом или исполняемым файлом, ролью с правом
  на схему. На старте: две попытки, падение или удвоение данных, права на схему у приложения.
- **[—]** Две роли в базе: для миграций и для приложения. Ошибка в коде физически не может уронить таблицу.
- **[37]** `migrations script --idempotent`: каждая команда под проверкой таблицы истории. Скрипт можно
  прочитать; `migrations bundle` — без исходников и SDK; `has-pending-model-changes` ловит забытую миграцию.
- **[—]** Вторая проверка в конвейере: применить все миграции к пустой базе в контейнере.
- **[38]** Выкладка без остановки: добавленная колонка не ломает старый код; новая обязательная — три шага;
  переименование — четыре шага и две выкладки; удаление — две выкладки. Инструмент об этом не знает.
- **[—]** Тяжёлые миграции прогоняют на обезличенной копии прода.
- **[39]** Мысль раздела: миграция выводится из модели, не знает провайдера, применяется до выкладки.

## 5. Запросы и загрузка данных (15 мин · слайды 40–50)

- **[40]** Раздел: чтение — девяносто процентов работы с базой и сто процентов сюрпризов.
- **[41]** Три способа: eager (`Include`, вместе), explicit (потом, отдельным вызовом), lazy (сама, при
  обращении — N+1). `Include` умеет вложенность и фильтр.
- **[42]** Вопрос: сто заказов, цикл по позициям, ленивая загрузка — сколько запросов? Сто один.
- **[43]** N+1: обращение к свойству выглядит как чтение поля. Счётчик команд: 101 при ленивой загрузке,
  1 с `Include`. На дашборде — гребёнка. Ленивую загрузку в сервисе не включать.
- **[—]** Тест (Л15) может считать команды: больше трёх на список — красный.
- **[44]** Две коллекции в `Include` — декартово произведение: 10 позиций и 5 тегов — 50 строк на заказ.
  `AsSplitQuery` — по запросу на коллекцию.
- **[—]** Явная загрузка: заказ для проверки прав (Л11), позиции — только если нужны.
- **[45]** Проекция: было — `Include`, всё отслеживается, DTO в памяти; стало — `Select` в DTO в запросе.
- **[46]** Два SQL: все колонки и `LEFT JOIN` против двух колонок и подзапроса с `count`.
- **[—]** Проекция ходит через связи. DTO живёт в проекте контракта, проекция — в хранилище. Сервису,
  который в основном читает, — отслеживание выключено по умолчанию.
- **[47]** Читаем без отслеживания: `AsNoTracking`, однозначная сортировка, `AsAsyncEnumerable`, токен отмены
  в каждом вызове. Без отслеживания нет тождественности: одна строка — два объекта.
- **[48]** Вопрос: «найти по ключу» против «первый, у кого идентификатор равен». Первый сначала смотрит в
  отслеживатель.
- **[—]** В тестах чтения после записи напрямую в базу — свежий контекст или запрос без отслеживания.
- **[49]** Три способа увидеть SQL: лог категории команд на уровне `Information`, `ToQueryString()`, дашборд
  из Л12. Значения параметров — только в разработке. SQL верный, а запрос медленный — это план.
- **[—]** Предупреждения провайдера читать как предупреждения компилятора. Группировка: агрегат — в базе,
  элементы групп — в памяти. Страницы — `Skip`/`Take` или курсор; сортировка однозначная, вторым ключом —
  идентификатор.
- **[50]** Мысль раздела: проекция в DTO, сущности — для изменения, SQL — после каждого нового запроса.

## 6. Правила, грабли и альтернативы (15 мин · слайды 51–59)

- **[51]** Раздел: шесть тем о том, где ORM начинает мешать.
- **[52]** Отслеживание: состояние живёт между строчками кода — чужое сохранение, изменение снаружи,
  несохранённое изменение неотслеживаемого. Изменение и сохранение — в одном методе. Меняют методом
  сущности; record — для DTO.
- **[—]** Цена в процессоре: сравнение со снимком на тысячах объектов. Хранилище не возвращает отслеживаемые
  сущности наружу.
- **[53]** Транзакции и гонки: токен параллелизма — `UPDATE … WHERE id = @p1 AND xmin = @p2`; не сработало —
  исключение параллелизма и 409. Сохранение — одна транзакция; несколько сохранений — транзакция явно.
  Уровень изоляции — по сценарию.
- **[—]** Чтение зафиксированного по умолчанию; сериализуемый — блокировки и обязательные повторы.
  Распределённых транзакций избегают: таблица исходящих сообщений. Нарушение уникальности — 409 в одном
  обработчике ошибок.
- **[54]** Массовые операции: было — N объектов и N команд; стало — `ExecuteUpdateAsync`, один `UPDATE …
  WHERE`. Идёт мимо отслеживателя. `EnableRetryOnFailure` — повтор при временной ошибке.
- **[—]** Повтор — повтор всего сохранения: уникальный индекс или ключ идемпотентности (Л7). Явная
  транзакция повторяется целиком. Вставка тысячи объектов — пакетами.
- **[55]** AOT: модель компилируется заранее; запрос предкомпилируется, только если написан в одном месте
  (экспериментально). Запрос из необязательных фильтров — только при выполнении. Пишите запросы просто.
- **[—]** Готовность к AOT проверяется свойством публикации и анализатором обрезки. Компилируемые запросы —
  для горячего пути, мерить.
- **[56]** «ORM превращает объекты в мешки данных, а поведение уезжает в сервисы» — Егор Бугаенко,
  «ORM Is an Offensive Anti-Pattern».
- **[57]** Что делать: чтение — проекции в DTO без сущностей; запись — загрузить агрегат, вызвать метод с
  правилом, сохранить рядом. Границы агрегата — границы транзакции. ORM — генератор, а не архитектура.
- **[58]** Альтернативы: Dapper — вы пишете SQL, он делает маппинг (отчёты, аналитика); linq2db — LINQ ближе
  к SQL, без отслеживания. Часто вместе с EF Core; все работают через один драйвер.
- **[—]** Как выбрать: мало простых запросов — EF Core; сложные отчёты — плюс Dapper; команда живёт в SQL —
  Dapper или linq2db; AOT — минимум динамики.
- **[59]** Мысль раздела: меняйте и сохраняйте рядом, массовое — одной командой, запросы — просто; ORM —
  генератор, а не архитектура.
- **[—]** Дальше (Л15) — тесты: то, что отличает работающий код от кода, про который известно, что он работает.
