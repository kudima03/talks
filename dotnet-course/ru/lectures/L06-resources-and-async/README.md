# Л6. Ресурсы, файлы и асинхронность — тезисы

**Длительность:** 80 минут
**Цель:** научить владеть ресурсом и объяснить, почему сервер обязан быть асинхронным.
**Полный текст лекции:** [L06-resources-and-async.md](L06-resources-and-async.md)
**Слайды:** [slides/L06-resources-and-async-slides.tex](slides/L06-resources-and-async-slides.tex) —
55 кадров, один на каждый `[СЛАЙД n — …]` в сценарии.

Лекция — две половины одного правила: рантайм не управляет ни ресурсами операционной системы, ни вашим
временем ожидания, и то и другое ваша забота. Раздел 1 — ресурс: что такое unmanaged, как его освобождает
владелец (`IDisposable`, `using`), как устроены файлы и пути. Раздел 2 — ожидание: почему поток не должен
ждать, что на самом деле делает `await`, как ждать несколько вещей, как остановить и какие грабли ломают
всё это под нагрузкой.

## Как читать

Число в начале тезиса — кадр, на котором он живёт: **[7]**. Прочерк **[—]** значит, что кадра нет и
тезис идёт голосом. Кадры с вопросом в зал — **[4]**, **[25]**, **[30]**, **[41]**, **[48]**: на слайде
только вопрос, ответ звучит вслух.

## Сквозные тезисы

- Сборщик мусора убирает память, а не ресурсы. За всё, что принадлежит ОС, отвечает владелец, и явно.
- Ресурс освобождает владелец, **один раз**, **детерминированно**, через `using`. Всё остальное — «когда-нибудь».
- Асинхронность — не «быстрее», а «не занимать поток ожиданием». Один запрос она не ускоряет, она
  увеличивает число запросов, которые сервер держит на том же железе.
- У асинхронного метода нет своего потока. Он выполняется кусками, и каждый кусок — тот поток, что свободен.
- `await` — не ожидание, а регистрация продолжения и возврат. Между кусками метода потока нет вообще.
- Ввод-вывод — асинхронно, через `await`. Вычисления — параллельно, если можно разрезать, и синхронно, если нельзя.
- Не блокируй поток: заблокированный поток пула — потерянный, и под нагрузкой это голодание пула.

## 1. Владение ресурсом (30 мин · слайды 2–23)

- **[2–3]** Пять подтем: managed/unmanaged, `IDisposable` и `using`, три уровня работы с файлом, пути,
  финализаторы.
- **[4]** Вопрос: файл не закрыли, объект собрали — файл закрыт? Верный ответ «когда-нибудь», и это худший
  из трёх.
- **[5]** Managed — объекты в куче, GC видит. Unmanaged — дескриптор, сокет, соединение с БД — GC не видит.
  Для GC `FileStream` — несколько десятков байт с числом внутри.
- **[—]** Пока не сказали «закрой», файл открыт и заблокирован для других; у процесса есть предел дескрипторов.
  Та же история: соединение с БД не вернулось в пул, сокет остался в ОС.
- **[6]** `IDisposable`: один метод, договор «я закончил, освободи». `FileStream` закрывает дескриптор,
  `StreamReader` — свой поток, соединение возвращается в пул, сокет закрывается.
- **[7]** `using` с блоком — старая форма: объект живёт до конца блока. Пример: поиск первой строки с `Hello!`.
- **[8]** `using` без блока — современная форма: объект живёт до конца области.
- **[—]** Пример заодно показывает, что чтение линейное: файл идёт подряд с начала и останавливается на
  первом совпадении.
- **[9]** Обе формы — `try / finally`: ресурс освобождён при любом исходе. `null` в `finally` не страшен.
- **[10]** Несколько `using` подряд освобождаются в обратном порядке: сначала `writer` (сбросил буфер в
  поток), потом `stream` (закрыл дескриптор). Перепутанный порядок — потерянный хвост файла.
- **[11]** Забытый `using`: `File.OpenWrite` без `Dispose`, и сразу `File.ReadAllText` того же пути —
  `IOException: …being used by another process`. «Другой процесс» — ваш собственный дескриптор двумя
  строками выше. `File.OpenWrite` открывает без совместного доступа, поэтому падает и на Linux.
- **[11]** Освобождение детерминированное, в этой строке. Сборщик — когда-нибудь.
- **[12]** Свой тип: `Dispose` идемпотентен (флаг), использование после `Dispose` — `ObjectDisposedException`.
  Финализатора нет; `sealed` убирает «полный паттерн Dispose».
- **[13]** Владеет тот, кто создал, — он и освобождает, ровно один раз. Передали снаружи — не владеете. Двое
  владельцев — двойное освобождение, ни одного — утечка.
- **[—]** `Dispose` не бросает исключений: он вызывается из `finally`, и второе исключение затрёт первое.
- **[14]** Уровень 1, `File.ReadAllText`: одна строка, сам открыл и закрыл. Нет верхней границы размера —
  не читаем целиком.
- **[—]** Кодировка: по умолчанию UTF-8; файл в национальной кодировке нужно читать с явной.
- **[15]** Уровень 2, `StreamReader`: буфер на блок, отдаёт строки; в памяти один блок и одна строка;
  гигабайтный файл — в постоянной памяти. Первый уровень, где нужен `using`.
- **[16]** Уровень 3, `FileStream`: байты, позиция, `FileMode`, `FileAccess`, `FileShare` — доступ к файлу
  задаётся явно. Совместное чтение — контракт с ОС, выбирайте сознательно.
- **[—]** Буферизация: запись копится и сбрасывается; упал до сброса — хвост потерян. `Dispose` сбрасывает.
- **[—]** `FileStream` — наследник `Stream`; `StreamReader` принимает любой `Stream`, поэтому тот же код
  читает тело HTTP-запроса. Потоки вкладываются, как операторы LINQ.
- **[17]** Путь собирает `Path.Combine` / `Join`, а не конкатенация: разделитель по платформе.
- **[18]** Сигнатуры `Path`: `Combine`, `Join`, `GetExtension`, `GetFileName`, `GetDirectoryName`. Не режьте
  путь руками. «Если файл есть, открыть» — гонка; открывайте и обрабатывайте исключение.
- **[19]** Относительный путь — от рабочей директории процесса, не от сборки: `dotnet run`, публикация и
  контейнер — три разных места. Абсолютный — от папки приложения или из конфигурации.
- **[19]** Регистр: Windows не различает, Linux различает — `Config.json` и `config.json` там два файла.
- **[20]** Приложение работает со своей папкой; записать что-то — во временную (`Path.GetTempPath()`). В
  контейнере папка приложения может быть только для чтения.
- **[—]** Имена файлов извне проверяются. Путь из пользовательского ввода может вести за пределы папки (`..`):
  сделать путь полным, проверить префикс, только потом открывать. Вернёмся в Л11.
- **[21]** Финализатор — метод с тильдой, вызывается сборщиком перед уборкой объекта. Так `FileStream`
  когда-нибудь закрывается.
- **[22]** Три причины не писать финализатор: недетерминированность, цена (лишняя сборка, дороже всегда),
  сложность (отдельный поток, соседи уже собраны). Сырой дескриптор — готовая обёртка из библиотеки.
- **[—]** При завершении процесса финализаторы не обещаны: незакрытый файл может потерять последние строки.
  Graceful shutdown вызывает `Dispose` только у того, что оформлено как `IDisposable`.
- **[23]** Мысль раздела: сборщик убирает память, а не ресурсы; ресурс освобождает владелец, один раз, через
  `using`.

## 2. Асинхронность (45 мин · слайды 24–55)

- **[24]** Поток — дорогой ресурс, и он не должен ждать.
- **[25]** Вопрос: что делает поток, пока запрос 50 мс в базе? Ждёт.
- **[26]** Ждать — значит быть заблокированным: стек и запись в ядре занять, ни одной инструкции не
  выполнить. 50 мс — десятки миллионов инструкций.
- **[—]** Тысяча запросов — тысяча потоков: мегабайт стека на каждый, переключения контекста, создание
  потока за миллисекунды. Это thread-per-request — потолок задолго до процессора и базы.
- **[27]** Тысяча потоков, все ждут, против восьми потоков и тысячи ожиданий в виде маленьких объектов.
- **[—]** Асинхронность не ускоряет один запрос: те же 50 мс. Она меняет, сколько запросов сервер держит
  одновременно. Узким местом остаётся то, что действительно медленное.
- **[28]** Синхронно — один поток, ждёт; асинхронно — потоков мало, никто не ждёт (ввод-вывод); параллельно —
  по числу ядер, все считают (вычисления).
- **[—]** Плохой код от путаницы: ввод-вывод в `Task.Run` (поток пула просто ждёт) и тяжёлое вычисление под
  `async` (всё тот же занятый поток).
- **[29]** Правило: ввод-вывод — асинхронно, через `await`; вычисления — параллельно, если можно разрезать, и
  синхронно, если нельзя.
- **[—]** Параллельный цикл и PLINQ занимают все ядра — под нагрузкой осторожно. Параллельное *ожидание* —
  не параллелизм, а композиция задач.
- **[30]** Вопрос: что такое `Task`?
- **[31]** `Task` — обещание: состояние, результат или исключение, список continuations. Не поток и не
  операция.
- **[32]** Источник 1, `Task.Run`: делегат в очередь пула; за задачей стоит поток; инструмент для вычислений.
- **[33]** Источник 2, ввод-вывод: библиотека просит ОС прочитать и сообщить; за задачей потока нет.
- **[—]** По типу `Task` не понять, стоит ли за ним поток; понять можно по тому, откуда задача пришла.
- **[34]** `Task.Delay` регистрирует таймер, поток свободен; `Thread.Sleep` блокирует поток. В сервисе —
  никогда второе.
- **[—]** `ValueTask` — структура, чтобы не аллоцировать, когда результат уже есть: `await` один раз; в
  своём коде возвращайте `Task`, пока измерение не скажет иное. `TaskCompletionSource` — мост от callback к
  задаче.
- **[35]** У асинхронного метода нет своего потока.
- **[36]** Пять `await` подряд: каждый — место, где метод может улететь в ожидание. Выглядит как
  последовательный код, по смыслу — callback.
- **[37]** Пять `await` режут метод на шесть кусков; номер куска — состояние; на каждом `await` метод
  запоминает, где остановился.
- **[38]** Исключение после `await` лежит в задаче и вылетает в строке `await` с сохранённой трассировкой.
  Цепочка разорвана — исключение так и лежит в задаче.
- **[39]** Четыре шага: компилятор строит state machine → на `await` проверка «завершена?» (да — идём дальше,
  нет — регистрируем продолжение и возвращаемся) → операция завершилась, продолжение в очередь пула →
  `MoveNext` продолжает с сохранённого состояния.
- **[—]** Очень часто задача уже завершена, и переключения нет вообще: из сотни `await` на буферизованном
  чтении приостанавливаются единицы.
- **[40]** Шаг 3: библиотека просит ОС, поток уходит в пул; уведомление принимает служебный поток рантайма,
  выставляет результат задаче, продолжение уходит в очередь пула. «There is no thread».
- **[41]** Вопрос: код до `await` шёл на потоке 5 — на каком пойдёт после? На любом.
- **[42]** Куски метода выполняются на разных потоках; метод начался на одном, закончится на другом.
- **[43]** Переживает `await`: локальные переменные (поля state machine в куче), `this`, `AsyncLocal`. Не
  переживает: данные, локальные для потока, `lock` (`await` внутри запрещён).
- **[—]** Побочный эффект: большой массив в локальной переменной живёт всё время ожидания. Нужен только до
  `await` — пусть его область закончится раньше.
- **[—]** `async` не отправляет метод в фон: до первого реально приостановившегося `await` он идёт синхронно
  на потоке вызывающего. Убрать вычисление с потока — `Task.Run`.
- **[44]** Thread pool: очередь элементов работы и потоки по числу ядер; добавляет новые потоки медленно, не
  отличая тяжёлую работу от заблокированных потоков.
- **[45]** Голодание пула: заблокированный поток выбыл, очередь продолжений растёт, выполнять некому. Не
  блокируй поток!
- **[—]** Симптом: задержки в секунды при простаивающем процессоре и быстрой базе; очередь пула растёт, потоки
  медленно ползут вверх. Ищите синхронное ожидание, а не оптимизируйте запросы.
- **[—]** Цена: метод без приостановки не аллоцирует; приостановившийся — одна state machine в куче и задача.
- **[46]** Сквозной пример в четырёх блоках: А идёт вниз → поток 3 свободен → база отвечает → А идёт вверх на
  потоке 7. Запрос А начался на потоке 3, закончился на потоке 7, в промежутке не занимал
  ни одного. Три раза «зарегистрировать и вернуться» вниз, три раза «продолжить» вверх.
- **[47]** `await` — не ожидание, а регистрация продолжения и возврат; между кусками потока нет вообще.
- **[48]** Вопрос: два независимых `await` по 50 мс подряд — сколько? Сто.
- **[49]** `Task.WhenAll`: задачи создаются до `await`, `await` один; 50 мс вместо 100, потоков не занимает.
  Но десять тысяч задач — десять тысяч одновременных запросов: параллелизм ограничивают.
- **[—]** `WhenAny` — гонка с таймером, но проигравшая задача не отменяется и её исключение никто не увидит;
  для таймаута есть готовый метод у задачи.
- **[50]** `CancellationToken`: три метода вызывают друг друга и передают токен последним параметром; нижний
  отдаёт его `File.ReadAllLinesAsync`. Забыли передать в одном звене — отмена там обрывается. Асинхронный
  метод принимает токен всегда.
- **[51]** Токен в своём цикле: `ThrowIfCancellationRequested` бросает, `IsCancellationRequested` спрашивает.
  Ввод-вывод прервётся сам, цикл — только если его спросить.
- **[—]** Отмена — исключение, его не глушат: оно долетает до границы. Механизм кооперативный. Источник —
  `IDisposable`. Таймаут плюс отмену запроса можно связать в один токен.
- **[52]** Файлы асинхронно: `using` читателю, `await using` писателю (сбрасывает буфер ожидаемо),
  `ReadLineAsync(ct)`, `WriteLineAsync(line.AsMemory(), ct)` — `Memory`, потому что `Span` не пронести через
  `await`.
- **[—]** `ReadLine` без `Async` внутри асинхронного метода компилируется и блокирует поток на каждой строке;
  глазами не видно, анализатор видит. Библиотека без асинхронного API — не решается `Task.Run`.
- **[53]** `IAsyncEnumerable` + `await foreach`: элементы появляются по мере запроса, в памяти одна строка.
  Атрибут `[EnumeratorCancellation]` доставляет токен из `await foreach` в тело метода. Нужен результат
  целиком — задача со списком.
- **[54]** Три опасности: `.Result` / `.Wait()` (поток выбыл, голодание), `async void` (исключению некуда деться,
  процесс падает; только для обработчиков событий), забытый `await` (исключение исчезает, порядок нарушен).
  Правило: асинхронность до конца.
- **[55]** Мысль раздела: `await` регистрирует продолжение и отдаёт поток; всё, что заставляет поток ждать,
  ломает эту схему.

## Связки с другими лекциями

- **Назад, Л2:** сборщик знает про кучу и ничего — про остальное; куча больших объектов (большая строка);
  счётчики процесса (очередь пула, потоки); декомпилятор для state machine.
- **Назад, Л3:** `sealed` убирает сложный паттерн `Dispose`; горячий путь и `ValueTask`.
- **Назад, Л4:** `finally` выполняется всегда; обработчики событий и `async void`; замыкание переносит
  переменную в кучу, как state machine; `catch (Exception)` и отмена.
- **Назад, Л5:** `Span`/`Memory` и `await`; контракт `IEnumerable` и его асинхронный брат;
  `using` у перечислителя.
- **Вперёд, Л8:** graceful shutdown вызывает `Dispose` у созданного; обработчик запроса — граница для
  исключения отмены.
- **Вперёд, Л9:** тело запроса — тот же `Stream`; токен запроса; `IAsyncEnumerable` из обработчика —
  стриминг ответа.
- **Вперёд, Л10:** конфигурация вместо путей в коде; контейнер зависимостей создаёт и освобождает
  (владелец); сокеты исходящих вызовов.
- **Вперёд, Л11:** уязвимость выхода за папку через `..`.
- **Вперёд, Л12:** `AsyncLocal` — связывание логов одного запроса.
- **Вперёд, Л13–Л14:** соединения в пуле; токен последним параметром запроса к базе.
- **Вперёд, Л15:** анализатор на неосвобождённый `IDisposable` и на синхронный вызов внутри асинхронного
  метода; код нейросети с `ReadLine` без `Async`.

**Лабораторная 6:** потоковый разбор большого файла — асинхронное чтение построчно, `CancellationToken`,
запись результата, корректное освобождение ресурсов. Проверка одна: после работы файл не остаётся
заблокированным. Подробности для составителя — в конце сценария.

## Открытые вопросы

Авторское решение, не менять по умолчанию:

1. **`yield` в Л6.** В шаге 1 механизма (кадр 39) и перед `IAsyncEnumerable` (кадр 53) сценарий ссылается
   на `yield` «из прошлой лекции», а листинг кадра 53 содержит `yield return`. В Л5 `yield return` был
   сознательно вырезан и не преподаётся. Нужно либо вернуть его в Л5, либо объяснить в Л6 с нуля.
2. **Латинский шрифт-замена (Latin Modern) не проверялся** для этой колоды; собиралась с PT Sans.
