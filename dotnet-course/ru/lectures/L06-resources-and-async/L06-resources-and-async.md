[СЛАЙД 4 — вопрос в зал: «Файл открыли, прочитали и не закрыли. Объект стал недостижим, и сборщик мусора его убрал. Файл закрыт?»]

Начнём с вопроса. Вы открыли файл, прочитали строку и забыли закрыть. Объект, через который вы читали, стал недостижим, и через какое-то время сборщик мусора его убрал. Файл после этого закрыт? Кто скажет «да, сборщик же убрал объект»? Кто скажет «нет»? Кто скажет «когда-нибудь»? Правы последние, и вот почему это худший из трёх ответов.

[СЛАЙД 5 — сравнение: слева «managed — объекты в куче, GC видит», справа «unmanaged — файловый дескриптор, сокет, соединение с БД, GC не видит»]

Есть managed-ресурсы: объекты в управляемой куче. Их видит сборщик, он знает их размер, знает, кто на них ссылается, и убирает, когда они не нужны. Вся вторая лекция была про них.

И есть unmanaged-ресурсы: то, что принадлежит операционной системе, а не рантайму. Файловый дескриптор, он же handle. Сетевой сокет. Соединение с базой данных. Мьютекс операционной системы. Кусок памяти, выделенный не в куче. Когда вы открываете файл, операционная система выдаёт вашему процессу число, дескриптор, и заводит у себя запись: этот процесс держит этот файл открытым, с такими правами. Сборщик мусора про эту запись не знает и знать не может. Для него объект FileStream это несколько десятков байт в куче с числом внутри. Он не понимает, что число это дескриптор, и что операционной системе нужно сказать «я закончил», чтобы она свою запись убрала.

Отсюда ответ на вопрос. Пока вы не сказали «закрой», файл открыт. Сборщик уберёт объект, но дескриптор останется, файл останется заблокирован для других, и у операционной системы есть предел на количество открытых дескрипторов на процесс. Исчерпали, и следующий Open в любом месте программы упадёт.

Ответ «когда-нибудь» связан с финализаторами, о которых скажу в конце раздела. Пока запомните: за unmanaged-ресурсы отвечаете вы, и явно.

Файл здесь просто самый наглядный пример. Тот же механизм у всего, что вы будете открывать в сервисе. Соединение с базой данных: в тринадцатой лекции мы увидим, что соединения живут в пуле, и незакрытое соединение это соединение, которое в пул не вернулось. Пул конечен, и через сотню таких утечек следующий запрос к базе будет ждать освобождения соединения до таймаута. Сокет исходящего HTTP-вызова, о котором в десятой: незакрытые сокеты копятся в операционной системе и заканчиваются. Везде одна и та же история: объект в куче маленький и безобидный, а за ним запись у операционной системы или у пула, о которой сборщик не знает.

### IDisposable и using

[СЛАЙД 6 — «IDisposable: интерфейс с одним методом Dispose»; под ним: что делает Dispose у FileStream, у соединения с базой, у сокета]

Значит, нужен способ сказать «я закончил» явно и вовремя. В .NET он один на все ресурсы: IDisposable. Интерфейс с одним методом, Dispose. Договор: тип, который владеет unmanaged-ресурсом или другим IDisposable, реализует его, и вызов Dispose означает «я закончил, освободи». FileStream закрывает дескриптор. StreamReader закрывает свой FileStream. Соединение с базой возвращается в пул. Сокет закрывается.

Вызывать Dispose руками можно, но неправильно, потому что вы забудете, а ещё потому что между открытием и вашим вызовом может вылететь исключение, и до Dispose дело не дойдёт. Для этого есть using. Пример возьмём простой: найти в файле первую строку со словом «Hello!». StreamReader читает файл строка за строкой с начала, и мы останавливаемся на первом совпадении. Файл читается линейно, подряд, и дальше первого совпадения мы не идём. Подробно про StreamReader через несколько минут, сейчас важно слово using.

[СЛАЙД 7 — листинг целиком: старая форма, using-statement с блоком в фигурных скобках; метод ищет первую строку с «Hello!»]

```csharp
string? FindHello(string path)
{
    using (StreamReader reader = new StreamReader(path))
    {
        string? line = reader.ReadLine();
        while (line != null && !line.Contains("Hello!"))
        {
            line = reader.ReadLine();
        }
        return line;
    }
}
```

Первая форма, старая: using, в скобках создание объекта, потом блок в фигурных скобках. Объект живёт до конца блока, и в конце блока вызывается Dispose. Цикл читает строки по одной, пока не встретит нужную или пока строки не кончатся: ReadLine в конце файла возвращает null.

[СЛАЙД 8 — листинг целиком: современная форма, using-declaration без блока; тот же метод]

```csharp
string? FindHello(string path)
{
    using StreamReader reader = new StreamReader(path);
    string? line = reader.ReadLine();
    while (line != null && !line.Contains("Hello!"))
    {
        line = reader.ReadLine();
    }
    return line;
}
```

Вторая форма, современная: using перед объявлением переменной, без блока. Объект живёт до конца текущей области, метода или цикла, и Dispose вызывается при выходе из неё. Меньше отступов, и при нескольких ресурсах подряд не нужна лестница вложенных блоков.

[СЛАЙД 9 — «во что компилятор разворачивает using»: листинг try { … } finally { if (reader != null) reader.Dispose(); }]

```csharp
StreamReader reader = new StreamReader(path);
try
{
    // your code
}
finally
{
    if (reader != null)
    {
        reader.Dispose();
    }
}
```

Обе формы компилятор разворачивает в одно и то же: try, внутри ваш код, finally, внутри проверка на null и Dispose. Вспомните четвёртую лекцию: finally выполняется всегда. Вернулись из метода, выполнился. Вылетело исключение, выполнился. Вышли через break, выполнился. Это и есть гарантия: ресурс освобождён при любом исходе, а не только при удачном. Using это не сокращение, это способ не думать об исключениях между открытием и закрытием. И если переменная оказалась null, using это переживёт: проверка на null встроена в развёрнутый finally.

[СЛАЙД 10 — «несколько using подряд освобождаются в обратном порядке»: два объявления, FileStream и StreamWriter поверх него; стрелки порядка закрытия: сначала writer, потом stream]

```csharp
using FileStream stream = new FileStream(path, FileMode.Create);
using StreamWriter writer = new StreamWriter(stream);
writer.WriteLine("Hello!");
// scope ends: writer.Dispose(), then stream.Dispose()
```

Когда в одной области несколько объявлений через using, освобождаются они в обратном порядке: последний созданный первым. Это не случайность, а необходимость: писатель создан поверх потока, значит, писатель освобождается первым, сбрасывает буфер в поток, и только потом поток закрывает дескриптор. Перепутанный порядок это потерянный хвост файла. Форма объявления без блока делает порядок правильным сама, потому что следует порядку объявлений.

Что будет, если забыть. Не гипотетически, а конкретно.

[СЛАЙД 11 — код без using: два подряд File.Create одного пути; под ним реальный текст исключения IOException «процесс не может получить доступ к файлу, так как он используется другим процессом»]

Вот два открытия одного файла подряд без using и без Dispose. File.Create открывает файл на запись и не разрешает другим ничего: ни читать, ни писать. Переменная вышла из области, объект недостижим, но Dispose никто не вызвал. Второе открытие того же файла падает с исключением: файл используется другим процессом. Другим процессом! Это вы сами. Это ваш собственный незакрытый дескриптор из предыдущей строки. Ошибка выглядит так, будто виновата операционная система или антивирус, и люди тратят часы на поиск «кто держит файл», а держит их же код десятью строками выше.

Это не особенность Windows, хотя текст исключения оттуда. На Linux и macOS рантайм воспроизводит те же правила совместного доступа своими средствами, и вы получите то же исключение. И это не каприз, это защита: два писателя в один файл без координации это испорченный файл.

С using второе открытие работает, потому что к его моменту первый дескриптор уже освобождён, детерминированно, в finally. Вот это слово, детерминированно, и есть вся разница между Dispose и сборщиком мусора. Сборщик уберёт когда-нибудь. Dispose освобождает сейчас, в этой строке.

[ПАУЗА]

Теперь свой тип, владеющий ресурсом. Рано или поздно вы напишете класс, у которого внутри FileStream, соединение, сокет или чужой IDisposable. Тогда ваш класс тоже IDisposable, и его Dispose должен быть написан правильно. Правильно это значит две вещи.

[СЛАЙД 12 — листинг целиком: класс LogWriter; выделить флаг _disposed, проверку в начале Dispose и ObjectDisposedException]

```csharp
sealed class LogWriter(string path) : IDisposable
{
    private readonly StreamWriter _writer = new StreamWriter(path, append: true);
    private bool _disposed;

    public void Write(string line)
    {
        ObjectDisposedException.ThrowIf(_disposed, this);
        _writer.WriteLine($"{DateTime.UtcNow:O} {line}");
    }

    public void Dispose()
    {
        if (!_disposed)
        {
            _writer.Dispose();
            _disposed = true;
        }
    }
}
```

Первое: Dispose идемпотентен. Вызвали дважды, второй вызов ничего не делает и не падает. Флаг проверяется перед освобождением, и если объект уже освобождён, ничего не происходит. Зачем: ваш объект может оказаться внутри using и одновременно кто-то вызовет Dispose руками, или два владельца решат, что освобождать должны они. Двойной Dispose должен быть безопасен, это часть договора интерфейса, и стандартная библиотека его соблюдает.

Второе: использование после Dispose это ошибка, и о ней нужно сказать сразу. Метод Write проверяет флаг и бросает исключение с говорящим именем: объект освобождён. В стандартной библиотеке для этого есть однострочный помощник, он в листинге. Без проверки вы получите либо непонятное исключение из глубины, либо, что хуже, тихую запись в никуда.

Заметьте, чего в листинге нет. Нет финализатора. Нет сложной схемы с виртуальным методом и параметром «из финализатора или нет», которую вы найдёте в старых статьях под названием «полный паттерн Dispose». Она нужна только тому, кто держит сырой дескриптор операционной системы напрямую, а вы его не держите: вы держите FileStream, и он сам разбирается со своим дескриптором. Ваш Dispose просто передаёт вызов дальше по цепочке владения. Класс, который владеет IDisposable, освобождает его в своём Dispose. Всё.

Две детали в листинге, которые не случайны. Класс запечатан, из третьей лекции: если бы от него можно было наследоваться, наследнику понадобился бы способ добавить своё освобождение, и вот тогда появилась бы та самая сложная схема с виртуальным методом. Sealed убирает проблему целиком. И освобождение внутри идёт в порядке, обратном созданию, если ресурсов несколько: сначала то, что построено поверх, потом то, на чём построено. Тот же принцип, что у нескольких using подряд.

[СЛАЙД 13 — «владеет — освобождает»: слева «создали сами — владеем, освобождаем», справа «получили снаружи — не владеем, не освобождаем»; внизу «владелец один»]

И слово «владеет» здесь главное. Если объект вам передали через конструктор, вы им, скорее всего, не владеете: его создал кто-то другой, он же и освободит. Если вы создали его сами, владеете вы. Dispose вызывает владелец, ровно один раз. Когда двое считают себя владельцами, ресурс освобождается дважды, и вторая половина сервиса получает закрытое соединение. Когда никто, он не освобождается вовсе. В десятой лекции контейнер зависимостей возьмёт это на себя: он создаёт, он и освобождает, в конце запроса. Но правило то же.

Одна мелочь из практики. Dispose не должен бросать исключения. Он вызывается из finally, часто в момент, когда исключение уже летит, и второе исключение из finally затрёт первое, то самое, которое объясняло, что случилось. Освобождайте молча, а если освобождение может упасть, ловите внутри Dispose и пишите в лог.

### Три уровня работы с файлом

Теперь файл сверху вниз, три уровня, и на каждом уровне вопрос: когда этого уровня перестаёт хватать. Чем ниже уровень, тем больше контроля и тем больше ответственности.

[СЛАЙД 14 — уровень 1, «File.ReadAllText: всё в строку»: одна строка кода, принцип работы коротко]

Уровень первый: статические методы класса File. Прочитать весь файл в строку. Прочитать все строки в массив. Записать строку в файл. Одна строка кода, никаких объектов, никакого закрытия: метод сам открыл, прочитал, закрыл. Это правильный выбор для конфигурации, для маленького шаблона, для теста. Всё, что помещается в память с запасом и читается один раз.

Когда его перестаёт хватать. Вспомните вторую лекцию: строка это объект в куче, и большая строка это куча больших объектов, которую сборщик не уплотняет. Файл на сто мегабайт превращается в строку на двести мегабайт, потому что символы двухбайтовые, и эта строка живёт, пока вы её обрабатываете. Теперь представьте, что это сервис, и файл приходит с каждым запросом. Десять одновременных запросов, два гигабайта. Вот момент, когда «прочитать всё в строку» перестаёт быть допустимым: когда размер не ограничен вами, или когда файлов много одновременно, или когда вам нужна не вся строка, а проход по ней. Правило: если вы не можете назвать верхнюю границу размера, вы не читаете файл целиком.

У этих методов есть асинхронные варианты с тем же именем и суффиксом, и во второй половине лекции они пригодятся. И одна деталь про текст: файл это байты, а строка это символы, и между ними кодировка. Методы класса File по умолчанию считают, что файл в UTF-8, и умеют распознать маркер кодировки в начале файла, если он есть. Файл из старой системы в национальной кодировке прочитается как мусор, и кодировку нужно указать явно. Это редкость, но когда случается, люди ищут ошибку не там.

[СЛАЙД 15 — уровень 2, «StreamReader: построчно»: файл читается блоками в буфер, из буфера отдаются строки; в памяти один блок и одна строка]

Уровень второй: StreamReader. Объект, который читает текст из потока построчно или кусками, ровно как в примере с «Hello!». Внутри у него буфер на несколько килобайт: он читает из файла блок, отдаёт вам строки из блока, когда блок кончился, читает следующий. В памяти в каждый момент один блок и одна строка. Файл на гигабайт обрабатывается в постоянной памяти. Плюс он занимается кодировкой: байты в файле превращаются в символы по правилам, которые вы указали или которые он определил по началу файла. Это уровень для логов, выгрузок, любого текста, который обрабатывается строка за строкой. И это первый уровень, где появляется объект, который нужно закрыть, и для него мы уже знаем, как: using.

[СЛАЙД 16 — уровень 3, «FileStream: байты, позиция, режим, доступ»: конструктор FileStream с FileMode, FileAccess и FileShare; рядом пометка, что доступ к файлу можно задавать явно]

Уровень третий: FileStream. Байты. Никакого текста, никаких строк. Позиция в файле, которую можно двигать. Режим открытия: создать, открыть существующий, дописать в конец. Права доступа: чтение, запись. И режим совместного доступа: можно ли другим открыть этот файл, пока он открыт у вас. Всё это задаётся прямо в конструкторе, и слайд показывает его целиком с четырьмя аргументами. Это уровень для двоичных форматов, для больших файлов с произвольным доступом, для случаев, когда вам нужно записать точно в это место. StreamReader, кстати, внутри работает поверх FileStream, так что три уровня это не три разных механизма, а три слоя над одним.

Обратите внимание на четвёртый аргумент: совместное чтение разрешено, запись нет. Пока мы держим файл открытым, другой процесс сможет его читать, но не изменять. Это контракт с операционной системой, и его стоит выбирать сознательно: лог, который пишет сервис, обычно разрешает чтение, чтобы его можно было смотреть на ходу; файл, который вы перезаписываете целиком, не разрешает ничего. У класса File есть короткие методы для частых случаев, открыть текст на чтение или создать файл, и внутри у них те же FileStream с разумными умолчаниями.

На этом уровне видна ещё одна вещь, которую верхние уровни прячут: буферизация. Запись в FileStream не уходит на диск сразу, она копится в буфере и сбрасывается, когда буфер полон или когда вы попросили явно. Это правильно, потому что диск любит большие блоки. Но если процесс упал до сброса, хвост данных потерян, хотя код записи отработал без ошибок. Закрытие через Dispose сбрасывает буфер, это ещё одна причина закрывать. А для критичных записей, например журнала операций, есть явный сброс, и его вызывают после каждой важной записи, осознанно платя скоростью за гарантию.

И здесь важное обобщение. FileStream это наследник абстрактного класса Stream, поток байтов. У Stream есть и другие наследники: сетевой поток, поток в памяти, поток со сжатием, поток шифрования. StreamReader принимает любой Stream, ему всё равно, откуда байты. Поэтому код, который построчно читает файл, без изменений читает тело HTTP-запроса или ответ от сервера, и в девятой лекции вы это увидите. Потоки ещё и вкладываются друг в друга: поток сжатия поверх файлового потока, и читатель поверх них. Стандартная библиотека собирает конвейеры из потоков ровно так же, как LINQ из операторов.

[ПАУЗА]

### Пути к файлам

[СЛАЙД 17 — «Path.Combine(dir, "logs", "app.txt")»: на Windows с обратными косыми чертами, на Linux с прямыми; подпись «путь не склеивают строками»]

Теперь путь к файлу. Отдельная боль, которая не выглядит как боль, пока сервис работает у вас на машине.

Разделители. На Windows обратная косая черта, на Linux и macOS прямая. Если вы склеиваете путь строками с разделителем внутри, у вас есть код, который работает на одной платформе. Для склейки есть метод Combine класса Path, и есть более новый Join, который ведёт себя предсказуемее с начальными разделителями. Они подставляют разделитель текущей платформы, и путь, собранный ими, работает везде. Правило простое: путь никогда не собирается через конкатенацию.

[СЛАЙД 18 — сигнатуры методов класса Path: Combine, Join, GetExtension, GetFileName, GetDirectoryName]

В том же классе Path лежат разборщики: взять расширение, взять имя файла без папки, взять папку без имени. Не режьте путь по последней точке или последней косой черте руками, эти методы знают про все платформенные особенности. И одна ловушка вокруг проверки существования. Код «если файл существует, открыть» выглядит безопасным, но между проверкой и открытием файл может исчезнуть или появиться, это гонка, и она реальна на сервере с несколькими процессами. Честнее открыть и обработать исключение, чем проверять заранее. То же с созданием папки: метод создания папки не падает, если она уже есть, и проверка перед ним не нужна.

[СЛАЙД 19 — сравнение: слева «абсолютный путь — не зависит от места запуска», справа «относительный путь — от рабочей директории процесса»; внизу про регистр: Windows не различает, Linux различает]

Относительные пути. Файл «data/input.txt» это путь относительно чего? Относительно рабочей директории процесса. Не директории, где лежит ваша сборка, а той, откуда процесс запустили. Когда вы запускаете через dotnet run, это папка проекта. Когда запускаете опубликованный файл из другой папки, это та другая папка. Когда сервис запускается в контейнере, это рабочая директория, заданная в образе, обычно корневая папка приложения, но не обязательно. Один и тот же относительный путь указывает в три разных места, и код, который работал у вас, в контейнере не находит файл. Если файл лежит рядом с приложением, стройте путь от директории приложения, для неё есть свойство в стандартной библиотеке. Если файл приходит снаружи, берите его расположение из конфигурации, о которой будет десятая лекция, и никогда не зашивайте в код.

И регистр. На Windows файловая система не различает регистр, на Linux различает. Файл Config.json на вашей машине найдётся по имени config.json, а в контейнере на Linux нет. Ещё один способ получить «у меня работает».

[СЛАЙД 20 — «приложение работает со своей папкой; записать что-то нужно во временную»: слева своя папка — читаем, справа временная директория — пишем]

И три вещи, о которых спросят на ревью. Временные файлы кладутся не в папку приложения, а в системную временную директорию, для неё есть метод в том же классе Path; в контейнере папка приложения может быть только для чтения. Приложение работает со своей папкой, а всё, что нужно записать, пишет во временную. Имена файлов, пришедшие снаружи, проверяются: есть метод, отдающий список символов, недопустимых в имени. И самое важное для безопасности: путь, собранный из пользовательского ввода, может содержать две точки и вести на уровень выше, за пределы папки, которую вы хотели отдать. Клиент просит файл «две точки, косая, две точки, косая, etc, passwd», и ваш сервис его отдаёт. Это классическая уязвимость, и в одиннадцатой лекции мы к ней вернёмся. Правило: превратить путь в полный, проверить, что он начинается с разрешённой папки, и только потом открывать.

[ПАУЗА]

### Финализаторы

И последнее в разделе: финализаторы. Тот самый ответ «когда-нибудь».

[СЛАЙД 21 — синтаксис финализатора: класс с методом, у которого перед именем класса стоит тильда]

Финализатор это метод с тильдой перед именем класса, который сборщик мусора вызовет перед тем, как убрать объект. Звучит как решение: положим закрытие дескриптора туда, и забытые файлы закроются сами. FileStream, кстати, примерно так и защищён: у его дескриптора есть обёртка с финализатором, и это причина, по которой забытый файл когда-нибудь закроется.

Почему это не ваш инструмент. Три причины.

[СЛАЙД 22 — три причины не писать финализатор: «недетерминированность», «цена», «сложность»; к каждой одна короткая строка]

Первая: недетерминированность. Финализатор вызывается, когда сборщик решит собрать объект, а решает он по своим соображениям, о которых мы говорили во второй лекции. Может через миллисекунду, может через час, может никогда, если процесс завершится раньше. Ресурс, который освобождается «когда-нибудь», это ресурс, на который нельзя рассчитывать. Файл, который «когда-нибудь» разблокируется, это тот же самый час поисков «кто держит файл».

Вторая: цена. Объект с финализатором сборщик не может убрать сразу. Он должен вызвать финализатор, а для этого объект переживает лишнюю сборку и уезжает в следующее поколение, в отдельную очередь, которую обрабатывает специальный поток. Объект с финализатором дороже обычного всегда, даже если ресурс освободили правильно через Dispose. Поэтому правильно написанный Dispose ещё и говорит сборщику «финализатор не нужен», и в листинге этого нет ровно потому, что финализатора нет.

Третья: сложность. Финализатор выполняется в отдельном потоке, в неизвестный момент, когда другие объекты, на которые вы ссылаетесь, возможно, уже собраны. Писать код, который корректен в таких условиях, трудно, и почти весь код с финализаторами в интернете написан неправильно.

Что вместо. Если вы держите сырой дескриптор операционной системы, чего в сервисе почти не бывает, для этого есть готовый базовый класс безопасной обёртки над дескриптором в стандартной библиотеке: он реализует и Dispose, и финализатор, и защиту от гонок, и вам остаётся указать, как именно закрывать. Если вы держите managed-объекты, у вас Dispose без финализатора, как в листинге. Финализатор нужно знать, чтобы понимать, почему забытый файл всё-таки когда-нибудь закрывается, и чтобы не удивляться слову в чужом коде. Писать его вам не нужно.

И про завершение процесса, раз уж речь о «когда-нибудь». При обычном завершении процесса рантайм не обещает вызвать финализаторы для оставшихся объектов. То есть файл, который вы не закрыли и надеялись на финализатор, может остаться с несброшенным буфером, и последние строки лога не попадут на диск. Единственный способ быть уверенным, что всё закрыто, это закрыть явно. В восьмой лекции мы увидим, как сервер при остановке вызывает Dispose у всего, что он создал, в правильном порядке, и это называется graceful shutdown. Он работает только для того, что было оформлено как IDisposable и передано ему во владение.

[СЛАЙД 23 — мысль раздела одной строкой]

Мысль раздела на ребро. Сборщик мусора убирает память, а не ресурсы. Ресурс освобождает владелец, один раз, детерминированно, через using. Всё остальное это «когда-нибудь», и «когда-нибудь» в проде не наступает вовремя.

## 2. Асинхронность (кульминация лекции) (45)

[СЛАЙД 24 — заголовок раздела и фраза: «поток — дорогой ресурс, и он не должен ждать»]

Вторая половина, и она главная. Сорок пять минут, и я честно скажу, как их потрачу. Первые десять на вопрос «зачем», потому что без него всё остальное выглядит как усложнение ради усложнения. Потом двадцать минут на то, как это устроено внутри: что происходит в момент, когда вы пишете await, кто и на каком потоке продолжает ваш метод, и почему это работает без тысячи потоков. Это та часть, которую обычно проходят мельком, а потом люди годами пишут асинхронный код, не понимая, что он делает. И последние пятнадцать на инструменты и грабли.

[ВОПРОС В ЗАЛ]

[СЛАЙД 25 — вопрос в зал: «Запрос идёт в базу данных, ответ приходит через 50 мс. Что делает поток, обрабатывающий запрос, эти 50 мс?»]

Вопрос для начала. Сервис обслуживает запрос: принял, сходил в базу данных, дождался ответа, собрал результат, отдал. Поход в базу занимает, скажем, пятьдесят миллисекунд. Что делает поток, который обрабатывает этот запрос, эти пятьдесят миллисекунд? Кто скажет «ждёт»? Все. Правильно. А что значит «ждёт» для операционной системы? Поток заблокирован: он не выполняет инструкций, планировщик его не запускает, он занимает свой стек и свою запись в таблице потоков и не делает ничего. Пятьдесят миллисекунд это вечность для процессора: за это время он мог выполнить десятки миллионов инструкций. И поток не выполнил ни одной.

[СЛАЙД 26 — схема времени одного потока: короткий кусок работы (принял запрос), длинный пустой отрезок «ждёт базу, 50 мс», короткий кусок работы (собрал ответ)]

Теперь масштаб. Тысяча одновременных запросов. Если на каждый запрос свой поток, у нас тысяча потоков, из которых почти все в каждый момент времени ждут базу. Что стоит тысяча потоков? Каждый поток это стек, порядка мегабайта зарезервированной памяти. Это запись в ядре операционной системы. Это переключения контекста: планировщик перебирает потоки, чтобы найти тот, кому есть что делать, и каждое переключение это микросекунды и сброс кэшей процессора. Создание потока это миллисекунды. Десять тысяч запросов, десять тысяч потоков, и операционная система тратит больше времени на переключение между ними, чем на полезную работу. Это называется thread-per-request, поток на запрос, и это модель, в которой сервер упирается в потолок задолго до того, как упёрся в процессор или в базу.

Отсюда идея, и она простая. Пока запрос ждёт базу, его поток не должен ждать вместе с ним. Поток должен уйти обслуживать другой запрос, а когда ответ базы придёт, какой-нибудь поток, не обязательно тот же самый, продолжит обработку с того места, где остановились. Тысяча запросов в ожидании, а потоков столько, сколько ядер, и все они заняты работой, а не ожиданием. Вот что такое асинхронность. Не «быстрее», а «не занимать поток ожиданием».

Проговорю, что асинхронность даёт и чего не даёт, потому что ожидания часто неверные. Один запрос она не ускоряет: база отвечает те же пятьдесят миллисекунд, и клиент ждёт те же пятьдесят. Она меняет то, сколько запросов сервер держит одновременно на том же железе: вместо тысячи потоков с их стеками и переключениями восемь потоков и тысяча маленьких объектов в куче. Пропускная способность на поток растёт на порядки, память на запрос падает на порядки, и сервер упирается в базу или в сеть, а не в собственные потоки. Это и есть цель: чтобы узким местом было то, что действительно медленное, а не то, как вы ждёте.

[СЛАЙД 27 — две картинки: слева тысяча потоков, каждый ждёт; справа восемь потоков работают, тысяча ожиданий висят «в воздухе» как маленькие объекты]

[ПАУЗА]

И сразу разведём два слова, которые путают чаще всего, и путаница порождает худший код в проекте. Асинхронность и параллелизм.

Асинхронность про ожидание. Операция, результата которой нужно дождаться, не занимая поток: сеть, диск, база, таймер. Это ввод-вывод. Пока данные идут по проводу, процессору нечего делать, и асинхронность позволяет ему делать что-то другое.

Параллелизм про вычисления. Задача, которую можно разрезать на части и считать одновременно на нескольких ядрах: обработка изображения, перемножение матриц, перебор вариантов. Это загрузка процессора, а не ожидание.

[СЛАЙД 28 — таблица три строки: «синхронно — один поток, ждёт», «асинхронно — потоков мало, никто не ждёт», «параллельно — потоков по числу ядер, все считают»; колонка «когда»: I/O против CPU]

Почему путаница порождает плохой код. Вариант первый: человек берёт операцию ввода-вывода и заворачивает её в Task.Run, «чтобы было асинхронно». Task.Run отдаёт делегат в thread pool, и там поток блокируется в ожидании сети. Мы потратили поток из пула, чтобы он ждал. Ничего не выиграли, а поток из общего пула отняли у тех, кому он нужен. Вариант второй: человек берёт тяжёлое вычисление и помечает метод async, ожидая, что оно станет быстрее или перестанет мешать. Не станет: вычисление занимает поток ровно так же, async ничего не распараллеливает. Асинхронность не даёт вычислениям ни одного лишнего ядра, она даёт ожиданиям возможность не занимать ядро.

[СЛАЙД 29 — правило: «ввод-вывод — асинхронно, через await»; «вычисления — параллельно, если можно разрезать, и синхронно, если нельзя»]

Правило, которое я прошу запомнить дословно. Ввод-вывод: асинхронно, через await. Вычисления: параллельно, если их можно разрезать, и синхронно, если нельзя. В сервисе почти всё это ввод-вывод, поэтому в сервисе почти всё асинхронно, а параллелизм появляется редко и осознанно.

Как выглядит параллелизм, когда он всё-таки нужен. Стандартная библиотека даёт параллельный цикл, который разрезает коллекцию на части и обрабатывает их на нескольких потоках пула, и параллельный LINQ с тем же смыслом. Обе штуки для вычислений над данными в памяти, и обе занимают все ядра, поэтому в сервисе под нагрузкой их применяют осторожно: ядра нужны другим запросам. А когда нужно параллельно ждать, например сходить в три внешних сервиса одновременно, это не параллелизм, а композиция асинхронных операций, и она будет через двадцать минут: запустить три ожидания и дождаться всех. Потоков это не занимает вообще.

[ПАУЗА]

Теперь объект, вокруг которого всё крутится: Task.

[ВОПРОС В ЗАЛ]

[СЛАЙД 30 — вопрос в зал: «Что такое Task?»]

Что такое Task? Кто скажет «поток»? Есть такие. Кто скажет «фоновая операция»? Ближе, но нет. Задача это не поток и не операция. Это обещание. Объект, который говорит: результат будет, но, возможно, не сейчас. У него есть состояние: ещё не завершён, завершён успешно, завершён с исключением, отменён. У него есть результат, если это Task с параметром типа, и исключение, если что-то пошло не так. И у него есть список того, что нужно сделать, когда он завершится. Этот список называется continuations, продолжения, и через десять минут он окажется центром всей истории.

[СЛАЙД 31 — Task как карточка: «состояние», «результат / исключение», «список continuations»]

Откуда берутся задачи. Два принципиально разных источника, и это важно различать. Первый: Task.Run. Вы даёте делегат, он ставится в очередь thread pool, какой-то поток из пула его выполнит, и задача завершится, когда делегат вернёт результат. Здесь за задачей стоит поток, и это инструмент для вычислений.

[СЛАЙД 32 — источник задачи 1, «Task.Run → поток из пула»: строка кода и короткое пояснение; за задачей стоит поток]

Второй: библиотека ввода-вывода. Вы вызвали асинхронное чтение из сокета, и библиотека вернула вам задачу. За этой задачей не стоит никакой поток. Библиотека попросила операционную систему прочитать данные и сообщить, когда они придут. Задача завершится в момент, когда операционная система сообщит и библиотека выставит ей результат. Между запросом и ответом задача существует, поток не существует. Вот это второе и есть асинхронность в чистом виде.

Так что Task это единый способ говорить о результате, который будет позже, независимо от того, считает его поток или ждёт операционная система. Это и удобно, и опасно: по типу Task нельзя понять, стоит ли за ним поток. Понять можно по тому, откуда задача пришла.

[СЛАЙД 34 — сравнение: слева «Task.Delay — регистрирует таймер, поток свободен», справа «Thread.Sleep — блокирует поток»]

Самый наглядный пример этой разницы: пауза. Есть метод, который блокирует поток на заданное время, и есть метод, который возвращает задачу, завершающуюся через заданное время. Первый занимает поток: он ничего не делает, но никому не достаётся. Второй регистрирует таймер у операционной системы и возвращает задачу; поток свободен, а через нужное время таймер завершит задачу и запустит продолжение. Оба выглядят как «подождать секунду», и разница между ними это вся сегодняшняя лекция. В сервисе первого не должно быть никогда.

Когда задача считается завершённой. Когда у неё выставлен результат или исключение. С этого момента её результат можно взять, и все продолжения из списка запускаются. Если вы попросили результат раньше, вам придётся ждать, и как именно ждать, это разница между правильным и неправильным кодом, о чём в конце раздела.

Два слова про ValueTask, потому что вы увидите его в сигнатурах стандартной библиотеки. Task это объект в куче, аллокация на каждый вызов. Для методов, которые вызываются миллионы раз и очень часто завершаются сразу, например чтение из буфера, который уже заполнен, эта аллокация лишняя: результат есть, а задачу всё равно создали. ValueTask это структура, которая содержит либо готовый результат без всякой аллокации, либо ссылку на настоящую задачу, если ждать всё-таки пришлось. Правило потребления простое: await ровно один раз, не сохранять, не ждать дважды. Правило создания ещё проще: возвращайте Task, пока измерение не показало, что аллокация в этом месте мешает. Это тот самый горячий путь из третьей лекции, и вне его ValueTask это усложнение без выгоды.

Куда копать, если захочется понять, как библиотека создаёт задачу, за которой нет потока. Есть тип, который так и называется, источник завершения задачи: он выдаёт задачу и позволяет тому, у кого он в руках, в любой момент выставить ей результат или исключение. Библиотека создаёт его, отдаёт вам задачу, а в callback от операционной системы выставляет результат. Это мост между миром callback и миром задач, и если вам когда-нибудь придётся оборачивать старую библиотеку с событиями в асинхронный API, вы возьмёте именно его.

[СЛАЙД 35 — фраза крупно: «У асинхронного метода нет своего потока»]

У асинхронного метода нет своего потока. Он выполняется кусками, и каждый кусок выполняет тот поток, который оказался свободен в нужный момент.

[СЛАЙД 36 — листинг целиком: метод с пятью await подряд, каждый await на отдельной строке с номером в комментарии]

```csharp
async Task<string> HandleAsync(int id)
{
    User user = await LoadUserAsync(id);              // 1
    int[] orders = await LoadOrdersAsync(user);       // 2
    decimal price = await CalcPriceAsync(orders);     // 3
    await SaveAsync(price);                           // 4
    await NotifyAsync(user);                          // 5
    return user.Name;
}
```

Посмотрите на этот метод. Он выглядит как пять обычных строк подряд, но каждый await в нём это тормоз. На каждом await метод может улететь в ожидание: он говорит «всё, что ниже, выполни, когда это завершится» и возвращает управление вызывающему. Пять await это пять мест, где метод может остановиться, и каждый раз он продолжится потом, возможно на другом потоке. Синтаксис выглядит как последовательный код, а семантика это callback: компилятор берёт код после await и превращает его в продолжение, которое вешается на задачу. Await это не «подожди здесь». Понимание этой фразы это половина понимания асинхронности.

[СЛАЙД 37 — метод разрезан пятью await на шесть кусков; под ними цепочка состояний 0 → 1 → 2 → 3 → 4 → 5; на каждом await подпись «может улететь в ожидание»]

Отсюда цепочка состояний. Пять await режут метод на шесть кусков. Первый выполняется до первого await, второй от первого до второго, и так далее. Метод должен помнить, до какого куска он дошёл, чтобы после ожидания продолжить с нужного места. Это и есть номер состояния: ноль, один, два, три, четыре, пять. На каждом await состояние запоминается, метод улетает, а когда ожидание закончилось, продолжение читает номер и прыгает на нужный кусок.

И сразу про исключения в этой модели, потому что четвёртая лекция это обещала. Если код после await бросил исключение, оно не может улететь вверх по стеку обычным способом: стека, из которого вызвали метод, уже нет, тот вызов давно вернулся. Поэтому исключение кладётся в задачу, которую метод вернул, и задача переходит в состояние «завершена с ошибкой». А тот, кто эту задачу ожидает через await, получит исключение в своей строке await, как будто оно брошено там, с сохранённой трассировкой оригинала. Так исключение путешествует по цепочке задач вверх, от await к await, пока не дойдёт до обработчика. Пока в цепочке везде await, всё работает как в синхронном коде. Где цепочка разорвана, исключение остаётся лежать в задаче, и это последние грабли сегодняшней лекции.

[СЛАЙД 38 — листинг: асинхронный метод бросает исключение после await; вызывающий ловит его в try/catch вокруг await; подпись «исключение лежит в задаче и вылетает в строке await»]

```csharp
async Task FailAsync()
{
    await Task.Delay(10);
    throw new InvalidOperationException("boom");
}

try
{
    await FailAsync();   // the exception is thrown here
}
catch (InvalidOperationException ex)
{
    Console.WriteLine(ex.Message);
}
```

Теперь шаги. Что делает компилятор и что делает рантайм.

[СЛАЙД 39 — схема из четырёх шагов: 1 — компилятор превращает метод в state machine; 2 — на await: завершена? да → идём дальше, нет → регистрируем продолжение и возвращаемся; 3 — операция завершилась → продолжение ставится в thread pool; 4 — MoveNext продолжает с сохранённого состояния]

Шаг первый, компилятор. Помните yield из прошлой лекции? Метод с yield превращался в класс с полем состояния и методом MoveNext, который продолжал с места паузы. Async устроен точно так же, тем же приёмом. Компилятор берёт ваш асинхронный метод и генерирует state machine: структуру, у которой все ваши локальные переменные стали полями, есть поле с номером состояния, и есть метод MoveNext, который выполняет код от текущего состояния до следующего await. Каждый await в вашем методе это номер состояния. Сам ваш метод превращается в три строки: создать state machine, запустить её первый раз, вернуть задачу. Откройте собранную сборку в декомпиляторе из второй лекции и посмотрите: там будет большой switch по состояниям, и вы узнаете в нём свой код, разрезанный по точкам await.

Шаг второй, что происходит в момент await. MoveNext дошёл до await. У объекта, который ожидают, запрашивается awaiter, маленькая обёртка с двумя членами: завершено ли, и «вызови вот это, когда завершится». Первое, что делает MoveNext: проверяет, завершено ли. И вот важная деталь, которую упускают. Очень часто ответ «да». Данные уже в буфере, результат уже в кэше, задача уже выполнилась. Тогда никакого переключения нет: MoveNext просто идёт дальше, на том же потоке, синхронно, как будто await не было. Это быстрый путь, и на нём асинхронность почти ничего не стоит.

Насколько часто это случается, покажу на файле из первой половины. StreamReader читает из файла блоками по несколько килобайт в буфер. Первый ReadLineAsync действительно ждёт диск. Следующие десятки вызовов возвращают строки из уже заполненного буфера, и awaiter на каждом из них отвечает «завершено», и MoveNext идёт дальше без переключения. Из сотни await реально приостанавливаются единицы. Это к вопросу о цене: асинхронный код не переключается на каждом await, он переключается только там, где действительно есть чего ждать.

Если не завершено, MoveNext делает две вещи. Регистрирует продолжение: говорит awaiter «когда завершишься, вызови мой MoveNext». Продолжение это ссылка на state machine, в которой сохранено всё: локальные переменные, номер состояния, место, откуда продолжать. И возвращается. Просто return. Из MoveNext, из вашего метода, в вызывающий код. Вызывающий получает задачу, ещё не завершённую, и делает с ней что хочет: обычно тоже await, тогда он тоже регистрирует продолжение и возвращается, и так по цепочке вверх, пока не дойдёт до того, кто эту цепочку начал: до обработчика запроса в сервере. И обработчик тоже возвращается. Поток, на котором всё это выполнялось, свободен. Он возвращается в thread pool и берёт следующий запрос.

Вот этот момент нужно увидеть отчётливо. Тысяча запросов дошли до await на походе в базу. Тысяча state machine лежат в куче, каждая размером с несколько десятков байт плюс её локальные переменные. Тысяча продолжений зарегистрированы у тысячи задач. И ни один поток ничего не ждёт. Потоки из пула обслуживают следующие запросы, пока эти тысяча ожиданий висят в воздухе. Это и есть картинка со слайда: ожидания это объекты, а не потоки.

Шаг третий, завершение. Здесь важно понять, что происходит с вводом-выводом, потому что именно тут исчезает поток.

[СЛАЙД 40 — схема: ваш поток → «прочитай сокет» → ОС; поток возвращается в пул; ОС получает данные → сигнал завершения → служебный поток рантайма → продолжение в очередь thread pool → любой поток пула выполняет MoveNext]

Когда библиотека просит операционную систему прочитать из сокета асинхронно, она не ждёт. Она регистрирует запрос: вот дескриптор, вот буфер, сообщи, когда данные будут. У операционной системы для этого есть механизм уведомления о завершении ввода-вывода: на Windows он один, на Linux другой, суть одна. Рантайм держит небольшое количество служебных потоков, которые ждут этих уведомлений, и это единственное место, где кто-то ждёт, и там ждут за всех сразу. Данные пришли по сети, сетевая карта положила их в память, ядро операционной системы отметило: запрос такой-то завершён. Служебный поток рантайма получает уведомление, находит задачу, которая соответствует этому запросу, выставляет ей результат, и задача переходит в состояние «завершена». И теперь срабатывает список продолжений.

Есть статья с названием, которое стало поговоркой: «There is no thread». Потока нет. Между моментом, когда ваш метод сказал «прочитай», и моментом, когда данные пришли, никакой поток не был занят вашим запросом. Ни ваш, ни из пула, ни служебный. Ожидание было записью в таблице ядра, и ничем больше. Именно поэтому тысяча ожиданий стоят тысячу маленьких объектов, а не тысячу потоков.

Шаг четвёртый, продолжение. Задача завершилась, и в её списке лежит продолжение: «вызови MoveNext вот этой state machine». Кто его вызовет и на каком потоке? Продолжение ставится в очередь thread pool как обычный элемент работы. Любой свободный поток пула берёт его и вызывает MoveNext. MoveNext смотрит на номер состояния, восстанавливает локальные переменные из полей, и продолжает выполнять ваш код с той строки, которая идёт после await. Дошёл до следующего await, и всё повторяется: проверка, регистрация, возврат. Дошёл до конца метода, выставил результат задаче, которую ваш метод вернул вызывающему, и это запускает продолжение вызывающего, и так по цепочке вверх, до обработчика, который наконец отправляет ответ клиенту.

[СЛАЙД 43 — сравнение: слева «переживает await — локальные переменные, this, AsyncLocal», справа «не переживает await — данные, локальные для потока; lock»]

Отсюда следствие: всё, что привязано к потоку, через await не переживает. Данные, сохранённые в переменной, помеченной как локальная для потока, после await будут чужими. Блокировка, взятая на одном потоке, не может быть отпущена на другом, и компилятор прямо запрещает await внутри блока lock. Что переживает await: ваши локальные переменные, потому что они поля state machine в куче, и ссылка this. И есть специальный тип для данных, которые должны течь вместе с асинхронной цепочкой, а не с потоком: он называется AsyncLocal, и на нём в двенадцатой лекции будет держаться связывание логов одного запроса в одну историю. Запомните слово.

Про локальные переменные добавлю то, что связывает это с четвёртой лекцией. Замыкание переносило захваченную переменную из кадра стека в скрытый класс в куче, чтобы она пережила выход из метода. State machine делает то же самое со всеми локальными переменными асинхронного метода: они поля объекта в куче и живут, пока метод не завершился. Отсюда следствие, которое кусается: большой массив в локальной переменной перед await живёт всё время ожидания, даже если после await он не нужен. Ожидание длинное, запросов много, и память под массивы, которые «уже не нужны», занята. Если объект нужен только до await, пусть его область видимости закончится до await.

[ПАУЗА]

И ещё одно заблуждение, которое стоит снять здесь, пока мы говорим о потоках. Слово async не отправляет метод в фон. Вызов асинхронного метода выполняется синхронно, на потоке вызывающего, до первого await, который действительно приостановился. Если перед первым await у вас тяжёлое вычисление на секунду, вызывающий ждёт эту секунду, как при обычном вызове, и никакая задача ему не помогает. Асинхронность начинается там, где начинается ожидание, а не там, где стоит слово async. Если вычисление нужно убрать с потока вызывающего, это Task.Run, и это уже параллелизм со всеми его оговорками из начала раздела.

Теперь про thread pool, потому что от его поведения зависит, будет ли сервис держать нагрузку.

[СЛАЙД 44 — thread pool: очередь элементов работы → потоки-рабочие по числу ядер; подпись «добавляет потоки медленно»]

Thread pool это набор потоков, которые рантайм создал заранее и переиспользует. Есть очередь элементов работы: продолжения, делегаты из Task.Run, обработчики таймеров. Потоки берут элементы из очереди и выполняют. Стартовое количество потоков примерно равно числу ядер, потому что больше потоков, чем ядер, для вычислений бессмысленно. Если очередь растёт, а потоки не справляются, пул добавляет потоки, но делает это медленно, по одному за заметный промежуток времени, потому что не может отличить «работа тяжёлая» от «потоки кто-то заблокировал», и не хочет плодить сотни потоков из-за временного всплеска.

[СЛАЙД 45 — голодание пула: все потоки-рабочие заблокированы синхронным ожиданием, очередь продолжений растёт; крупная пометка «Не блокируй поток!»]

Отсюда самое важное следствие для сервера. Если поток из пула заблокировать, заставить его ждать синхронно, он выбыл. Он не обслуживает очередь, а очередь при этом растёт, в том числе продолжениями, которым нужен поток, чтобы завершить те самые операции, которых ждёт заблокированный. Восемь ядер, восемь потоков, восемь синхронных ожиданий, и сервис стоит: продолжения в очереди, а выполнять их некому. Пул добавит девятый поток, через секунду десятый, и это будет выглядеть как задержки в секунды на ровном месте. Это называется thread pool starvation, голодание пула, и это самая частая причина того, что асинхронный сервис под нагрузкой ведёт себя хуже синхронного. Причина всегда одна: где-то кто-то ждёт синхронно того, что должно ожидаться через await. Не блокируй поток!

Как это выглядит снаружи, чтобы вы узнали симптом. Сервис отвечает быстро на малой нагрузке. Нагрузка растёт, и внезапно задержки прыгают до секунд, при том, что процессор не загружен и база отвечает быстро. Процессор простаивает, потому что потоки не считают, а ждут. Счётчики из второй лекции покажут это прямо: длина очереди thread pool растёт, количество потоков медленно ползёт вверх. Это подпись голодания, и когда вы её увидите, ищите синхронное ожидание, а не оптимизируйте запросы к базе.

И последнее в этой части: что это стоит. Асинхронный метод, который ни разу не приостановился, потому что все await были уже завершены, не выделяет ничего: state machine это структура на стеке. Метод, который приостановился хотя бы раз, выделяет свою state machine в куче, один раз, и она живёт до завершения метода. Плюс объект задачи. Это десятки байт на метод, и на фоне того, что мы экономим поток с мегабайтом стека, это ничто. Если вам захочется копать: у авторов рантайма есть длинный текст с названием вроде «как на самом деле работает async и await», и он проходит весь этот путь на уровне кода. И декомпилятор, который вы уже знаете.

[СЛАЙД 46 — сквозной пример: запрос А идёт по цепочке обработчик → сервис → репозиторий → драйвер БД на потоке 3; «зарегистрировать и вернуться» три раза вниз; поток 3 берёт запрос Б; через 40 мс ответ базы, продолжения идут вверх на потоке 7; ответ клиенту]

Соберу всё в один сквозной пример, чтобы картинка сложилась. Запрос А пришёл, поток три из пула взял его и выполняет обработчик. Обработчик вызвал сервис, сервис вызвал репозиторий, репозиторий вызвал драйвер базы, драйвер отправил запрос в сокет и вернул задачу. Репозиторий на await проверил: не завершена. Зарегистрировал продолжение, вернул задачу сервису. Сервис на своём await сделал то же, вернул задачу обработчику. Обработчик то же, вернул задачу серверу. Поток три свободен и берёт запрос Б. Через сорок миллисекунд база ответила, служебный поток рантайма получил уведомление, выставил результат задаче драйвера. Её продолжение, MoveNext репозитория, попало в очередь пула. Его взял поток семь. Репозиторий продолжился, вернул результат своей задаче, это запустило MoveNext сервиса, на том же потоке семь, синхронно, потому что результат уже есть. Сервис завершил свою задачу, обработчик продолжился, отправил ответ клиенту. Запрос А начался на потоке три и закончился на потоке семь, и в промежутке не занимал ни одного. Вот и всё переключение задач: три раза «зарегистрировать и вернуться» вниз, три раза «продолжить» вверх.

[СЛАЙД 48 — вопрос в зал: «Два независимых похода по 50 мс, два await подряд. Сколько займёт метод?»]

Два независимых похода: за пользователем и за его заказами. Каждый по пятьдесят миллисекунд. Вы написали два await подряд. Сколько займёт метод? Кто скажет «пятьдесят»? Кто скажет «сто»? Сто. Await это последовательность: второй поход начнётся, когда первый завершится. Если они независимы, это лишние пятьдесят миллисекунд на каждом запросе. Правильно так: запустить оба, потом дождаться обоих.

[СЛАЙД 49 — листинг целиком; выделить, что две задачи созданы до await, и что await один, на WhenAll]

```csharp
async Task<int> TotalLengthAsync(string first, string second, CancellationToken ct)
{
    Task<string> firstTask = File.ReadAllTextAsync(first, ct);
    Task<string> secondTask = File.ReadAllTextAsync(second, ct);

    string[] texts = await Task.WhenAll(firstTask, secondTask);

    return texts[0].Length + texts[1].Length;
}
```

Две строки создают две задачи, и обе операции уже идут: чтение началось в момент вызова, а не в момент await. Потом один await на WhenAll: задача, которая завершится, когда завершатся обе, и отдаст массив результатов. Пятьдесят миллисекунд вместо ста, и ни одного лишнего потока: оба чтения ждёт операционная система, как мы разбирали. Если одна из задач упала, WhenAll завершится с исключением, и await его бросит; если упали обе, await бросит первое, а остальные доступны через саму задачу.

Одно предостережение про WhenAll. Он ждёт столько задач, сколько вы создали, и если вы создали десять тысяч одновременных запросов к внешнему сервису, вы сделали десять тысяч одновременных запросов к внешнему сервису. Он ляжет, или вас ограничат, или кончатся сокеты. Параллельные ожидания нужно ограничивать: запускать не больше, скажем, десяти одновременно, а остальные по мере освобождения. Для этого есть семафор с асинхронным ожиданием, и есть асинхронный параллельный цикл в стандартной библиотеке, у которого степень параллелизма это параметр. WhenAll для нескольких задач, цикл с ограничением для сотен.

Рядом с WhenAll живёт WhenAny: завершится, когда завершится любая из задач, и отдаст её. Классическое применение: гонка между операцией и таймером, то есть таймаут. Но у WhenAny есть ловушка: проигравшая задача не отменяется, она продолжает работать, и если она упадёт, её исключение никто не увидит. Поэтому для таймаута сегодня есть готовый метод прямо у задачи: подождать столько-то, и если не успела, исключение таймаута. А для настоящей отмены проигравшего нужен следующий инструмент.

[ПАУЗА]

CancellationToken. Это то, что превращает набор асинхронных методов в систему, которую можно остановить.

[СЛАЙД 50 — цепочка: CancellationTokenSource → токен → эндпоинт → сервис → репозиторий → драйвер БД; подпись «один параметр сквозь весь стек»]

Устройство простое. Есть источник отмены, объект, у которого можно вызвать «отменить». У источника есть токен, лёгкая структура, которую передают всем, кто должен узнать об отмене. Токен умеет две вещи: сказать, отменён ли он, это свойство IsCancellationRequested, и бросить исключение отмены, если отменён, это метод ThrowIfCancellationRequested. И у него можно зарегистрировать callback на момент отмены.

Как это используется. Токен протягивается через весь стек как последний параметр каждого асинхронного метода. Обработчик запроса получает его от сервера, в девятой лекции мы увидим, что у каждого запроса есть токен, который отменяется, когда клиент отключился. Обработчик передаёт его в сервис, сервис в репозиторий, репозиторий в драйвер базы, и в четырнадцатой лекции запрос к базе примет его последним параметром. Каждый метод стандартной библиотеки, который что-то ждёт, принимает токен и прерывает ожидание при отмене. Клиент закрыл вкладку, и через долю секунды все операции по его запросу остановлены, включая запрос к базе, а не доработаны впустую.

[СЛАЙД 51 — листинг: как использовать токен в своём цикле; ThrowIfCancellationRequested бросает исключение отмены, IsCancellationRequested позволяет прибраться и выйти самому]

```csharp
int Sum(int[] items, CancellationToken ct)
{
    int total = 0;
    for (int i = 0; i < items.Length; i++)
    {
        ct.ThrowIfCancellationRequested();   // throws OperationCanceledException
        total += items[i];
    }
    if (ct.IsCancellationRequested)          // asks without throwing
    {
        return -1;
    }
    return total;
}
```

Правило, которое я прошу выполнять без исключений: если метод асинхронный, он принимает токен. Даже если сегодня его нечему передать. Потому что завтра появится, и переделывать сигнатуры по всему стеку это день работы. Единственное место, где токена может не быть, это самый верх, и там есть готовое значение «без отмены».

Отмена выражается исключением. Метод, который заметил отмену, бросает исключение отмены, оно летит вверх по стеку, и его нельзя глушить, вспомните четвёртую лекцию про catch Exception. Оно должно долететь до границы, до обработчика запроса из восьмой лекции, который знает, что делать: клиент ушёл, ответ не нужен, просто прибраться. В своих вычислительных циклах проверяйте токен явно, раз в итерацию, одним вызовом: ввод-вывод сам прервётся, а ваш цикл не прервётся, если вы его не спросите.

И два источника можно связать: таймаут плюс отмена запроса в один токен, который сработает от любого. Так и делают ограничение времени на операцию: связанный источник с таймаутом, его токен вниз.

Чем отмена не является. Она не прерывает поток принудительно и не останавливает код, который её не проверяет. Это кооперативный механизм: токен говорит «пора», а слушает ли его кто-то, зависит от кода. Метод, который крутит цикл без проверки токена, доработает до конца, что бы ни случилось с клиентом. Поэтому правило про «принимает токен» дополняется правилом «передаёт его дальше и проверяет в своих циклах». И источник отмены это IDisposable из первой половины: у него внутри таймер и список зарегистрированных callback, и его нужно освобождать, как любой ресурс.

[СЛАЙД 52 — листинг целиком; рядом список «что здесь используется»: using, await using, ReadLineAsync с токеном, WriteLineAsync с AsMemory и токеном]

```csharp
async Task CopyNonEmptyLinesAsync(string source, string target, CancellationToken ct)
{
    using StreamReader reader = new StreamReader(source);
    await using StreamWriter writer = new StreamWriter(target);

    string? line = await reader.ReadLineAsync(ct);
    while (line != null)
    {
        if (line.Length > 0)
        {
            await writer.WriteLineAsync(line.AsMemory(), ct);
        }
        line = await reader.ReadLineAsync(ct);
    }
}
```

Всё из сегодняшней лекции в одном методе. Читатель через using: его освобождение синхронное, ему нечего сбрасывать. Писатель через await using: это асинхронный вариант using, он вызывает DisposeAsync и ожидает освобождения. Перед закрытием писатель сбрасывает буфер на диск, и это ожидание, а не блокировка. Цикл читает строку за строкой асинхронно, с токеном, и пока ReadLineAsync не вернул null, строка есть. Запись тоже асинхронная, с токеном, и обратите внимание на AsMemory: асинхронные методы принимают Memory, а не Span, ровно по причине из пятой лекции, Span нельзя пронести через await, а Memory можно. На слайде рядом с кодом выписано, что именно здесь использовано.

И вот пара методов, которую я просил запомнить: ReadLineAsync и WriteAsync. В пятнадцатой лекции я покажу код, сгенерированный нейросетью, в котором внутри асинхронного метода стоит ReadLine без Async. Компилируется. Работает. И блокирует поток из пула на каждой строке, ровно то голодание, которое мы разобрали. Глазами эту ошибку не видно, потому что имя отличается на одно слово. Анализатор видит её сразу, и это будет ответом на дисклеймер из первой лекции про ИИ и мастера.

Ещё одно правило, связанное с этим. Если библиотека, которую вы взяли, не даёт асинхронного API для ввода-вывода, завернуть её синхронный вызов в Task.Run это не решение, а маскировка: поток из пула всё равно заблокируется, просто в другом месте. Это допустимо как временная мера, с комментарием, но настоящее решение это библиотека с честным асинхронным API, и в чек-листе выбора зависимости из второй лекции появляется ещё один вопрос: асинхронная ли она.

[ПАУЗА]

IAsyncEnumerable. Вспомните yield из прошлой лекции: последовательность, элементы которой появляются по мере запроса. Теперь представьте, что получение следующего элемента это ожидание: строка из сети, запись из базы, сообщение из очереди. Для этого есть асинхронный вариант контракта: MoveNext, который возвращает задачу, и синтаксис await foreach.

[СЛАЙД 53 — листинг целиком; выделить async перед IAsyncEnumerable, yield return внутри await foreach, и атрибут на токене]

```csharp
async IAsyncEnumerable<string> ErrorsAsync(
    string path, [EnumeratorCancellation] CancellationToken ct = default)
{
    await foreach (string line in File.ReadLinesAsync(path, ct))
    {
        if (line.Contains("ERROR"))
        {
            yield return line;
        }
    }
}

await foreach (string error in ErrorsAsync("app.log", token))
{
    Console.WriteLine(error);
}
```

Метод помечен async и возвращает асинхронную последовательность; атрибут живёт в пространстве имён System.Runtime.CompilerServices. Внутри он сам асинхронно перебирает строки файла, стандартная библиотека отдаёт их именно так, и отдаёт наружу только те, что с ошибками, через yield return. Ни одна строка не загружена заранее, файл читается по мере того, как потребитель просит следующий элемент, и в памяти в каждый момент одна строка. Атрибут на параметре токена нужен, чтобы токен, переданный при переборе, доехал до тела метода: без него токен из await foreach не попадает внутрь. Это та же машина состояний, что и у yield, и что у async, только теперь обе вместе.

Зачем это в сервисе. В девятой лекции мы увидим, что такую последовательность можно вернуть прямо из обработчика запроса, и сервер начнёт отдавать клиенту первые элементы до того, как получены последние. Стриминг вместо «собрать всё в список, сериализовать, отправить». Для больших выгрузок это разница между ответом через секунду и ответом через минуту с гигабайтом в памяти.

Когда выбирать асинхронную последовательность, а когда обычную задачу со списком. Если результат нужен целиком, чтобы, например, посчитать сумму или отсортировать, это задача со списком: стриминг ничего не даст, вы всё равно дождётесь конца. Если результат обрабатывается по элементам и элементов много или они приходят долго, это асинхронная последовательность: потребитель начинает работу с первого элемента, а память не растёт. И заметьте, как отмена доезжает до перебора: у await foreach есть метод, которым передают токен, и именно его атрибут из листинга направляет в параметр метода.

[ПАУЗА]

И грабли. Три штуки, каждая стоит проду.

[СЛАЙД 54 — три грабли: «.Result / .Wait() — поток выбыл, голодание пула», «async void — исключение некуда доставить», «забытый await — исключение исчезает»]

Первые: Result и Wait. Взять результат задачи синхронно. Поток блокируется, пока задача не завершится. Мы полчаса разбирали, почему поток не должен ждать, и вот способ заставить его ждать. В ASP.NET Core поток из пула выбывает, и это то самое голодание: восемь таких вызовов под нагрузкой, и сервис стоит. Плюс исключение из задачи, взятой через Result, приходит завёрнутым в агрегирующее, и ваш catch по типу его не поймает. Правило: асинхронность до конца. Если внизу есть await, всё, что выше, тоже await, до самого обработчика. Единственное место, где синхронное ожидание допустимо, это Main консольной утилиты, и там сегодня тоже можно написать await.

Вторые: async void. Метод помечен async и ничего не возвращает. Кажется безобидным. Но задачи нет, значит, исключение, брошенное внутри, некуда положить. Оно вылетает в никуда, и рантайм считает его необработанным: процесс падает. Целиком. Из-за одной ошибки в одном методе, который никто не ждал. Async void существует для одной цели: обработчики событий из четвёртой лекции, у которых сигнатура задана и вернуть задачу нельзя. Везде, кроме них, async Task. Если метод ничего не возвращает по смыслу, он возвращает Task без параметра, и тот, кто его вызвал, обязан его дождаться.

Третьи: забытый await. Вы вызвали асинхронный метод и не написали await. Метод запустился, дошёл до первого await, вернул задачу, и вы её выбросили. Ваш код пошёл дальше, не дожидаясь. Если внутри что-то упало, исключение лежит в задаче, которую никто не смотрит: оно исчезло бесследно, ни в логе, ни на экране. Если порядок был важен, он нарушен: запись в базу ещё не закончилась, а вы уже отправили ответ «готово». Компилятор предупреждает об этом отдельным предупреждением, и это ещё одно, которое должно быть ошибкой сборки. Если вы действительно хотите запустить и не ждать, это делается явно и с обработкой исключений внутри, а не забытым словом.

Все три объединяет одно: непонимание, что за задачей нет потока, а за await нет ожидания. Если после сегодняшней лекции это понимание есть, грабли вы узнаете сами.

Сегодня мы прошли две половины одного правила: рантайм не управляет ни ресурсами операционной системы, ни вашим временем ожидания, и то и другое ваша забота. Ресурс освобождает владелец через using. Ожидание не занимает поток через await. В следующей лекции мы выходим из процесса наружу: HTTP, сеть, и то, что происходит между клиентом и вашим сервисом до того, как ваш код вообще вызвали.

На шестой лабораторной вы напишете потоковый разбор большого файла: асинхронное чтение построчно, CancellationToken, запись результата и корректное освобождение ресурсов, и проверка будет одна: файл не остаётся заблокированным.

[СЛАЙД 55 — мысль раздела одной строкой]

Мысль раздела на ребро. Await регистрирует продолжение и отдаёт поток. Всё, что заставляет поток ждать, ломает эту схему, и ломает её под нагрузкой, а не на вашей машине.

[ЛАБА 6 — подробности для составителя: входной файл генерируется скриптом на сотни мегабайт, чтобы чтение целиком в строку было заведомо невозможно; задание: построчное асинхронное чтение через StreamReader с ReadLineAsync и токеном, фильтрация или агрегация строк, запись результата через await using StreamWriter с WriteLineAsync; обязательно принять CancellationToken из источника с таймаутом и показать, что при отмене процесс завершается быстро, а частичный результат корректно закрыт; проверка на выходе: после работы программы файл можно открыть на запись другим процессом, то есть дескриптор освобождён; типичные ошибки для проверки: ReadLine вместо ReadLineAsync, using без await у writer, забытый await у WriteLineAsync, файл читается целиком через ReadAllText, токен принят, но не передан дальше; дополнительное задание: переписать чтение как IAsyncEnumerable<string> и потребить через await foreach.]
