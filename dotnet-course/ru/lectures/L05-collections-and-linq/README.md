# Л5. Коллекции, IEnumerable и LINQ — тезисы

**Длительность:** 80 минут (секции сейчас размечены на 85, и §3 с 36 кадрами явно плотнее
22 минут — см. «Открытые вопросы»)
**Цель:** связать знание структур данных с тем, что реально лежит в стандартной библиотеке, и научить
писать запросы вместо циклов.
**Полный текст лекции:** [L05-collections-and-linq.md](L05-collections-and-linq.md)
**Слайды:** [slides/L05-collections-and-linq-slides.tex](slides/L05-collections-and-linq-slides.tex) —
72 кадра, один на каждый `[СЛАЙД n — …]` в сценарии.

Раздел 1 идёт в два прохода: сначала структуры данных вообще, без единого слова про .NET, потом та же
карта с именами из стандартной библиотеки. Разделы 2–4 — один сквозной сюжет: `IEnumerable` как
контракт на обход → LINQ как язык над этим контрактом → `IQueryable` как тот же синтаксис, но
скомпилированный в дерево выражений вместо делегата. Раздел 5 — механизм, на котором держится весь
LINQ. `yield return` в лекции не звучит нигде — отложенное выполнение показано через обычный `Where` со
счётчиком вызовов, не через свой итератор.

## Как читать

Число в начале тезиса — кадр, на котором он живёт: **[6]**. Прочерк **[—]** значит, что кадра нет и
тезис идёт голосом. В разделе 3 у каждого перечисленного метода LINQ свой кадр с одной типизированной
строкой кода — там тезисы даны построчно, без лишних слов, как и сами кадры.

## Сквозные тезисы

- Стек и очередь — не структуры данных, а правило доступа: их можно построить на любой структуре с
  прошлых слайдов.
- Сложность считает операции, машина считает обращения к памяти — локальность объясняет, почему
  связный список медленнее массива при одной и той же асимптотике, и почему двумерный массив быстрее
  читать по строкам, чем по столбцам.
- `IEnumerable` — это описание способа обойти нижележащую последовательность, а не обещание, что
  данные уже где-то лежат. Не материализовали — обход повторится заново на каждом переборе.
- Запрос — значение: его можно положить в переменную, дополнить условием, вернуть из метода, и ничего
  не вычислится, пока его не перебрали.
- `IQueryable` не выполняет код — он копит условия в дерево выражений, которое провайдер переводит в
  целевой язык платформы (SQL) только в момент перебора.
- По умолчанию — иммутабельный стиль для коллекций-значений: гарантия по построению, а не честное
  слово.

## 1. Данные в памяти (30 мин · слайды 2–25)

- **[2]** Два прохода: сначала структуры без .NET, потом те же имена в библиотеке.
- **[3]** Массив: адрес = начало + индекс × размер. Доступ по номеру — одна операция, размер фиксирован.
- **[—]** Непрерывность — это локальность: процессор читает блоками, и это объяснит разницу между
  List и LinkedList на тех же O(n).
- **[—]** Минус, который не виден на бумаге: фрагментация кучи может не дать сплошной кусок нужного
  размера, даже если места в сумме хватает.
- **[4]** Динамический массив: `Count` занято, `Capacity` выделено. Добавление в конец —
  амортизированная O(1), не постоянная.
- **[5]** Связный список: узлы разбросаны по памяти, доступа по номеру нет — только проход. Вставка у
  известного узла — O(1).
- **[6]** Однонаправленный — один кружок-указатель внутри узла и одна стрелка наружу. Двунаправленный —
  два кружка, две стрелки, в разные стороны, за счёт лишней памяти на каждый узел.
- **[7]** Хеш-таблица: значение → блок хеш-функции → попадание в корзину. Коллизия — цепочка, и
  `Equals` сравнивает внутри неё.
- **[8]** Бинарное дерево поиска: слева меньше, справа больше — бинарный поиск по ссылкам. Сбалансированное
  — O(log n); несбалансированное вырождается в связный список.
- **[9]** Пять структур рядом: каждая следующая платит за то, чего не было у предыдущей.
- **[10]** Стек и очередь — не структуры данных, а правило доступа: LIFO с одного конца, FIFO с разных.
- **[11]** Доказательство: один и тот же стек — на массиве и на связном списке. Очередь на массиве без
  трюка неудобна — сдвиг.
- **[—]** Вопрос на закрепление: «сложность у стека» — вопрос неполный, не хватает «на чём».
- **[—]** Разминка: сколько структур данных понимает сам рантайм без библиотеки? Одна — массив. IL знает
  только про `T[]`: `newarr`, `ldlen`, `ldelem`, `stelem` — без отдельного кадра, идёт голосом.
- **[12]** Динамический массив → `List<T>`: Capacity растёт 4 → 8 → 16 → 32 — реальный вывод программы.
  Знаете размер — передайте в конструктор, копирований не будет вообще.
- **[—]** `Contains` в списке — линейный перебор; в цикле по другому списку — квадрат. `RemoveAll` —
  один проход вместо сдвига на каждое удаление.
- **[13]** Связный список → `LinkedList<T>`: ровно двунаправленный вид, другого в библиотеке нет.
- **[14]** Вопрос в зал: список на массиве или связный список — что быстрее сложить миллион чисел?
- **[15]** Массив — лента в кэше процессора; связный список — острова в куче. Один и тот же O(n), разное
  время: локальность, а не сложность.
- **[—]** Связный список нужен редко: держите ссылки на узлы и часто удаляете из середины по ним —
  иначе берите List.
- **[16]** Вопрос в зал с визуализацией: двумерный массив десять на десять — быстрее читать по строкам, по
  столбцам, или без разницы? По строкам: та же последовательность адресов, что у одномерного массива, и
  открытая строка модуля памяти не нужно каждый раз перезаряжать — в разы быстрее на большом массиве.
- **[17]** Хеш-таблица → `Dictionary<TKey, TValue>`: `GetHashCode` → корзина, `Equals` — внутри. Равные
  ключи обязаны давать равные хэши; ключ — неизменяемый (record, record struct, строка).
- **[—]** Индексатор на отсутствующий ключ — исключение; `TryGetValue` — то, что пишут почти всегда.
  Порядок перебора словаря не гарантирован.
- **[18]** Множество → `HashSet<T>`: словарь без значений. Визуализация: список в список — море стрелок,
  O(n²); список в множество — одна стрелка на элемент, O(n).
- **[19]** Отсортированные коллекции: `SortedSet`/`SortedDictionary` — дерево, O(log n). `SortedList` —
  два массива, поиск O(log n), вставка O(n) — собрали один раз, читаем много.
- **[20]** Стек и очередь на массиве: `Stack<T>` — с одного конца; `Queue<T>` — массив по кругу, ради
  локальности.
- **[21]** `Concurrent*`: тот же договор не держит один писатель — атомарные «получить или добавить», не
  гарантирующие вызов функции ровно один раз.
- **[22]** Лестница интерфейсов: `IEnumerable<T>` → `IReadOnlyCollection<T>` → `IReadOnlyList<T>`,
  отдельно `ICollection<T>` → `IList<T>`. Принимайте слабое, возвращайте безопасное.
- **[—]** `IEnumerable` не говорит о стоимости и повторяемости — проходите дважды, материализуйте один
  раз в начале метода.
- **[—]** Проверка: метод дважды проходит по принятому `IEnumerable` циклом — если он ленивый, выполнится
  дважды.
- **[23]** Моя рекомендация: иммутабельный стиль по умолчанию для коллекции-значения — гарантия по
  построению, не честное слово. `ImmutableList<T>` — дерево, дешёвое добавление, O(log n) по индексу.
  `ImmutableArray<T>` — обёртка над массивом, O(1) по индексу, добавление копирует всё — без отдельного
  кадра, идёт голосом.
- **[24]** `Frozen*`: построили один раз — читаем быстрее обычного словаря. Для справочников, загруженных
  при старте.
- **[25]** `Span`/`Memory`: то же окно без копирования, что в Л2, только для коллекций. `Memory` — когда
  нужно пронести через `await`.
- **[—]** Мысль раздела: всё построено поверх массива, каждая структура — выбор, за что платить.

## 2. IEnumerable как контракт (15 мин · слайды 26–29)

- **[26]** `foreach` — это цикл по контракту, не по коллекции.
- **[—]** Что нужно типу для `foreach`: способ отдать нечто, что умеет сказать «вот следующий элемент».
  Форма, а не конкретный интерфейс.
- **[—]** Во что компилятор разворачивает `foreach`: `GetEnumerator`, курсор, `MoveNext`, `Current`, `using` —
  перечислитель может держать ресурс.
- **[—]** У массива компилятор вообще не создаёт перечислитель — цикл по индексу, тот же, из которого JIT
  убирает проверку границ.
- **[—]** Главное: `IEnumerable` — описание способа обойти нижележащую последовательность, а не обещание
  коллекции. Запрос не выполняется в момент построения — только в момент обхода, и повторяется заново
  без материализации.
- **[27]** `Where` со счётчиком вызовов в предикате: `calls so far: 0` сразу после построения, `7` после
  первого прохода, `14` после второго. Никакого `yield` — тот же урок на стандартном операторе.
- **[28]** Две ловушки: двойной перебор = двойное выполнение; лямбда захватила переменную, а не значение
  — изменили её, изменился результат запроса.
- **[—]** Изменять коллекцию во время перебора нельзя — исключение на следующем `MoveNext`.
- **[29]** Мысль раздела: запрос — описание, а не результат; материализуйте, если нужен результат ровно
  один раз.

## 3. LINQ-методы (22 мин · слайды 30–65)

- **[30]** Пять семейств: фильтрация → проекция → агрегация → группировка → соединение.
- **[—]** Задача про заказы: циклами — двадцать строк и три временные коллекции; запросом — семь строк,
  порядок слов совпадает с порядком действий.
- **[31]** `Where` → `GroupBy` → `Select` → `Where` → `OrderByDescending` → `Take` → `ToList`. Тип данных
  течёт по конвейеру как по трубе: после `Select` старое поле недоступно.
- **[—]** Анонимный тип в `Select` — удобно внутри запроса, но без имени: наружу — `record`.

Дальше — лестница операторов, и у каждого свой кадр с одной типизированной строкой кода:

- **[32]** `Where` — оставить подходящие. **[33]**
  `Distinct` — убрать повторы, через `GetHashCode`/`Equals`. **[34]** `Take` — первые n. **[35]** `Skip`
  — пропустить n. **[36]** `TakeWhile` — брать, пока условие истинно. **[37]** `SkipWhile` — пропускать,
  пока условие истинно.
- **[38]** `Select` — превратить каждый элемент. **[39]** `SelectMany` — склеить списки списков в одну
  ленту; самый недооценённый оператор.
- **[40]** `Count` — сколько подходящих. **[41]** `Sum` — сумма. **[42]** `Min` — наименьшее. **[43]**
  `Max` — наибольшее. **[44]** `Average` — среднее. **[45]** `Any` — есть ли хоть один, останавливается
  на первом. **[46]** `All` — все ли подходят. **[47]** `Aggregate` — свернуть по своему правилу.
  **[48]** `First` — первый, исключение если пусто. **[49]** `FirstOrDefault` — первый или `null`.
  **[50]** `Single` — ровно один, исключение иначе: утверждение о данных. **[51]** `SingleOrDefault` —
  ноль или один.
- **[52]** `GroupBy` — последовательность групп по ключу, ленивый. **[53]** `ToLookup` — словарь из ключа
  в список сразу, безопасен для отсутствующего ключа.
- **[54]** `Join` — сопоставить два источника по ключу, линия, не квадрат. **[55]** `GroupJoin` — для
  каждого слева группа справа. **[56]** `Zip` — склеить поэлементно.
- **[57]** `OrderBy` — по возрастанию. **[58]** `OrderByDescending` — по убыванию. **[59]** `ThenBy` —
  второй ключ. **[60]** `ToList`, **[61]** `ToArray`, **[62]** `ToDictionary` (исключение на дубликате
  ключа), **[63]** `ToHashSet` — материализация, конец конвейера.

- **[—]** Синтаксис запросов (`from`/`where`/`select`) — чистый сахар над теми же методами; пишите
  методами: композиция, однородность, полнота операторов.
- **[64]** Запрос — значение: `query` переприсваивается под двумя необязательными фильтрами, выполняется
  один раз в конце.
- **[—]** Читаемость против аллокаций: каждый оператор конвейера — объект-перечислитель; но LINQ не
  спасает от плохого алгоритма — `Any` внутри `Where` по другому списку всё равно квадрат.
- **[65]** Мысль раздела: запрос говорит, что вы хотите; цикл говорит, как.

## 4. IQueryable (10 мин · слайды 66–69)

- **[66]** `IEnumerable` выполняет, `IQueryable` описывает.
- **[—]** Тот же запрос над таблицей на миллион строк: загрузить всё и отфильтровать в памяти — не
  вариант. Нужен перевод в SQL.
- **[67]** Две сигнатуры `Where`: `Func<T, bool>` для `IEnumerable`, `Expression<Func<T, bool>>` для
  `IQueryable`. `Expression` превращает лямбду в дерево, а не в метод.
- **[68]** Дерево выражения `o => o.Status == OrderStatus.Paid` — не код, а данные: узел `==`, под ним
  `o.Status` и константа.
- **[—]** Провайдер обходит дерево в момент перебора и генерирует SQL. Вызов своего метода внутри `Where`
  — провайдеру негде его взять: исключение в момент выполнения или, у старых провайдеров, тихая загрузка
  всей таблицы в память.
- **[69]** Мысль раздела: `IQueryable` не выполняет код — описывает его для кого-то другого.

## 5. Extension methods (8 мин · слайды 70–72)

- **[70]** Статический метод, который выглядит как метод экземпляра.
- **[71]** `this` в первом параметре: компилятор переписывает вызов через точку в обычный статический.
  Нет доступа к приватным членам; метод экземпляра всегда побеждает; вызов на `null` не падает.
- **[—]** Уместно: расширить чужой тип, собрать словарь операций (LINQ), сделать цепочку. Неуместно:
  спрятанная зависимость — расширение, которое читает время, конфигурацию или базу.
- **[72]** Мысль раздела: расширение — функция от своих аргументов и ничего больше.
