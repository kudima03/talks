# Лабораторная 1. От исходника до процесса: консольное приложение через CLI

**К лекции:** [Л1. Платформа .NET и dotnet CLI](../L01-platform.md)
**Условие:** всё делается **только из терминала**. IDE в этой лабораторной не используется — ни
чтобы создать проект, ни чтобы собрать, ни чтобы запустить. Текстовый редактор для файлов —
любой.
**Сдаётся вживую:** отчёта нет. Вы садитесь за терминал со своим проектом, показываете
результат и отвечаете на вопросы по любому шагу.

## Что нужно поставить заранее

**Два SDK: .NET (6/7/8/9) и .NET 10.** Оба ставятся с
[dotnet.microsoft.com/download](https://dotnet.microsoft.com/download) для Windows, из пакетных
менеджеров для Linux/macOS, и живут на одной машине рядом. Проект в этой лабораторной
собирается под **.NET 10** — вторая версия нужна затем, чтобы вы своими глазами увидели, что
их на машине несколько и что выбор между ними чем-то управляется. Плюс .NET 8 пригодится
в последующих работах.

## Что должно быть готово

- Консольное приложение `HelloWorld` под `net10.0`, созданное, собранное и запущенное из
  терминала.
- Один пакет из реестра, подключённый командой и вызываемый из кода.
- Результат `dotnet publish` в отдельной папке, запускаемый двумя способами.
- Локальный репозиторий git, в котором нет ни `bin`, ни `obj`, ни папки публикации.

## Шаги

Под каждым шагом — **«Вопрос»**: то, что вы должны уметь объяснить на приёмке. Вопросы
с пометкой **«усложнённый»** — со звёздочкой: их задают тем, у кого основной ответ уже есть.

### 1. Что стоит на машине

```sh
dotnet --list-sdks
dotnet --list-runtimes
dotnet --version
dotnet --info
```

**Вопрос:** сколько .NET SDK установлено на компьютере и какой SDK используется
для сборки проекта в этой папке прямо сейчас? Сколько установлено .NET Runtime и почему
их может быть больше, чем SDK? Что из показанного является SDK, а что — Runtime, чем они
отличаются по составу и назначению? Что из этого необходимо установить на машину, на которую
вы отдаёте готовое .NET-приложение?

### 2. Создать проект

```sh
dotnet new console --name HelloWorld
cd HelloWorld
```

**Вопрос:** какие файлы появились и что делает каждый.

**Вопрос (усложнённый):** где при этом класс `Program` и метод `Main`.

### 3. Прочитать csproj

Откройте `HelloWorld.csproj` и разберите его целиком.

**Вопрос:** любая строка файла — что означает и что изменится, если её убрать или поменять.

**Вопрос (усложнённый):** почему файл такой короткий и откуда сборка знает, какие файлы
компилировать, если они в нём не перечислены. Откуда в `Program.cs` взялся `Console`, если
нет ни одного `using`.

### 4. Добавить зависимость

Пакет — любой на ваш выбор, лишь бы вы могли вызвать какой-нибудь его компонент одной-двумя
строками кода. Например:

```sh
dotnet add package Humanizer.Core
```

Допишите в `Program.cs` вызов какого-либо компонента из пакета и запустите — на приёмке должно
быть видно, что пакет реально работает и компилируется, а не просто числится в файле.

**Вопрос:** какая строка появилась в `csproj` и почему в ней есть версия. Что сделала команда,
кроме правки файла, и откуда пакет взялся у вас на машине.

### 5. Собрать в двух конфигурациях

```sh
dotnet build --configuration Debug
dotnet build --configuration Release
ls -l bin/Debug/net10.0
ls -l bin/Release/net10.0
```

**Вопрос:** чем два набора отличаются, а чем нет. И если размеры файлов у вас получились
практически одинаковыми — что это говорит о том, где именно лежит разница между Debug
и Release.

### 6. Опубликовать

```sh
dotnet publish --configuration Release --output ./out
ls -l out
```

**Вопрос:** каждый файл в `out` — что это и кто его читает. Почему файлов оказалось больше, чем
пять, о которых говорили на лекции. Почему в `out` нет ни исходников, ни `obj`. Почему
`--configuration Release` написан явно, хотя эта команда и без него собирает в Release.

Проверьте руками: уберите из `out` файл `HelloWorld.runtimeconfig.json`, запустите приложение и
прочитайте, что скажет вывод. Верните файл на место. На приёмке этот опыт попросят
повторить и объяснить.

### 7. Запустить двумя способами

Первый — файлом рядом с dll: на Windows это `HelloWorld.exe`, на Linux и macOS тот же файл без
расширения, `./HelloWorld`. Второй — командой `dotnet` с путём к dll:

```sh
cd out
./HelloWorld          # на Windows: .\HelloWorld.exe
dotnet HelloWorld.dll
```

**Вопрос:** чем эти два способа отличаются и почему `dotnet run` для этого не годится.

### 8. Убрать производное из репозитория

```sh
git init
dotnet new gitignore
git add .
git status
```

**Вопрос:** посмотрите на `git status` внимательно. Шаблон закрывает `bin` и `obj`, но папку,
в которую вы опубликовали, — нет: имя `out` вы придумали сами, шаблон о нём не знает. Допишите
её в `.gitignore` сами и добейтесь, чтобы в индекс попадали только исходники. Плюс назовите
причины, по которым производное не коммитят.

### 9. Собрать картинку

Главный вопрос приёмки, его задают всем: **что происходит между вашим `Program.cs` и процессом
в операционной системе.** По шагам, своими словами, у своей машины. Каждый шаг назвать, сказать,
кто его делает, где лежит его результат и на какой машине это происходит.

Это тот вопрос, с которого началась лекция.

## Дополнительное задание (по желанию)

Раз уж у вас стоят два SDK — зафиксируйте для репозитория тот, который постарше:

```sh
dotnet new globaljson --sdk-version <ваша младшая версия из dotnet --list-sdks>
dotnet --version
dotnet build
```

Посмотрите, что изменилось в выводе `dotnet --version` и что сказала сборка. Объясните, при чём
здесь `TargetFramework` вашего проекта. Верните версию 10 и убедитесь, что сборка снова
проходит.

**Вопрос:** зачем такой файл нужен в рабочем репозитории, где у всех своя машина.

## Как проходит приёмка

Вы за своим терминалом, проект уже собран. Принимающий просит показать несколько шагов и
задаёт вопросы по тому, что видит на экране. Прогоните шаги у себя хотя бы раз заранее — на
приёмке не будет времени разбираться, почему команда не находит проект.
