## Сквозные тезисы

- Базу выбирают по запросам, которые будут задавать, а не по данным и не по моде.
- Схема есть всегда: вопрос в том, записана она в базе или размазана по коду.
- Соединение берётся из пула поздно и возвращается рано; `using` — это и есть возврат.
- Читатель — поток строк: в памяти одна строка, соединение занято, пока его перебирают.
- Транзакция без фиксации откатывается сама; всё, что должно быть атомарным, — одна команда базы.
- В текст запроса не попадает ни один байт снаружи: только параметры.
- ORM — генератор SQL и маппинга поверх того же драйвера; SQL она не отменяет.

## 1. Какие бывают базы (15 мин · слайды 2–16)

- **[2]** Раздел: выбор базы переживёт весь остальной код.
- **[—]** Двенадцать лекций обходили базу; две лекции про данные, первая — про драйвер.
- **[3]** Вопрос: какие базы вы знаете и чем они отличаются? «Синтаксисом» — это разница внутри семейства.
- **[4]** Пять семейств: реляционные, документные, ключ-значение, колоночные, графовые. Не знаете, что
  нужно, — нужно реляционное.
- **[5]** Реляционные: строгая схема, связь ссылкой, SQL, транзакции. Документные: документ со своей
  структурой, связь вложенностью, поперёк документов трудно. Граница размыта: PostgreSQL хранит JSON в колонке
  с индексом — одна база вместо двух.
- **[6]** «Без схемы» не значит «без структуры»: структура в коде, старые документы остаются в старой форме,
  код читает обе. Та же миграция, только неявная.
- **[7]** Ключ-значение — кэш, сессии, счётчики; не для поиска. Аналитические колоночные — суммы по
  миллиардам строк. Широкостолбцовые — запись на много узлов. Графовые — «друзья друзей». Поисковые и
  векторные — данные копируют из основной.
- **[—]** Ключ-значение — ещё и строительный блок: первичный ключ — тот же словарь. Узкие семейства —
  временные ряды.
- **[8]** Четыре вопроса: форма данных, запросы, согласованность, масштабирование. Главный — запросы.
- **[9]** Одни и те же заказы: «по номеру» быстро везде; «сумма по клиентам за квартал» и «заказы с товаром X»
  — группировка и соединение по индексу против обхода всех документов и перебора ключей. Разница в тысячи раз.
- **[10]** Согласованность: транзакции («сохранил — вижу») против доступности («сохранил — не вижу, секунды»).
  Деньги и лайки. Реплика для чтения отстаёт так же: своё читают оттуда, куда писали.
- **[—]** Теорема: при разрыве сети нельзя сохранить и согласованность, и доступность; знать, что выбрала
  ваша база.
- **[11]** Масштабирование: реляционная — большая машина и реплики, на этом долго. Распределённая «на вырост»
  — сложность каждый день. Сначала измерить, потом менять.
- **[12]** Вопрос: интернет-магазин — какая база?
- **[13]** Магазин — реляционная: отчёты поперёк заказов, клиент в тысяче заказов. Лента событий игры —
  широкостолбцовая. Запросы узнают заранее: какие отчёты, по чему искать, что хранить как историю.
- **[14]** Базы сочетают: PostgreSQL — источник правды, Redis — кэш, поисковая, аналитическая. Каждая база —
  копии, обновления, мониторинг, человек; транзакции между двумя базами не бывает.
- **[15]** Почему PostgreSQL: открытый, строгий к стандарту, JSON, поиск, расширения. SQLite — для локальных
  утилит. В проде — управляемый сервис: код тот же.
- **[16]** Мысль раздела: семейства отличаются тем, что делают быстро; базу выбирают по запросам.

- **[18]** Одна схема: `customers` и `orders`, внешний ключ, индекс, запрос с `join`. Связь — ссылкой. SQL

- **[20]** Ограничения — последняя линия: проверяются при любой записи, кто бы её ни делал. Два одновременных

- **[—]** Представления и хранимые процедуры — осознанные исключения; логика живёт в сервисе.
- **[—]** Мысль раздела голосом: таблицы, ключи, индексы, соединения, транзакции — язык, на котором говорим

## 3. ADO.NET — как оно работает без магии (35 мин · слайды 21–50)

- **[21]** Раздел: под любой ORM лежит ровно это.
- **[22]** Ваш код → ADO.NET → драйвер (Npgsql) → протокол → база. Пять абстракций: соединение, команда,
  параметр, читатель, транзакция.
- **[23]** Вопрос: что дорогого произошло при «открыть»? TCP, TLS, аутентификация — десятки миллисекунд.
- **[24]** Пул: `Open` берёт свободное, `Close` возвращает. Настоящее соединение живёт долго, ваш объект —
  секунды. Предел — порядка ста на процесс.
- **[25]** Пул — на строку подключения и на процесс: три экземпляра — триста соединений; сумма пулов не больше
  предела базы; много экземпляров — внешний пул. При возврате драйвер сбрасывает состояние сессии.
- **[26]** Два правила: открывать поздно, закрывать рано; всегда `using` — `Dispose` и есть возврат в пул.
  Такси вызывают на поездку.
- **[27]** Утечка, запуск: пул из трёх, четвёртое открытие — `The connection pool has been exhausted`.
  Выглядит как «база тормозит». Метрика «занято» на уровне предела — подпись утечки.
- **[28]** Листинг `OrderCounter`: источник данных — singleton, открыть перед запросом, параметр, одно
  значение; `await using` возвращает в пул при любом выходе.
- **[29]** Источник владеет пулом; строка подключения с паролем — секрет; токен доезжает до базы отменой
  запроса; тип параметра выводится, `null` — `DBNull.Value`; `count` — `long`: с `(int)` —
  `InvalidCastException` при выполнении.
- **[—]** Именованные параметры (`@name`) против позиционных (`$1`): в курсе именованные.
- **[30]** Три вида: `ExecuteScalar` — одно значение, `ExecuteReader` — поток строк, `ExecuteNonQuery` — число
  затронутых строк; ноль строк у `update` — «не найдено». Синхронных версий в сервисе нет.
- **[31]** Два null, запуск: `max` без отгрузок — `DBNull`; строк нет — `null`.
- **[32]** Число поездок важнее размера каждой: 2 против 101. N + 1 живёт в любом коде с запросом в цикле.
- **[—]** Пакет команд: несколько независимых команд одной поездкой.
- **[33]** Страница: «следующие после ключа» по индексу — за одно время; «пропустить и взять» перебирает
  пропущенные. В API — курсор.
- **[34]** Листинг читателя: номера колонок до цикла, `ReadAsync` по строке, `yield return`, проверка `null`.
  Тип не совпал — исключение при чтении.
- **[35]** Запуск: две строки `OrderRow`. Тот же контракт, что перечислитель (Л5); в памяти одна строка; до
  HTTP-ответа без списка; соединение открыто, пока перебирают.
- **[—]** Сборка объекта — в один статический метод на таблицу: ручной аналог того, что сгенерирует ORM.
- **[36]** Вопрос: прочитали три строки и вышли по `break` — что с соединением?
- **[37]** Один читатель на соединение, запуск: `A command is already in progress`. `using` закрывает
  читатель и делает `break` безопасным.
- **[—]** `DataTable`/`DataSet` — узнавайте, не пишите. Таймаут команды меньше таймаута клиента. Даты — во
  всемирном времени, тип с поясом. Метаданные схемы: база может рассказать о себе. Подготовленные запросы.
- **[38]** `DbConnection`, `DbCommand`: переносимость механики, не SQL. Тесты доступа к данным — на той базе,
  что в проде (Л15).
- **[39]** Транзакция, вставка: `BeginTransactionAsync` на соединении, команда в транзакции, `returning id`.
- **[40]** Условие в `update`, ноль строк — исключение, `CommitAsync` в конце. Запуск: второй заказ не
  остался, явного отката нет.
- **[41]** Проверка остатка — в SQL: «прочитать, проверить, записать» продаёт два при одном на складе. Что
  должно быть атомарным — одна команда базы.
- **[42]** Правила: короткая (вызовы наружу — до неё); откат сам; вложенных нет, есть точки сохранения; повтор
  временной ошибки — всей транзакции; версия строки — оптимистичная блокировка, 409; блокировка при чтении —
  пессимистичная.
- **[—]** Уровни изоляции — в Л14.
- **[43]** Вопрос: запрос собран плюсом из текста и значения — что не так?
- **[44]** Инъекция, запуск: `1 or 1=1` — все заказы; `1; drop table orders; --` — таблицы нет. Данные
  попали в текст программы.
- **[—]** Вопрос голосом: «экранировать кавычки»? Двадцать лет обходов; гонка, которую проиграете.
- **[45]** Параметр, запуск: те же строки — ноль совпадений, таблица цела. Значение уходит отдельно от
  текста. Бонус: один текст — один план.
- **[46]** Фраза: в текст запроса не попадает ни один байт снаружи. Только параметры.
- **[47]** Где параметр не спасает: шаблон `like`, имена таблиц и колонок (белый список), сырой SQL в ORM.
  «Снаружи» — и то, что лежит в базе.
- **[—]** Как убедиться: в логе текст с именами параметров; тест со строкой с кавычкой (Л15).
- **[48]** Вопрос: что не так с `select *`?
- **[49]** Колонки явно: лишний трафик, сдвиг порядковых номеров, скрытая зависимость. SQL живёт в классе
  хранилища; ошибки базы там же становятся исключениями домена.
- **[—]** Логировать длительность и текст с именами параметров, не значения.
- **[50]** Мысль раздела: взять поздно, вернуть рано; читатель — поток; транзакция откатывается сама; данные
  не должны становиться программой.

## 4. Мост к ORM (20 мин · слайды 51–60)

- **[51]** Раздел: ORM не заменяет драйвер, она пишет то, что вы писали руками.
- **[52]** Вопрос: сколько строк про «что» и сколько про «как»? Одна и десять.
- **[53]** Три боли: маппинг руками, дублирование, схема меняется — компилятор не знает. «SQL сложный» в
  списке нет. Двадцать таблиц — две тысячи строк механики. Для пяти запросов ORM не нужна.
- **[—]** Скучный код — опасный код: «дата в поле суммы». Тесты с настоящей базой ловят после, компилятор —
  до. Промежуточные ответы: библиотека-маппер и генератор кода по SQL.
- **[54]** Реляционная алгебра ↔ SQL ↔ LINQ: выборка, проекция, соединение, группировка, объединение,
  сортировка. Это дизайн. Края: оконные функции, рекурсия — пишите SQL.
- **[55]** `Where` → `WHERE`, `Select` → две колонки, `OrderByDescending` → `ORDER BY DESC`, `Take` → `LIMIT`;
  `customerId` стал параметром — инъекция невозможна по построению.
- **[—]** Сопоставление имён и конвертер перечисления — как для JSON в Л9.
- **[56]** Механизм: лямбда → дерево выражений (Л5) → провайдер → SQL и параметры → драйвер → читатель →
  объекты. Перевод кэшируется. Цена: абстракция протекает.
- **[—]** Отслеживание изменений: ORM пишет `update` за вас. Три боли закрыты.
- **[57]** Вопрос: свой метод в `Where` над таблицей?
- **[58]** Исключение при выполнении — или вычисление на клиенте: миллион строк в память ради десяти.
  Родственное — N + 1 по обращению к свойству. Лечится одним: смотреть SQL.
- **[—]** Провайдер логирует каждый запрос; в разработке категория включена.
- **[59]** `IQueryable` — описание SQL. Три шага: представить SQL, написать LINQ, посмотреть в лог. ORM —
  инструмент, а не архитектура.
- **[60]** Мысль раздела: ORM — генератор поверх драйвера; граница между базой и памятью — ваша забота.

## Открытые вопросы

Авторское решение, не менять по умолчанию:

1. **Кадр 45 показывает запрос с `customer_id::text = @customerId`**, а не листинг `OrderCounter`: в `int`-параметр
   строку `1 or 1=1` положить нельзя, а кадру нужен тот же ввод, что на кадре 44. Сценарий говорит о параметре
   в общем виде.
2. **Кадры 44–45 считают `count(*)`, вопрос на кадре 43 и сценарий говорят о `select *`.** Вывод на слайдах —
   с настоящего запуска; со звёздочкой он не поместился бы.
3. **Утверждение сценария про даты** («драйвер откажется писать местное время») на запуске не воспроизвелось:
   `AddWithValue` с `DateTime.Now` Npgsql 10 записал без исключения (тип параметра вывелся как время без
   пояса). Кадра про это нет; текст сценария не менялся.
4. **Латинский шрифт-замена (Latin Modern) не проверялся** для этой колоды; собиралась с PT Sans.
