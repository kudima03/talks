# Л8. ASP.NET Core: хост и конвейер запроса — тезисы

**Длительность:** 80 минут
**Цель:** показать, что приложение — это хост плюс конвейер, и что вы туда встраиваетесь.
**Полный текст лекции:** [L08-host-and-pipeline.md](L08-host-and-pipeline.md)
**Слайды:** [slides/L08-host-and-pipeline-slides.tex](slides/L08-host-and-pipeline-slides.tex) —

Первая лекция, где мы пишем сервис. Раздел 1 — шесть строк `Program.cs` как фазы жизни: builder, регистрация,
`Build`, конвейер, `Run`, корректная остановка. Раздел 2 — Kestrel: где слушать, HTTPS локально, версии,
лимиты. Раздел 3 — конвейер: middleware как делегат, явный `Program.cs`, порядок как семантика, обработка
ошибок в одном месте, короткое замыкание. Раздел 4 — `HttpContext` и почему его не носят вглубь. Раздел 5 —
фоновая работа в том же хосте: `BackgroundService`, Quartz, идемпотентность.

## Сквозные тезисы

- Приложение — хост плюс конвейер. До `Build` описываем, после `Build` собираем конвейер, `Run` запускает и
  корректно останавливает.
- Всё, что может быть настроено неправильно, ломается до `Run`: падать сразу и громко.
- Адрес, схема и лимиты сервера — конфигурация окружения, а не код.
- Middleware — делегат, который знает следующего. Порядок регистрации — это семантика.
- Ошибки ловятся в одном месте, снаружи всех: в лог всё, наружу минимум.
- `HttpContext` не уходит дальше эндпоинта: берите нужное на границе и передавайте обычными параметрами.
- Фоновая работа запускается столько раз, сколько экземпляров и перезапусков. Повтор должен быть безвреден.

## 1. Точка входа и жизненный цикл (20 мин · слайды 2–14)

- **[2]** Раздел: шесть строк, и в них вся структура сервиса.
- **[—]** Прошлая лабораторная — сервер на сокетах; сегодня фреймворк, который делает это за вас. С этой
  лабораторной сервис живёт до конца курса.
- **[3]** Вопрос: сколько строк нужно для HTTP-сервера? «Пять» — ближе всех.
- **[4]** Листинг: создать builder, зарегистрировать сервисы, собрать приложение, собрать конвейер,
  запустить. Каждая строка — фаза.
- **[5]** `CreateBuilder` уже собрал: конфигурацию (файлы, переменные, `args`), логирование, пустой
  контейнер, окружение, Kestrel. Конфигурация и контейнер — Л10, логирование — Л12.
- **[—]** Источники конфигурации: `appsettings.json` → `appsettings.{окружение}.json` → переменные окружения →
  `args`; позднее перекрывает раннее. `ASPNETCORE_ENVIRONMENT` не задана — Production.
- **[6]** Регистрация — описание, а не создание (как отложенный запрос из Л5). Модули фреймворка — `Add…`,
  метод расширения с десятком регистраций внутри. Свой сервис — `AddScoped<IOrderService, OrderService>()`:
  интерфейс, реализация, время жизни (Scoped — на запрос, Singleton — на всё, Transient — на обращение; Л10).
- **[—]** В Development `Build` проверяет каждую регистрацию: незарегистрированная зависимость — падение на
  старте с понятным сообщением, а не на первом запросе.
- **[—]** Маршрут — путь и лямбда; обработчик — делегат из Л4. Строка уходит текстом, объект — JSON.
  Минимальный API подробно — Л9.
- **[—]** Всё до `Run` — один раз при старте; конвейер — на каждый запрос. `Run` не возвращается.
- **[7]** Где ломаться: на старте старая версия продолжает работать; на первом запросе падает новая — при
  клиентах.
- **[8]** Две фазы и `Build` как граница. На `Build` контейнер заморожен (регистрация после — исключение:
  коллекция только для чтения), конфигурация зафиксирована, сервер создан; `app` собирает конвейер и
  запускается.
- **[9]** Хост — контейнер для всего, что живёт в процессе; сервер — один из жильцов. Конфигурация,
  контейнер, логгер одинаковы в любом приложении на платформе.
- **[—]** Три builder: веб, рабочий сервис (`dotnet new worker`, без порта), Slim — меньше умолчаний для
  обрезки и AOT.
- **[—]** На `Run`: фоновые сервисы стартуют → сервер слушает → «приложение запущено» → ожидание сигнала.
- **[10]** Вопрос: откуда сигнал остановки? Локально Ctrl+C; на сервере — сигнал и время, потом убивают.
- **[11]** Остановка: сервер не принимает новые соединения → текущие запросы дорабатывают → фоновые сервисы
  получают токен → `Dispose` → процесс завершён.
- **[11]** `HostOptions.ShutdownTimeout` — по умолчанию 30 секунд; меньше, чем ждёт тот, кто
  запустил процесс. Не уложились — работа брошена.
- **[11]** Контейнер вызывает `Dispose` в порядке, обратном созданию, и только для того, чем владеет (Л6).
- **[—]** Обходить остановку (`Environment.Exit`, игнорировать токен) — обрезанные ответы, недописанные
  файлы, незакрытые транзакции.
- **[—]** `IHostApplicationLifetime`: `ApplicationStarted`, `ApplicationStopping`, `StopApplication` —
  остановка из кода тем же корректным путём.
- **[12]** Первые строки лога: адрес, окружение, папка. Половина «почему не открывается» решается здесь.
- **[13]** Development против Production: страница с трассировкой, подробные логи, проверка при `Build`.
  Разница — в конфигурации, а не в коде (Л10).
- **[—]** Не видно в `Program.cs`: `Sdk="Microsoft.NET.Sdk.Web"` в манифесте сборки и `launchSettings.json`
  только для локального запуска. Для лабораторной — пустой шаблон `web`.
- **[14]** Мысль раздела: приложение — хост плюс конвейер.

## 2. Kestrel и адрес (10 мин · слайды 15–18)

- **[15]** Раздел: Kestrel — ваш сервер на сокетах, только правильный.
- **[16]** Kestrel против сервера из лабораторной 7: HTTP/1.1, 2, 3, TLS, пулы буферов, лимиты.
- **[17]** Где слушать: `ASPNETCORE_URLS`, `--urls` (аргумент побеждает переменную), `ASPNETCORE_HTTP_PORTS`.
  Секция `Kestrel` в `appsettings.json` перекрывает их все — выбирайте один способ. В контейнере — порт 8080.
  Адрес — свойство окружения.
- **[—]** HTTPS локально: `dotnet dev-certs https --trust`; сертификат подписан сам собой. Подробно
  сертификаты не разбираем; в проде сертификат — конфигурация.
- **[—]** Версии: HTTP/1.1 и HTTP/2 по умолчанию, HTTP/2 — поверх TLS; HTTP/3 — явно и с поддержкой ОС.
- **[18]** Лимиты по умолчанию: тело 30 000 000 байт, заголовки 32 КБ и 100 штук, таймаут заголовков 30 с,
  простой 2 мин 10 с.
- **[—]** Поднять лимит — для всего сервера или для одного маршрута. Сверх лимита — `413` на первом чтении тела.
- **[—]** На сервере из прошлой лабораторной этой защиты не было: один клиент мог занять всю память.
- **[—]** Мысль раздела: Kestrel отсекает лишнее за вас; где слушать — решает окружение.

## 3. Конвейер запроса (25 мин · слайды 19–35)

- **[19]** Раздел: middleware — делегат, который знает следующего.
- **[—]** Каждому запросу нужно одно и то же: лог, кто, можно ли, сжатие, исключения, файлы. В каждом
  обработчике — сто копий; в одном месте — метод на тысячу строк.
- **[20]** Конвейер: ошибки → логирование → маршрутизация → аутентификация → авторизация → обработчик;
  ответ возвращается по той же цепочке.
- **[21]** Определение: делегат получает контекст и следующего и решает — вызвать ли, что до, что после.
- **[—]** Аналогия: досмотр в аэропорту.
- **[22]** Явный конвейер в `Program.cs`: порядок строк `Use` — порядок, в котором идёт запрос; `Map` —
  конец цепочки. В шести строках из начала стандартные компоненты расставлены за вас.
- **[—]** Три возможности: до и после — лог; до — аутентификация; вокруг — ошибки; не вызывать — файл.
- **[—]** Матрёшка: `RequestDelegate` и функция от следующего; при старте складывается в один делегат —
  без цикла и рефлексии.
- **[23]** Middleware одной лямбдой: засечь время, `await next`, записать метод, путь, статус, длительность.
  Шаблон лога с параметрами — Л12.
- **[—]** После `next` менять ответ поздно: заголовки ушли с первым байтом тела.
- **[24]** Порядок — семантика: аутентификация до авторизации, ошибки снаружи всех, маршрутизация до
  авторизации. Анализатор этого не ловит: авторизация до маршрутизации падает на первом запросе к
  защищённому маршруту. Ваши компоненты не проверяет никто.
- **[—]** Ветвление: `Map` — своя цепочка, в основную не возвращается; `UseWhen` — вставка, возвращается.
- **[25]** Конвейер по умолчанию: страница ошибок разработчика → фильтрация хостов → маршрутизация →
  аутентификация и авторизация → ваши → конечные точки.
- **[—]** Как убедиться: middleware до `UseRouting` не видит выбранного обработчика, после — видит. Без явного
  `UseRouting` маршрутизация стоит перед вашим первым `Use`.
- **[26]** Три способа: лямбда — для трёх строк; класс с `InvokeAsync` — для всего остального;
  `IMiddleware` — объект на запрос, редко.
- **[27]** Класс с `InvokeAsync`: конструктор — один раз, `InvokeAsync` — на каждый запрос, его параметры —
  из контейнера запроса.
- **[—]** Регистрация методом расширения `Use…`: файл запуска читается как словарь.
- **[28]** Пленённая зависимость: в конструктор — только то, что живёт вечно; «на запрос» — параметрами
  `InvokeAsync`. Л10.
- **[29]** Вопрос: граница процесса в сервисе — где? Не в каждом обработчике, а в одном middleware.
- **[30]** `ErrorHandlingMiddleware` целиком.
- **[31]** Пять решений: `try` вокруг `next` (поэтому первый), `when (!HasStarted)`, `switch` по типу (Л9
  добавит 422), в лог всё, наружу минимум и `traceId`.
- **[—]** Отмена — не ошибка: клиент ушёл, отвечать некому, в лог одна строка уровня Information (Л6).
- **[32]** Проверка руками: `curl` на 404 и 500. По-настоящему — тест, поднимающий приложение в памяти, Л15.
- **[—]** Один middleware против `try/catch` в каждом: дублирование и утечка деталей.
- **[—]** Принцип: одно место, снаружи всех, наружу минимум, в лог всё. Встроенный `IExceptionHandler` —
  то же самое.
- **[33]** Короткое замыкание: не вызвал `next` — ответ сформирован здесь.
- **[—]** Кто отвечает сам: здоровье, статические файлы, ограничение частоты (429), `OPTIONS`, нет токена
  (401). Стоит после проверки токена — сначала потребует токен.
- **[—]** Middleware — для всех запросов; фильтр конечной точки — для одного маршрута, видит параметры (Л9).
- **[34]** Забытый `next`: пустой 200 на всё.
- **[—]** Стоимость: цепочка дешёвая, дорого содержимое. Тело читается один раз; буферизация стоит памяти.
- **[35]** Мысль раздела: цепочка делегатов, порядок — семантика, ошибки в одном месте.

## 4. HttpContext (10 мин · слайды 36–42)

- **[36]** Раздел: всё о запросе в одном объекте.
- **[37]** Один объект на запрос: `Request`, `Response`, `User`, `RequestAborted`, `Items`, `Features`,
  `TraceIdentifier`, `RequestServices`, `Connection`.
- **[37]** `Request` и `Response`: всё разобрано; тело — поток, читается один раз; `HasStarted`.
- **[37]** `User` (Л11), `RequestAborted` — протягивать до базы, `TraceIdentifier` — в каждую строку лога (Л12).
- **[37]** `Items` — словарь из `object` в `object`; для структурного — свой тип «на запрос» (Л10).
- **[37]** `Features`, `RequestServices` (Л10), `Connection`: адрес — точка выхода в сеть, а не человек.
- **[38]** Вопрос: передать сервису `HttpContext` или идентификатор? Идентификатор.
- **[39]** Три цены: только внутри HTTP; живёт с запросом и не потокобезопасен; сигнатура врёт.
- **[40]** Контекст не уходит дальше эндпоинта: сервис получает `userId` и токен.
- **[41]** `ICurrentUser`: веб-реализация читает контекст, в тесте — заглушка, в фоне — системный
  пользователь. `IHttpContextAccessor` в бизнес-логике — сигнал на ревью.
- **[—]** Фоновой работе — скопированные значения, а не контекст.
- **[42]** Мысль раздела: берите нужное на границе.

## 5. Фоновая работа в том же хосте (15 мин · слайды 43–54)

- **[43]** Раздел: хост запускает не только сервер.
- **[44]** `IHostedService`: старт по порядку регистрации, остановка в обратном; веб-сервер запускается так же.
- **[44]** Хост ждёт каждый `StartAsync` по очереди: медленный старт держит весь запуск. `BackgroundService`
  в .NET 10 запуск не держит, даже код до первого `await`. Долгая инициализация — внутри фоновой работы.
- **[45]** `CleanupService`: `PeriodicTimer` с токеном, `try` внутри цикла, фильтр на отмену, регистрация
  одной строкой.
- **[46]** Четыре решения — каждое чей-то инцидент.
- **[46]** Исключение из `ExecuteAsync` останавливает всё приложение — так задумано; код выхода при этом 0.
- **[47]** Зависимости «на запрос» в фоне: фабрика областей, одна итерация — одна область (Л10).
- **[48]** Quartz: Job, Trigger, Scheduler; cron с секундами первым полем.
- **[—]** Сверх таймера: пропущенные запуски, данные задания, пауза, хранение в базе.
- **[49]** Задание с `[DisallowConcurrentExecution]`, ключ, cron-триггер, `WaitForJobsToComplete`. В Quartz.NET 4
  токен остановки — второй параметр `Execute`.
- **[—]** Три ночи по UTC — шесть утра в Минске; перевод часов; явный часовой пояс для расписаний людей.
- **[—]** Наложение: триггер раз в 30 минут, работа 40 — без атрибута два запуска одновременно.
- **[50]** Вопрос: два экземпляра, задание в три ночи — сколько счетов? Два.
- **[51]** Три пути к повтору: два экземпляра, остановка посередине, наложение.
- **[52]** Идемпотентность: пометка «отправлено», ключ «дата + тип», подтверждение после обработки.
  То же слово, что у методов HTTP в Л7.
- **[—]** Очередь: «хотя бы один раз» — обработчик обязан быть идемпотентным.
- **[—]** Кластерный режим Quartz и распределённая блокировка (Л12) не отменяют идемпотентности.
- **[—]** Тяжёлую работу — в отдельный рабочий сервис; признак — задержки повторяют график фоновой работы.
- **[53]** Фоновая работа невидима: лог начала и конца, метрика «последний успешный запуск», оповещение.
- **[54]** Мысль раздела: пишите так, чтобы повтор был безвреден.
- **[—]** Итог: хост и конвейер. Дальше (Л9) — обработчики, параметры, JSON.

## Открытые вопросы

Авторское решение, не менять по умолчанию:

1. **Логирование внутри обработки ошибок не видит упавших запросов.** В порядке «ошибки → логирование»
   (кадры 20, 22) исключение пролетает сквозь middleware логирования, и его код после `next` не выполняется:
   на `/orders/404` и `/orders/500` строки «метод, путь, статус» нет, есть только запись обработчика ошибок.
   Проверено запуском. Лабораторная ждёт «одну строку на запрос». Варианты: логирование снаружи ошибок
   (тогда оно видит итоговый 500, но «ошибки первыми» перестаёт быть правилом) или `try/finally` в
   логировании (тогда в лог попадает статус до обработчика ошибок).
2. **`ErrorHandlingMiddleware` превращает 413 от Kestrel в 500.** Тело сверх лимита бросает
   `BadHttpRequestException` при чтении, и ветка `_` отдаёт «Internal error». Проверено запуском. Если это
   важно для лабораторной — ветка `BadHttpRequestException bad => (bad.StatusCode, …)`.
3. **Латинский шрифт-замена (Latin Modern) не проверялся** для этой колоды; собиралась с PT Sans.
