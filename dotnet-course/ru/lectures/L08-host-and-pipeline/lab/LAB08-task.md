# Лабораторная 8. Первый сервис: конвейер, ошибки в одном месте и фоновая задача

**К лекции:** [Л8. ASP.NET Core: хост и конвейер запроса](../L08-host-and-pipeline.md)
**Условие:** проекты создаются, собираются и запускаются **из терминала**, как и раньше. Код
пишется в любом редакторе. Запросы к сервису — `curl`.
**Сдаётся вживую:** отчёта нет. Вы садитесь за терминал со своим проектом, показываете
результат и отвечаете на вопросы по любому шагу.

## Что нужно поставить заранее

Ничего нового: хватит .NET 10 SDK и `curl`. Нужны `Shop.Domain` из прошлых лабораторных и
`Shop.RawServer` из седьмой — сервер на сокетах с `OrderStore` внутри. Эта лабораторная
продолжает седьмую: те же маршруты и те же заказы, но вместо сокетов — хост и Kestrel. Проект
`Shop.Api`, который вы создадите сегодня, живёт до конца курса.

## Что должно быть готово

- Веб-проект `Shop.Api` по пустому шаблону `web`, со ссылкой на `Shop.Domain`. Он отвечает на
  те же три маршрута, что и сервер на сокетах, плюс `/health`.
- Отсутствующий заказ — **исключение домена** `NotFoundException`, а не ответ 404, собранный в
  обработчике руками.
- Свой middleware **обработки ошибок** — класс, первый в конвейере: в лог всё, наружу минимум.
- Свой middleware **логирования запросов** — класс: ровно одна строка в логе на каждый запрос,
  включая упавшие.
- **Фоновая задача** на `BackgroundService` с `PeriodicTimer`, которая останавливается по Ctrl+C
  за доли секунды.
- Сборка всех проектов без единого предупреждения.
- Проекты под git.

## Что строим

| Тип или файл | Где | Что это |
|---|---|---|
| `NotFoundException` | `Shop.Domain` | исключение домена «нет такого» — наследник `DomainException` из четвёртой лабораторной |
| `OrderStore` | `Shop.Api` | хранилище заказов, перенесённое из `Shop.RawServer` |
| `IOrderService`, `OrderService` | `Shop.Api` | свой сервис: заказы по номеру, отсутствие — исключение |
| `ErrorHandlingMiddleware` | `Shop.Api` | исключение → HTTP-ответ, в одном месте |
| `RequestLoggingMiddleware` | `Shop.Api` | строка в логе на каждый запрос |
| `UseErrorHandling`, `UseRequestLogging` | `Shop.Api` | методы расширения: конвейер читается как список того, что он делает |
| `OrderStatsService` | `Shop.Api` | фоновая задача: раз в 10 секунд — число заказов по статусам |

Маршруты сервиса:

| Маршрут | Что отвечает |
|---|---|
| `GET /` | приветствие, как у сервера на сокетах |
| `GET /orders` | строка на каждый заказ, как `list` в оболочке |
| `GET /orders/{n}` | один заказ; нет такого — `404` с JSON `{"error": ..., "traceId": ...}` |
| `GET /health` | `Healthy` |
| `GET /fail/{kind}` | тестовый: бросает исключение, чтобы проверить middleware |

Сессия может выглядеть так (номера, заказы и `traceId` у вас свои; заголовки ответа здесь не
показаны):

```text
$ curl http://localhost:5272/orders
1  Ann Smith  Paid  300.00
2  Bob Brown  Created  120.00
$ curl http://localhost:5272/orders/7
{"error":"no order 7","traceId":"0HNPV2H5T7K53:00000001"}
$ curl http://localhost:5272/fail/boom
{"error":"Internal error","traceId":"0HNPV2H5T7K54:00000001"}
```

### 3. Нет заказа — исключение домена

Обработчик не должен решать, каким HTTP-ответом выражается «нет такого заказа». Он бросает, а
решает одно место снаружи — его вы напишете на следующем шаге.

1. В `Shop.Domain` создайте `NotFoundException` — `sealed`-наследник `DomainException` из
   четвёртой лабораторной. Конструктор принимает сообщение.

   номеру — и класс `OrderService`, который получает `OrderStore` в конструкторе. Заказ по
   номеру возвращает `Order`, а не `Order?`: нет заказа — `NotFoundException` с сообщением

3. Зарегистрируйте сервис, как на слайде с регистрацией:


6. Остановите и запустите в другом окружении, снова `curl -i` на `/orders/7`:

### 4. Ошибки — в одном месте

1. Напишите класс `ErrorHandlingMiddleware` по образцу лекции: конструктор принимает
   следующий `RequestDelegate` и `ILogger<ErrorHandlingMiddleware>`, метод
   `InvokeAsync(HttpContext context)` оборачивает `await next(context)` в `try`.
2. В `catch` с фильтром `when (!context.Response.HasStarted)` выберите статус и сообщение
   switch-выражением по типу исключения: `NotFoundException` — `404` и сообщение исключения,
   всё остальное — `500` и `Internal error`.
3. Запишите исключение в лог **целиком** — первым параметром `LogError`, путь и статус —
   параметрами шаблона. Ответ — JSON с двумя полями, `error` и `traceId`
   (`context.TraceIdentifier`).
4. Добавьте ветку, которой нет в листинге лекции: **отмену**. Если клиент ушёл
   (`context.RequestAborted` отменён) и прилетело `OperationCanceledException`, в ответ ничего
   не пишите, а в лог — одну строку уровня `Information`. Эта ветка стоит выше общей.
5. Напишите статический класс с методом расширения `UseErrorHandling` над
   `IApplicationBuilder` — внутри одна строка `UseMiddleware<ErrorHandlingMiddleware>()`.
   Вызовите его **первым** после `Build`.
6. Добавьте тестовый эндпоинт:

   ```csharp
   app.MapGet("/fail/{kind}", async (string kind, HttpContext context) =>
   {
       if (kind == "slow")
       {
           await Task.Delay(TimeSpan.FromSeconds(10), context.RequestAborted);
       }
       if (kind == "late")
       {
           await context.Response.WriteAsync("partial\n");
       }
       throw new InvalidOperationException($"Test failure: {kind}");
   });
   ```

7. Проверьте: `curl -i` на `/orders/7` и `/fail/boom`, затем `curl -i --max-time 1` на

**Вопрос:** в ответе на `/fail/boom` нет текста исключения, а в ответе на `/orders/7` есть.

**Вопрос:** почему отмена — `Information`, а не `Error`? Что было бы в логе без этой ветки?

**Вопрос (усложнённый):** выполните `curl -i` на `/fail/late`. Что напечатал `curl` и каким

**Вопрос (усложнённый):** Kestrel отвечает `413` на тело больше 30 МБ. Если такое тело придёт в

### 5. Строка на каждый запрос — и та, которой нет

1. Напишите класс `RequestLoggingMiddleware`: засечь время (`Stopwatch.GetTimestamp()`),
   `await next(context)`, записать в лог метод, путь, статус ответа и длительность —
   **шаблоном с параметрами**, не интерполяцией.
2. Метод расширения `UseRequestLogging`; вызов — вторым, сразу после `UseErrorHandling`.
3. Запустите и выполните по одному `curl` на `/`, `/orders/1`, `/orders/7`, `/fail/boom`.
   Посчитайте строки `RequestLoggingMiddleware` в логе: их должно быть четыре. Сколько их?
4. Разберитесь, почему у двух запросов строки нет. Исправьте это, **не меняя порядок**
   компонентов: оберните `await next(context)` в `try` с `catch`, у которого фильтр вызывает
   ваш метод записи в лог и возвращает `false`.

   ```csharp
   catch (Exception e) when (LogFailed(context, started, e))
   {
   }
   ```

   Фильтр выполняется до того, как исключение кого-то поймало. Он вернул `false` — значит,
   этот `catch` исключение не ловит, и оно летит дальше, к обработчику ошибок. Для упавшего
   запроса пишите вместо статуса тип исключения: статус ещё не выбран, его выберет
   `ErrorHandlingMiddleware`.
5. Повторите четыре запроса: теперь строк четыре.

**Вопрос:** почему без фильтра у упавших запросов не было строки? Где был код после `await
next(context)` в тот момент?

**Вопрос:** чем фильтр, который возвращает `false`, отличается от `catch`, который пишет в лог
и делает `throw;`? Что случится, если во втором варианте кто-то однажды напишет `throw e;`?

**Вопрос (усложнённый):** есть ещё два способа получить строку на каждый запрос — поставить
логирование **перед** обработкой ошибок и записать строку в `finally`. Проверьте оба. Какой
статус каждый из них записал для `/orders/7` и чем каждый платит?

## Как проходит приёмка

Вы за своим терминалом, `Shop.Api` запущен. Принимающий выполняет `curl` на ваши маршруты —
правильные, несуществующие и бросающие, — смотрит вместе с вами в лог, просит нажать Ctrl+C и
может попросить изменить одну строку: убрать `await` перед `next`, переставить `Use`, убрать
фильтр `when`, поменять зависимость фоновой задачи — и объяснить, что сломалось.
