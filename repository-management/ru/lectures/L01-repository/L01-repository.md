# Л1. Репозиторий — центр мироздания проекта

**Длительность:** 80 минут
**Цель:** студент понимает, что такое репозиторий как система, владеет моделью Git и знает, чем защищается main.
**Состояние:** кадры и тезисы к ним. Сплошной текст для произнесения пишется после того, как структура утверждена.

---

## 1. Философия (15)

[СЛАЙД 7 — заголовок раздела и вопрос: «что должно лежать в репозитории, кроме кода?»]

[СЛАЙД 8 — диаграмма: репозиторий в центре; вокруг код, тесты, документация, задачи, решения, CI и правила, зависимости, релизы]

Всё, что нужно знать о продукте, лежит в одном месте — или не существует.

[СЛАЙД 9 — «Проверка: человек с улицы»: пять вопросов новичка и где на них отвечает репозиторий]

Self-contained: новый участник ничего не спрашивает, он клонирует и работает. Этот участник может быть агентом.

[СЛАЙД 10 — «Работа — это поставка артефактов»: «изучал», «нашёл проблему», «придумал», «обсудили», «почти готово» → документ, issue, черновой PR, комментарий, коммит]

Вся работа — поставка цифровых артефактов. «Делал, думал, анализировал» без следа — имитация.

[СЛАЙД 11 — «Жалоба — это вклад»: «я не могу запустить проект» как issue против личного сообщения]

Человек, который не смог запустить проект и оформил issue, сделал вклад: у нас плохие доки, ему говорят спасибо. Жаловаться нужно постоянно — в форме артефакта. Личное общение не оставляет следа.

## 2. Git в общих чертах (25)

[СЛАЙД 13 — заголовок раздела: команды выучите за вечер, сейчас — модель]

[СЛАЙД 14 — диаграмма: три коммита цепочкой, стрелка «мой родитель», указатель main]

Коммит — снимок всего проекта и ссылка на предыдущий. Имя коммита — хеш содержимого, поэтому прошлое нельзя изменить незаметно.

[СЛАЙД 15 — диаграмма: рабочая папка → индекс → локальный репозиторий → удалённый; add, commit, push, pull]

Индекс — то, что отличает Git от «сохранить всё»: в коммит идёт то, что выбрано осознанно.

[СЛАЙД 16 — терминал: `git init`, `status`, `add`, `status`, `commit`]

Проговорить построчно. В коммит попал один файл из двух.

[СЛАЙД 17 — «Один коммит — одна логическая мысль»: хорошие сообщения против плохих]

Каждый коммит собирается, проходит тесты и объясняет себя сам. Формат «тип: что сделано» позже превратится в changelog и номер версии.

[СЛАЙД 18 — терминал: `git switch -c`, `git log --oneline --graph --all` с развилкой]

Ветка — указатель, она ничего не стоит. Пока вы работали, main ушёл вперёд.

[СЛАЙД 19 — терминал: `git merge --no-ff` и граф после; справа три способа: merge commit, squash, rebase]

Выбор способа слияния — выбор того, как будет читаться история.

[СЛАЙД 20 — диаграмма: задача → ветка → коммиты → pull request → проверки и review → main, с возвратом «не прошло — исправить»]

В main никто не пишет напрямую. Pull request — просьба, её можно отклонить.

[СЛАЙД 21 — таблица: девять команд на каждый день; `push --force` в общую ветку отмечен как запрет]

[СЛАЙД 22 — терминал: `git bisect start`, `git bisect run`, найден первый плохой коммит]

Двоичный поиск по истории: восемь коммитов — три шага, тысяча — десять. Работает только при атомарных коммитах.

[СЛАЙД 23 — «Чему в репозитории не место»: результаты сборки, секреты, большие бинарные файлы и Git LFS]

## 3. Организация репозитория (13)

[СЛАЙД 24 — заголовок раздела: что класть и где]

[СЛАЙД 25 — дерево файлов репозитория слева, назначение каждого справа: README, CONTRIBUTING, CODEOWNERS, workflows, docs/adr, lock-файл, CHANGELOG, .devcontainer]

Кода здесь две папки. Остальное делает из папки с кодом продукт, в который можно войти. ADR — запись «что решили, какие были варианты, почему».

[СЛАЙД 26 — «„Работает у меня“ — не аргумент»: lock-файл, версия SDK в репозитории, dev-контейнер, CI]

Проверка: чистая машина, `git clone`, одна команда. Не собралось — ошибка репозитория, а не новичка.

[СЛАЙД 27 — «Зависимости — это чужой код в вашем продукте»: четыре правила и предупреждение о пакетах, выдуманных ИИ]

[СЛАЙД 28 — итог раздела: «После merge у кода нет автора. Это код репозитория»]

Не вини автора. Сломалось — значит, пропустила система; чиним систему.

## 4. Защита (22)

[СЛАЙД 29 — заголовок раздела: «Never trust the contributor» — ни новичку, ни эксперту, ни агенту, ни себе]

Дисциплина first.

[СЛАЙД 30 — «main всегда рабочий»: пять правил защиты ветки]

Правило, которое можно обойти «один раз, срочно», правилом не является.

[СЛАЙД 31 — диаграмма fail fast: формат → анализ → сборка → тесты → безопасность; «не отформатировано — не заслуживает тестирования»]

[СЛАЙД 32 — столбики «где дешевле поймать ошибку»: pre-commit hook, CI, review, пользователь]

Pre-commit hook — удобство, CI — закон.

[СЛАЙД 33 — «Репозиторий без CI — свалка»: workflow GitHub Actions, собранный из actions, включая свои]

Стройте CI из actions, а не из команд в yaml. Своя action логически завершена и обособлена.

[СЛАЙД 34 — фраза: «Код без теста — это мнение. Код с тестом — факт»]

Эмоциональный блок: личная история о том, что сломалось без теста.

[СЛАЙД 35 — «Тесты: что вы обязаны требовать»: PR без теста, красный тест, баг → сначала тест, тест как документация, тест от ИИ]

[СЛАЙД 36 — «Review — это защита, а не формальность»: ИИ-ревьюер советует, человек решает]

Последнее слово — за лидером проекта; о нём следующая лекция.
