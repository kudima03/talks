## 0. Зачем это всё (5 мин · слайды 1–6)

- **[1]** Титул: «Репозиторий — центр мироздания проекта», лекция 1 из 2.
- **[2]** «Контакты»: три QR (GitHub, Telegram, NuGet) и почта текстом. Регалии голосом, на слайде их нет.
- **[3]** Вопрос в зал: «Кто собирается быть разработчиком ПО? А кто — вайбкодером?» Два голосования подряд. Вторых не осуждать: вопрос не в том, пользуешься ли ты ИИ, а в том, кто отвечает, когда он ошибся.
- **[4]** «Код подешевел»: что осталось дорогим против того, что стало дешёвым. Изменение сейчас ничего не стоит: агент предложит десять за час. Ценность переехала от написания к контролю — проверить, принять или отклонить, не сломать тех, кто уже пользуется, отвечать.
- **[5]** Фраза: «Профессионализм — это не размер кода, который вы способны написать, а размер хаоса, который вы способны контролировать». Проект из 50 разработчиков и агентов. Нужен механизм, который не зависит от доверия к конкретному человеку.
- **[6]** Пять навыков цепочкой: первые три — сегодня, последние два — в следующий раз.

## 1. Философия (15 мин · слайды 7–12)

- **[7]** Заголовок раздела и вопрос: «что должно лежать в репозитории, кроме кода?»
- **[8]** Диаграмма: репозиторий в центре; вокруг код, тесты, документация, задачи, решения, CI и правила, зависимости, релизы. Всё, что нужно знать о продукте, лежит в одном месте — или не существует.
- **[9]** «Проверка: человек с улицы»: пять вопросов новичка и где на них отвечает репозиторий. Self-contained: новый участник ничего не спрашивает, он клонирует и работает. Этот участник может быть агентом.
- **[10]** «Работа — это поставка артефактов»: «изучал», «нашёл проблему», «придумал», «обсудили», «почти готово» → документ, задача в репозитории, черновик изменения, комментарий, коммит. Вся работа — поставка цифровых артефактов. «Делал, думал, анализировал» без следа — имитация.
- **[11]** «Жалоба — это вклад»: «я не могу запустить проект» как задача в репозитории против личного сообщения. Человек, который не смог запустить проект и оформил задачу в репозитории, сделал вклад: у нас плохие доки, ему говорят спасибо. Жаловаться нужно постоянно — в форме артефакта. Личное общение не оставляет следа.
- **[12]** Итог раздела: «Чего нет в репозитории — того не было».

## 2. Git в общих чертах (24 мин · слайды 13–24)

- **[13]** Заголовок раздела: команды выучите за вечер, сейчас — модель.
- **[14]** Диаграмма: три коммита цепочкой, стрелка «мой родитель», указатель main. Коммит — снимок всего проекта и ссылка на предыдущий. Имя коммита — хеш содержимого, поэтому прошлое нельзя изменить незаметно.
- **[15]** Вертикальная диаграмма: три коммита на одной линии снизу вверх, имя main указывает на верхний. Цепочка коммитов — это ветка. Новый коммит встаёт сверху, имя ветки указывает на последний, всё, что ниже, — её история.
- **[16]** Диаграмма: рабочая папка → индекс → локальный репозиторий → удалённый; add, commit, push, pull. Индекс — то, что отличает Git от «сохранить всё»: в коммит идёт то, что выбрано осознанно.
- **[17]** «Первый коммит»: четыре команды крупным моноширинным шрифтом — `git init`, `git status`, `git add`, `git commit` — и что делает каждая. Проговорить по строке и показать вживую. В папке два файла, в снимке один.
- **[18]** «Один коммит — одна логическая мысль»: хорошие сообщения против плохих. Каждый коммит собирается, проходит тесты и объясняет себя сам. Формат «тип: что сделано» позже превратится в changelog и номер версии.
- **[19]** «Ветка под задачу»: вертикальная диаграмма — линия main и вторая линия feat/greet-by-name от того же коммита; команда `git switch -c`. Ветка — ещё одно имя, она ничего не стоит. Пока вы работали, main ушёл вперёд. Две линии надо соединить — способов три.
- **[20]** «Слияние: merge commit»: две линии сходятся в коммите с двумя родителями. История сохранена как была; цена — граф ветвится.
- **[21]** «Слияние: squash»: вся ветка превращается в один новый коммит в main, коммиты ветки остаются в стороне. main прямой, одна задача — один коммит; цена — шаги внутри ветки теряются.
- **[22]** «Слияние: rebase»: коммиты ветки записаны заново поверх свежего main, с новыми хешами. История прямая, и каждый шаг сохранён; коммиты получают новые имена, поэтому нельзя делать это с веткой, которой пользуются другие. О способе договариваются один раз на проект.
- **[23]** Таблица: девять команд на каждый день; `push --force` в общую ветку отмечен как запрет.
- **[24]** «Чему в репозитории не место»: результаты сборки, секреты, большие бинарные файлы и Git LFS.

## 3. Организация репозитория и GitHub (22 мин · слайды 25–35)

- **[25]** Заголовок раздела: одному хватает Git; когда разработчиков много, нужно общее место и правила.
- **[26]** «Когда разработчиков много»: удалённый репозиторий origin сверху, внизу ваш ноутбук, коллега и агент; push, pull, clone. У каждого полная копия с историей, общая правда одна — на сервере. Никто не пересылает файлы друг другу.
- **[27]** «GitHub — это не Git»: программа на вашей машине против площадки в сети. Git отвечает за историю. Всё, что касается совместной работы, — площадка.
- **[28]** «Issue»: номер, обсуждение, метки, исполнитель. Любая работа начинается с записи. Issue может завести кто угодно — это та самая жалоба в форме артефакта.
- **[29]** «Pull request»: задача → ветка → коммиты → pull request → проверки и review → main, с возвратом «не прошло — исправить». В main никто не пишет напрямую. Pull request — просьба, её можно отклонить.
- **[30]** «Actions»: событие → workflow → шаги → прошло или не прошло. Площадка сама запускает проверки на каждое изменение, на чистой машине. Сейчас — только принцип; как строить сценарий — в разделе про защиту.
- **[31]** «Настройки и защиты»: роли, защита веток, обязательные проверки, обязательное review, секреты. Правила проекта — настройки репозитория, а не договорённости в чате. Показать вживую.
- **[32]** Дерево файлов репозитория слева, назначение каждого справа: README, CONTRIBUTING, CODEOWNERS, workflows, docs/adr, lock-файл, CHANGELOG, .devcontainer. Кода здесь две папки. Остальное делает из папки с кодом продукт, в который можно войти. ADR — запись «что решили, какие были варианты, почему».
- **[33]** «„Работает у меня“ — не аргумент»: lock-файл, версия SDK в репозитории, dev-контейнер, CI. Проверка: чистая машина, `git clone`, одна команда. Не собралось — ошибка репозитория, а не новичка.
- **[34]** «Зависимости — это чужой код в вашем продукте»: четыре правила и предупреждение о пакетах, выдуманных ИИ.
- **[35]** Итог раздела: «После merge у кода нет автора. Это код репозитория». Не вини автора. Сломалось — значит, пропустила система; чиним систему.

## 4. Защита (14 мин · слайды 36–42)

- **[36]** Заголовок раздела: «Never trust the contributor» — ни новичку, ни эксперту, ни агенту, ни себе. Дисциплина first.
- **[37]** «main всегда рабочий»: пять правил защиты ветки. Правило, которое можно обойти «один раз, срочно», правилом не является.
- **[38]** Диаграмма fail fast: формат → анализ → сборка → тесты → безопасность; «не отформатировано — не заслуживает тестирования».
- **[39]** Столбики «где дешевле поймать ошибку»: pre-commit hook, CI, review, пользователь. Pre-commit hook — удобство, CI — закон.
- **[40]** «Репозиторий без CI — свалка»: workflow GitHub Actions, собранный из actions, включая свои. Стройте CI из actions, а не из команд в yaml. Своя action логически завершена и обособлена.
- **[41]** Итог лекции: «Механизм не должен зависеть от доверия к конкретному человеку».
- **[42]** «Задавайте вопросы».
