## 1. Тесты и review (10 мин · слайды 3–5)

- **[3]** Заголовок раздела: автоматика проверяет то, что можно проверить машиной; остались две защиты, которые зависят от людей.
- **[4]** «Тесты: что вы обязаны требовать»: «код без теста — мнение, код с тестом — факт»; PR без теста, красный тест, баг → сначала тест, тест как документация, тест от ИИ. Эмоциональный блок: личная история о том, что сломалось без теста. Тесты — то, что позволяет менять код, а не бояться его.
- **[5]** «Review — это защита, а не формальность»: ИИ-ревьюер советует, человек решает. Автоматика говорит «можно», ИИ говорит «похоже, можно», сказать «сливаем» должен кто-то один. Кто этот человек — следующий раздел.

## 2. Лидер (20 мин · слайды 6–13)

- **[6]** Заголовок раздела: важнее любого утверждения — наличие лидера.
- **[7]** Вопрос в зал: «Вы делали проект командой. Кто принимал окончательное решение?» Запомнить ответ «тот, кто больше всех писал».
- **[8]** «Инструкция по саботажу, 1944 год»: пять приёмов из Simple Sabotage Field Manual. Написано для диверсантов — читается как протокол обычного совещания. Всё лечится человеком, который выслушал и сказал «делаем так». Документ прикладывается к лекции.
- **[9]** Фраза: «Самый плохой лидер лучше, чем его отсутствие». Команда хочет лидера; без него она тильтует. Не стесняйтесь принимать и отклонять, поощрять и наказывать.
- **[10]** «Сержант»: доклады (письменно) → лидер слушает → решение → все бегут в одну сторону. Лидер собирает разведку, слушает, потом говорит: всем спасибо, бежим туда. Неверное решение исправят следующим, отсутствие решения исправить нечем.
- **[11]** «Лидером не назначают»: боевой генерал против штабного. Единственный способ стать лидером проекта — стать его главным контрибьютором.
- **[12]** «Что лидер должен»: отвечать, держать дисциплину, расставаться, стоять, вдыхать жизнь. Успехи — команды, провалы — ваши. Тот, кто не работает, деморализует остальных. «Весь мир делает иначе» — не аргумент.
- **[13]** Итог раздела: «Решение всегда за лидером проекта».

## 3. Управление задачами (20 мин · слайды 14–21)

- **[14]** Заголовок раздела: смотрим с двух сторон — владелец с бюджетом и разработчик.
- **[15]** «След изменения»: issue #42 → ветка → pull request #43 → коммит в main → релиз 1.4.0. Про любую строку можно выяснить, кто просил, кто сделал и кто принял.
- **[16]** «Задача — маленькая»: что не так, что считается готовым, один результат, milestone. Вклад измеряется числом принятых микровкладов.
- **[17]** «Draft и пинг»: draft pull request против ping until death. Состояние работы видно в репозитории, а не выясняется в переписке.
- **[18]** «Вы платите за артефакт, а не за время»: цена за задачу против оплаты за время. Дайте цену — придут; не пришли — мало дали. Рабочего дня нет, есть результат.
- **[19]** «Одна задача, две стороны»: владелец репозитория и разработчик. Владельцу достаточно знать профиль и адрес для оплаты. Разработчик жадный — и это честный сигнал.
- **[20]** «Эксперт — это риск»: знание в голове против знания в репозитории. От эксперта избавляются тем, что его знание становится артефактом.
- **[21]** «Нанимайте агентов»: агент — такой же контрибьютор, правила те же.

## 4. Поставка (20 мин · слайды 22–30)

- **[22]** Заголовок раздела: код в main — ещё не продукт.
- **[23]** Trunk-based против GitFlow.
- **[24]** Номер версии 2.4.1 с подписями MAJOR, MINOR, PATCH. Номер версии — обещание тем, кто от вас зависит.
- **[25]** «Не обещайте лишнего»: класс `Greeter` с открытым, устаревшим и закрытым методом. Не декларируем наружу лишнего: задекларировал — обязан держать совместимость. Удаление — только через предупреждение.
- **[26]** «Релиз — это артефакт»: коммит → тег → сборка в CI → пакет и changelog → пользователь.
- **[27]** Feature flags: с флагом и без. Деплой — ещё не релиз. Флаг — долг.
- **[28]** Canary: 1 % → 10 % → 50 % → 100 %, стрелка назад при ухудшении метрик. Откат — обычная процедура.
- **[29]** «Из чего на самом деле собран продукт»: SBOM, сканирование, автообновления, закреплённые версии.
- **[30]** «Соедините пользователя с репозиторием»: ошибка → кнопка «сообщить» в продукте → issue → исправление в релизе.
